## 1. 为什么要做这次复核

1. 文档里每一条可验证的主张，代码真的做到了吗？

3. 边界（"本阶段不做"）是不是真的守住了？

## 4. 结论二：安全探针（3 条发现）

**独立探针确认有效的防线**：伪造 grant 被拒且目标文件未变；参数改一个字符旧审批立即作废；
审计链的五类敏感探针（JWT / Windows 绝对路径 / POSIX 绝对路径 / ANSI / NUL）全部不落盘；
超长记录失败关闭而不是截断；改审计链中间一条被检出；`;` `|` `&` 反引号 `$(` `${` `>` `<` 换行
全部结构性阻断；`..`、绝对路径、盘符相对路径、UNC、NTFS 数据流（`a.py:ads`）全部被拒；
**目录联接（junction）逃逸被执行驱动拒绝**；注册表漂移被 `schema_not_approved` 拦下；
15 条敌对检索查询无一崩溃或越权。

## 7. 交付方式的变化（DORA 视角）

复核还发现一个**非代码**问题：五个阶段的成果从未进入版本历史。按 DORA 的能力清单评价，
这次交付在"能力"维度（文档、测试、评审深度）明显高于"节律"维度（小批次、提交、集成）。
处置：

1. 把工作区切成**五个阶段提交**，每个都在**独立 worktree** 里验证通过：118 / 271 / 297 / 426 / 637；
2. 接上远端与 CI，让"每次提交都跑一遍"从文档里的话变成事实；
3. 加本机 pre-push 门禁（`tools/ci_local.py`），把"别把红的推出去"放在代码离开机器之前；
4. 按 DORA 的因果链补了锁文件真实性、凭据扫描、仓库一致性三项门禁。

## 8. 与原始计划的偏差（都需要知道）

1. **分段提交的口径**：工作区只保留了最终内容，因此凡是"最终内容依赖后续阶段"的文件随其依赖的
   阶段提交（`src/adapters/dsh/hooks.py` 因 `import enforcement` 随 Phase 4 一起提交）。
   结果是 Phase 2 / Phase 3 的提交比阶段文档**少 24 个用例**（297 vs 321、426 vs 450），
   差值恰好是那批 Hook 行为用例；**不凭记忆重建中间版本**。
2. **`uv.lock` 仍然没有**：生成它需要能探测解释器的环境（本机沙箱拒绝）。
   因此把 `requirements.lock` 确立为唯一真相，CI 从它安装，并由一致性门禁看守。
3. **GitHub 侧故意不启用规则集 / 分支保护**：单人仓库里它的边际价值低于"把检查前移到本机"，
   且一旦启用就会禁止直接推 main。决定与理由记名在 `AGENTS.md` 工作方式第 5 条。
4. **Linux 与 Windows 的覆盖差**：本机跑不了 CI 里的 bash-only 步骤（当前 2 步），
   `tools/ci_local.py` 会**显式跳过并打印原因**，不假装跑过。
5. **加字段会让全量重审**：给 `ToolSpec` 加字段会让**全部 6 个工具**的描述哈希都变，
   因此 M2 是六个工具一起重新审核的。这是"描述变了就必须重审"的预期行为，不是意外。
