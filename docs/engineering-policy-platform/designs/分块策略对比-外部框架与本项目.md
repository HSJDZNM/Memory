# 分块策略对比：外部框架与本项目

> **定位**：这是一份**评估记录**（不是提案、不是阶段记录）。对象是 Phase 3 检索层的分块与索引，
> 目的是回答"外部框架有哪些切分策略、它们的默认口径是什么、本项目的 `markdown-sections-1` 该学什么、不该学什么"。
> 结论以**主源**（官方文档 / GitHub 源码）与**本仓库语料上的实测**为准；不确定项集中写在 §8。

## 1. 对比对象与方法

| 项 | 内容 |
| --- | --- |
| 本项目 | `src/retrieval/chunker.py`（`CHUNKER_VERSION = "markdown-sections-1"`）、`indexer.py`、`store.py`；语料 `knowledge/corpus.yaml` |
| LangChain | `langchain-text-splitters`（`libs/text-splitters/`，main 分支）：Character / RecursiveCharacter / Token / MarkdownHeader / MarkdownText / ExperimentalMarkdownSyntax / HTMLHeader / HTMLSection / RecursiveJson / SemanticChunker(experimental) |
| LlamaIndex | `llama-index-core/llama_index/core/node_parser/`（main 分支）：Token / Sentence / Code / Markdown / JSON / SemanticSplitter / SentenceWindow / Hierarchical（+AutoMergingRetriever）/ Langchain / SimpleFile，以及 IngestionPipeline 的 docstore |
| 其他 | Chonkie、semantic-text-splitter（Rust）、Unstructured `chunk_by_title`、Docling HybridChunker、Anthropic Contextual Retrieval、Jina Late Chunking |
| 核对方式 | 官方文档 + GitHub 源码逐项核对默认参数与边界行为；**不采用二手博客** |
| 实测方式 | 同一份仓库语料（6 数据集 / 27 篇 / 535 chunk）上，按各框架**公开算法与默认参数等效复现**后跑三组指标（§4） |

**诚实声明**：本机没有安装 `langchain-text-splitters` / `llama-index-core`，沙箱内 pip 不可用，
因此实测中的外部策略是**按源码逐行复现的等效实现**（含 LangChain Markdown 切分器的围栏感知逻辑）。
数字刻画的是"该算法在这份语料上的行为"，不等于某个具体版本的库构建；参数取自 main 分支，版本变化会漂移。

## 2. 外部框架策略速览

### 2.1 LangChain（基类默认：`chunk_size=4000`、`chunk_overlap=200`、`length_function=len`，**单位是字符不是 token**）

| 策略 | 依据 | 关键默认 | overlap | 结构 | ID |
| --- | --- | --- | --- | --- | --- |
| CharacterTextSplitter | 字符 | `separator="\n\n"` | 有 | 无 | 无（可加 start_index） |
| RecursiveCharacterTextSplitter | 字符 | `separators=["\n\n","\n"," ",""]`、`keep_separator=True` | 有 | 仅段落→句→词边界 | 无 |
| MarkdownHeaderTextSplitter | 标题行 | `headers_to_split_on` **必填**、`strip_headers=True`、**无 chunk_size** | **无** | 标题栈 → metadata，标题不进正文；**围栏感知**（\`\`\` / ~~~ 内不识别标题） | 无 |
| MarkdownTextSplitter | 字符 | = Recursive + Markdown 分隔符表 | 有 | 同上 | 无 |
| ExperimentalMarkdownSyntaxTextSplitter | 行 | 默认 `#`…`######`，代码块单独成块 | 无 | Header/Code 元数据 | 无 |
| TokenTextSplitter | tiktoken token | `encoding_name="gpt2"` | 有 | 无 | 无 |
| HTMLHeader / HTMLSection | DOM 元素 / 标签+字号 | `headers_to_split_on` 必填 | 无 / 有 | 祖先标题 → metadata | 无 |
| RecursiveJsonSplitter | JSON | `max_chunk_size=2000` | 无 | 保留 key 路径 | 无 |
| SemanticChunker（experimental，README 自述 sunset） | 句子 embedding 距离 | `breakpoint_threshold_type="percentile"`、`buffer_size=1`、**无 chunk_size 上限** | 无 | 无 | 无 |

要点：**LangChain 的 Markdown 切分器是围栏感知的**（源码 `in_code_block`/`opening_fence`），但它逐行
`line.strip()` 后再入块——**缩进会被抹掉**（本语料 1493 行有缩进的行全部受影响）。它也没有 `chunk_size`：
超长小节只能靠后接别的 splitter。

### 2.2 LlamaIndex（长度单位是 **token**）

| 策略 | 依据 | 关键默认 | overlap | 结构 | ID |
| --- | --- | --- | --- | --- | --- |
| TokenTextSplitter | token | `chunk_size=1024`、`chunk_overlap=20`、`separator=" "`、`backup_separators=["\n"]` | 有（按 token 回填） | 无 | `uuid4` |
| SentenceSplitter | 段落→句子→次级正则→空格→逐字符，按 token 计长 | `chunk_size=1024`、`chunk_overlap=200`、`paragraph_separator="\n\n\n"`、`secondary_chunking_regex` 含中文标点 `。？！`、分句靠 nltk punkt | 有 | 无 | `uuid4` |
| CodeSplitter | tree-sitter AST | `language` 必填、`max_chars=1500`、`max_tokens=512`；`chunk_lines=40`/`chunk_lines_overlap=15` 在 main 的切分逻辑里**未被读取** | 无 | 无 | `uuid4` |
| MarkdownNodeParser | 行级 `^(#+)\s` 标题 | **无 chunk_size/overlap**；`\`\`\`` 内不识别标题 | 无 | `metadata["header_path"]`（只含父级） | `uuid4` |
| SemanticSplitterNodeParser | 相邻句组 embedding 距离，取第 95 百分位为断点 | `breakpoint_percentile_threshold=95`、`embed_model` 必填 | 无 | 原句入 metadata | `uuid4` |
| SentenceWindowNodeParser | 一句一节点 + 窗口 | `window_size=3` | 无 | window/original_text 入 metadata | `uuid4` |
| HierarchicalNodeParser | 多级 SentenceSplitter | `chunk_sizes=[2048,512,128]` | 每级 20 | PARENT/CHILD 关系 | `uuid4` |
| IngestionPipeline + docstore | 增量/去重 | `docstore_strategy=UPSERTS` | — | docstore 存 `{doc_id: node.hash}` | 见下 |

要点：**LlamaIndex 默认不给稳定 ID**（`default_id_func = str(uuid.uuid4())`），同一段原文重建索引
node_id 会变；内容哈希是另一个字段（`TextNode.hash = sha256(text + metadata)`），docstore 靠它判重。
`AutoMergingRetriever` 的 `simple_ratio_thresh=0.5`：命中的子节点数达到父节点子节点总数一半时，
用**父节点**替换子节点——这是"分层召回"的现成实现。

| --- | --- | --- | --- | --- |

### 2.4 三个共性结论

1. **没有一家默认给"位置稳定 ID"**：LlamaIndex/Chonkie 是 uuid4；LangChain 的 indexing API 用
   `uuid5(sha1(内容)+sha1(metadata))`（同一内容+同一 metadata 稳定，**改 metadata 就换 ID**）；
   只有 Unstructured 是按内容哈希派生的确定性 ID。**都没有"内容变了但位置不变"的语义**。
2. **默认参数不通用**：LangChain 4000 字符 / LlamaIndex 1024 token / Chonkie 2048 / Unstructured 500 字符
   / Docling = 所选模型的 max_seq_length。跨框架抄默认值没有意义。
3. **CJK 默认都不覆盖**：LangChain 的 `Language` 枚举无 zh，官方建议手动把 `。` `，` 等加进
   `separators`；LlamaIndex 的 `secondary_chunking_regex` 虽然含 `。？！`，但默认 nltk punkt 是英文模型，
   中文会退化成逐字符兜底；Chonkie 需要切到 `lang="zh"` 配方。

## 3. 本项目的分块与索引（对照基线）

六条规则（详见 `src/retrieval/chunker.py` 模块头与 `docs/architecture/规则文档转化为规则.md` 台阶 3）：
剥 front matter（元数据转存 `documents.front_matter`）→ 围栏外识别标题（标题行**只进** `heading_path`）→
空行为界块化（代码块为原子）→ 按 `max_chunk_chars=1200` 打包、`hard_max_chunk_chars=8000` 兜底 →
`chunk_id = hash(document_id | anchor | part_index)`、`text_hash = sha256(原文)` → 幂等重建（只动相关 chunk）。

与外部框架的三个结构差异：

| 维度 | 外部主流 | 本项目 |
| --- | --- | --- |
| 身份 | 内容哈希（LangChain）/ uuid4（LlamaIndex、Chonkie） | **位置 ID + 内容哈希分离**：改字不改 `chunk_id`，只改 `text_hash`/`revision` |
| 边界 | 窗口/句子/语义模型 | **章节 + 字符预算**：不跨章节，代码块永不切断（记 `oversized`） |
| 重叠 | 默认 200 字符/token（LangChain、LlamaIndex） | **无 overlap**：Context 层按 `text_hash` 去重，重叠会与去重语义打架 |
| 溯源 | 无（元数据可选） | `rule_sources(rule_id, rule_version, chunk_id)` 表 + 标题路径前缀解析 |

## 4. 实测：同一份语料、同一套指标

**指标定义**（全部在本仓库语料上计算）：

- **切断代码块**：chunk 文本内围栏计数为奇数的 chunk 数（围栏感知扫描）。
- **正文残留标题行**：chunk 内（围栏外）出现的 ATX 标题行数。含义随策略而变：对无结构策略（recursive、token 窗口）
  意味着该 chunk **跨了章节边界**；对 `MarkdownHeaderTextSplitter` 意味着 `####` 及更深的标题**没参与切分**（默认只配 `#`/`##`/`###`）；
  本项目为 0 是设计结果——标题行只进 `heading_path`，正文里一行都不留。
- **字符产出比**：所有 chunk 去空白字符数 ÷ 参考文本去空白字符数。>1 = 有重复（overlap）；<1 = 有内容未进块。
- **编辑稳定性（变化率）**：在**每篇**文档开头插入同一段固定文本（294 字符）后，"文本在旧集合里找不到"的 chunk 占比。
  表中数值是**变化率**——**越低越好**；"稳定性"是它的补数，但两者只在"每篇各自算比例再平均"这一种聚合下严格互补
  （见 §4.2 的聚合口径说明）。
- **聚合口径**：比率类指标必须写明是"每篇算比例再平均"还是"总体相除"——本项目 8% 属前者，换成后者是 4.8%，
  两者都不算错，但不可混用（同一个测量会因为聚合方式不同而给出不同数字）。

### 4.1 结构保真（6 数据集 / 27 篇）

| 策略 | chunk 数 | 均长 | p95 | 最长 | 切断代码块 | 正文残留标题行 | 字符产出比 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **本项目 markdown-sections-1** | 535 | 655 | 1163 | 3846 | **0** | **0** | 1.00 |
| LC recursive 4000/200（框架默认） | 117 | 3229 | 3978 | 3996 | 10 | 452 | 1.01 |
| LC recursive 1000/200（教程常用） | 529 | 755 | 992 | 1102 | 31 | 478 | 1.07 |
| LC markdown-header（忠实复现） | 364 | 973 | 3163 | 8252 | 0 | 39 | 0.96 |
| token-window 1024/200（tiktoken） | 110 | 4053 | 5438 | 5627 | 6 | 475 | 1.17 |

读法：LangChain 默认的 4000 字符窗口在这份语料上只产出 117 块（均长 3229），**452 处正文残留标题行**
意味着大量 chunk 跨章节；Markdown 切分器不切代码块（0 处切断）但**没有尺寸上限**（最长 8252 字符），
并把 1493 行缩进抹平；token 窗口重复率最高（1.17）。

### 4.2 编辑稳定性（变化率，越低越好）

| 策略 | 文本变化的 chunk 占比 | 新增 chunk | 平均 chunk 数（改前） |
| --- | --- | --- | --- |
| **本项目** | **8%**（每篇 +1 个） | +27 | 19.8 |
| LC recursive 4000/200 | 57% | +1 | 4.3 |
| LC recursive 1000/200 | 28% | +6 | 19.6 |
| LC markdown-header | 11% | +0 | 13.5 |
| token-window 1024/200 | 100% | +3 | 4.1 |

读法：窗口类策略的边界是**位置**的函数，开头插入内容会让后面所有窗口整体位移（token 窗口 100% 全变）；
本项目与 Markdown 切分器的边界是**结构**的函数，只有被改的那一节会变——这正是"只动相关 chunk"能成立的前提。

**不要只看百分比**："变化 chunk 占比"的分母是块数，块切得越细，同一个改动看起来越"稳定"。用字符级口径复核
（插入内容 294 字符，"放大系数" = 变化字符数 ÷ 294）：

| 策略 | 变化 chunk 占比 | 变化**字符**占比 | 变化 chunk 数（绝对值） | 变化字符数（绝对值） | 放大系数 |
| --- | --- | --- | --- | --- | --- |
| **本项目** | 8% | 8% | 1.0 | 593 | **2.0×** |
| LC markdown-header | 11% | 8% | 1.0 | 592 | 2.0× |
| LC recursive 1000/200 | 28% | 29% | 2.8 | 2299 | 7.8× |
| LC recursive 4000/200 | 57% | 59% | 2.0 | 6628 | 22× |
| token-window 1024/200 | 100% | 100% | 4.2 | 16907 | 57× |

结论：两种口径给出**同一排序**（本例中分母陷阱没有翻盘），所以增量成本应按"变化字符数"读——
它才是重写数据库行、重建 FTS 行与推进 `revision` 的实际工作量。变化字符数的下界是"被改段所在块的大小"
（所以本项目 ≈ 2×：新块同时包含插入文本与原前言），而窗口/重叠策略会把改动**放大到后续所有块**。

**本项目的 8% 是怎么算出来的**：27 篇文档**每篇恰好变化 1 个 chunk**（分布 `{1: 27}`），逐篇变化率从 1.6%（大文档）
到 25.0%（`documentation-quality.md` 只有 6 个 chunk）不等；
**口径 A（每篇变化率求平均）= 7.6%**（即表中的 8%），**口径 B（27 ÷ 562 总体相除）= 4.8%**。
所以正确的读法是"**变化率 8%，即 92% 的 chunk 一字未动（平均意义）**"，而不是"稳定性 8%"，也不是 27/535 = 5%。

### 4.3 同一评测集的检索指标（7 条固定查询，同一 FTS5 引擎）

| 策略 | hit@5 | support@5 | recall@5 | chunk 数 |
| --- | --- | --- | --- | --- |
| **本项目** | 1.00 | 1.00 | 0.914 | 535 |
| LC recursive 4000/200 | 1.00 | 1.00 | 0.914 | 117 |
| LC recursive 1000/200 | 1.00 | 1.00 | 0.886 | 529 |
| LC markdown-header | 1.00 | 1.00 | 0.886 | 364 |
| token-window 1024/200 | 1.00 | 1.00 | **0.943** | 110 |

**这张表最重要的一行是"五个策略全部满分"**：在本仓库自己的 7 条查询、门槛 hit@5 = support@5 = 1.0 的
评测集上，**分块策略分不出胜负**（recall 的细微差别来自 chunk 大小，不构成选型依据）。
这与学术证据一致（§5）——换策略的收益不稳定，**决定性的差异在结构保真、可追溯、增量重建这些工程属性上**，
而那正是本项目的设计目标。

## 6. 结论与建议

### 6.1 建议采纳

| 优先级 | 变更 | 依据 | 成本/风险 |
| --- | --- | --- | --- |
| **P0** | 修掉 §7 的**静默截断**（`_prose_pieces` 丢掉了 `_split_prose` 的 truncated/original） | 本仓库自己的不变式"丢了多少必须能算出来"被破坏；实测已发生 1 次（丢 53 字符，run 报告却写 `truncated_chunks=0`） | 2 行改动 + 1 条回归测试；不改变正常路径行为 |
| **P1** | 给"单行超预算"加 **CJK 句读兜底**（`。！？；` 处可断，再退到硬截断） | 本语料最长单行 1253 字符（英文，已触发 P0）；中文文档常整段无换行，届时是**系统性**问题。外部三家都把 CJK 标点放进分隔符集（LangChain 官方建议、Chonkie `zh` 配方、LlamaIndex `secondary_chunking_regex` 默认含 `。？！`） | 低：仍无损（只在标点处断），不破坏 ID/哈希语义；需补测试 |

### 6.2 明确不采纳

| 不采纳 | 理由 |
| --- | --- |
| 语义/LLM 切分（SemanticChunker、SemanticSplitter、Slumber、Neural） | 学术证据显示收益不稳健且真实文档常被固定长度反超；需要模型依赖，违反核心层"只依赖标准库/pydantic/PyYAML"的约束与失败关闭要求；边界随模型版本漂移，破坏"相同输入相同结论" |
| 盲目加 overlap | Context 层按 `text_hash` 去重，重叠文本会被判重丢弃；且"每个字符只落进一个 chunk"是增量 diff 与无损不变式的基础 |
| 用内容哈希当 chunk ID | 内容一改 ID 就变，规则溯源会断；本项目"位置 ID + 内容哈希分离"更适合"文档 → 规则"的溯源语义 |
| 让框架接管索引/增量 | 外部框架的 docstore/upsert 解决的是"向量库同步"，本项目的需求是"重建幂等 + 删除失效 + 溯源级联"，已有闭合实现与测试 |
| 摘要层（RAPTOR 式） | 实测报告约 4% 摘要含幻觉；治理语料不得改写 |

### 6.3 本项目已经领先的地方（对照外部默认）

- **位置稳定 ID + 内容哈希 + `revision`**：外部默认没有（§2.4 结论 1）；
- **围栏原子 + 章节边界 + 预算三者同时成立**：外部通常只有其中一两项（MarkdownHeader 有边界无预算，
  Recursive 有预算无边界）；
- **截断/超长/空章节/漂移全部计数进 run 报告**（除 §7 那处缺陷）；
- **规则溯源表**（`rule_sources`）与隔离清单（`quarantine`）在主源框架里没有对应物。

## 7. 顺带发现的缺陷：一处**静默截断**（实测，待修）

**现象**：`docs/dora-capabilities/core/continuous-integration.md` 里有一行 1253 字符 > `max_chunk_chars=1200`。
索引后该行**只留下前 1200 字符**，所在 chunk 的 `char_count=1200`、`truncated=0`、`original_chars=NULL`；
全库 `truncated=1` 的 chunk 数为 0，run 报告写 `truncated_chunks=0`。**53 个字符无记录地消失。**

**根因**：`src/retrieval/chunker.py` 的 `_pack()`（约 496–507 行）在"单块超预算的段落"分支调用 `_prose_pieces()`（548–551 行），
而 `_prose_pieces()` 只返回文本、**丢掉了 `_split_prose()` 返回的 `(text, truncated, original)` 三元组**；
随后的 `emit(..., truncated=False, original=None, oversized=len(text) > max_chars)` 把这次截断硬写成"没截断"。
（代码块路径不受影响：超硬上限的代码块走另一分支，会正确记录 `truncated + original_chars`。）

**为什么没有测试拦住**：无损不变式 `blocks_are_preserved()` 只在单元测试里被调用，
**索引运行期不校验**（`grep blocks_are_preserved src/` 只有定义处）；测试夹具也没有"单行 > max_chars"的用例。

**影响面**：当前语料 1 行 / 53 字符；但中文语料"整段无换行"会**成片触发**——这与 §6.1 的 P1 是同一个根因。

**建议修法**（二选一）：
1. 最小改动：`_pack()` 的段落超预算分支直接调用 `_split_prose()` 并把 `truncated/original_chars` 透传进 `emit`；
2. 更彻底：同一分支先按句读切分（P1），只有单句仍超硬上限才截断——两条一起做最自然。
