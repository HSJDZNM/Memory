**B2 控制台会不会变成"第二份业务逻辑"（AGENTS.md 30）？特别是"结构化起草表单"。**
- **支持"已经越界"的最强理由**：前端 §6.2 让表单固化"checker 6 选 1、scope 6 维、severity 4 值、规则体键名随
  checker 变形"——这些常数来自 `src/policy/checkers.py` 与规则模型，而代码里**没有任何只读接口**把它们交给前端
  （后端 §2.7 明说"没有 checker / 验证器 registry 的只读接口"）。即：**前端会自己抄一份 C13–C21 的规则**，
  并在本地给出"字段 OK / 错误"的结论；后端一旦数据化扩展（新增 checker/维度），界面会安静地给出不一致的判断。
- **反对"已经越界"的最强理由**：表单只约束**输入形状与可选项**，不产出 allow/block；不变量要求的是"判定只有
  一条路径"，输入收敛是 UX 而非判定；G3 落地后每个字段都能回后端复核；把 C13–C21 的**形状**做进表单，
  比让用户自由写 YAML 更符合"受控字段"原意（前端 §5.7 已禁止自由文本编辑器）。
- **结论：处于"可接受的偏置、但必须收口"**。三条硬要求：① 枚举/维度/规则体模板**必须来自后端只读接口**
  （随 G3/G5 提供），不得硬编码；② 一切"通过/OK"文案只能由后端响应字段驱动（前端 §4.3-G3 已写对）；
  ③ 跨条规则的一致性（C22 唯一性、C23 原子性）**不得**在前端实现——那才是真正的"第二份业务逻辑"。不满足 ①，我判定为越界。

- **结论：控制台若用 innerHTML/模板渲染 chunk 正文，就是一个真实的存储型 XSS 面**（内容来自外部镜像，属不可信数据）。
  严重级别：高（P0"只读浏览"就会踩到）。**不需要后端改动**即可缓解：前端一律 `textContent`/输出转义、禁用 innerHTML、显示层
  中和控制字符，并把"镜像内容永不作为 HTML 解析"写成验收断言。超长由 `max_chunk_chars=1200` / `hard_max_chunk_chars=8000`
  与响应预算兜住，但**没有分页接口**（后端 §6.2 已写明），界面必须自作分片。

**B6 `evidence_unavailable` 判为"API 上不可达"是否成立？**
- **成立**（grep：policy_api 内只有 `errors.py:59` 枚举与 `:97` 状态映射，无抛出点；真实抛出点在
  `src/adapters/runtime.py:871/878/894/901/912/919`，编排侧在 `orchestration/models.py:160`、`client.py:77`）。
  界面不为它写专门分支是对的。
- 严重性：**P0/P1 无所谓，P2 必须补**——P2 的"提交"由编排层驱动，失败码是编排层 FailureCode
  （`side_effect_unknown` / `approval_param_mismatch` / `evidence_unavailable` / needs_human），不是 policy_api 的 33 个码；
  只映射 policy_api 会让 P2 把它们显示成"未识别错误"。前端 §7.2 只映射了 policy_api 一侧，**应补编排侧映射表**。

**B7 同源静态托管 vs 独立源：AGENTS.md 30/35 与契约快照风险。**
- **字面上不违反 30/35**：静态挂载不把 Web 框架引入核心层，也不新增判定路径；AGENTS.md 35 关心的是
  `src/orchestration/` 可被删除后平台独立运行，与静态目录无关。但代价真实：① 前端与"判定传输边界"同进程
  （前端缺陷连带判定服务）；② 挂根路径改掉未知路径的 404/405 语义（A2-6），使 AGENTS.md 33 的"结构化错误码推导"
  对未知路径不再统一；③ 既有契约测试按 `route.name` 过滤（`test_api_protocol.py:174-180`），**挂载的副作用不会被 CI 发现**
  （后端"不会让既有测试变红"的读码结论正确，但**同时也意味着没有守护**）。
- **快照维护风险**：`contract.ENDPOINTS` 与 `app.openapi()["paths"]` 是**全等**比较（`contract.py:144-151`），
  任何**新 API 路由**（G1–G6）都必须三处同步（ROUTES、ENDPOINTS、api/openapi.json）——这是设计使然；
  真正的风险是**文档把"静态挂载"与"新增 API 路由"混写**（后端 §6.4:819），会诱使实施者做无谓的 `openapi --write`。
- **取舍**：默认选**反向代理同源**（后端 §6.4 形态 C / 前端 §8 形态 D）：policy_api 零改动、零契约影响、与判定进程解耦、
  不引入 A2-6 的语义变化。同源静态挂载（A）保留为**本地开发形态**，但必须补两条测试：未知路径 404/405 与挂载前一致、
  `paths == served` 仍成立。独立源 + CORS（B）**今天不可用**（无 ACAO），且要新增 origin 白名单配置（新部署数据 + 新契约字段）。

## C. 结论

**C1 前后端连接可行性：今天"能连"，但只能同源；P0 是"只读骨架"，不是"操作平台"。**
- P0 最小可行形态：**反向代理同源**（零代码、零契约）承载静态页 + 直接调用现有 6 条路由；必须单进程时用
  同源静态挂载（A）+ 补 A2-6 的回归测试。独立源 SPA **不可用**（实测无 ACAO、预检 405）。
- 代价一条：P0 的"文档 → 规则"体验**残缺**——镜像清单/sha256/漂移（G1）、分块浏览（G2）、checker 注册表与门禁聚合（G5）、
  会话身份（G6）都**没有 HTTP 面**；只能用 `retrieve` 命中片段间接浏览来源，用 `/v1/health/ready` 看粗粒度健康。
- 风险一条：**响应形状不受契约快照保护**（`app.py:270-273` 不声明 `response_model`；快照只覆盖请求体与错误信封，
  前端 §9.3 也承认）。界面必须自带"字段存在性"测试，否则后端一次拼装改动就能静默打断面板。

**C2 前端操作逻辑完备性：作为"约束清单"质量高，作为"可实施的操作平台"不足以独立支撑。**
- 12 行失败语义 + 10 条反模式 + 3 条渲染不变量：**覆盖度好**，未发现"把失败渲染成 allow"的缝隙；503/504≠allow、
  skipped≠通过、幂等空体、两种 retryable、readiness 不取令牌等关键结论全部实测成立。
- D0–D7 缺三件：① **草稿存储不存在**（文档自标【提案】），D0–D6 无载体，"草稿 id/版本"与 C22 version 语义、
  C30 `rule_id@version` 的对应关系未定义；② **D5 的 `action_hash` 谁来算没写清**——§3.2 写"先算并展示 `action_hash`"，
  但该值只能由 Phase 4/编排层的 `binding()` 产出，前端不得自算（否则就是"客户端自带决策"）；③ **D7 缺"生效失败"分支**：
  规则文件变了就整份替换（`services.py:73-97`），但**装配失败**时下一个请求是 503 `rule_set_unavailable`（我实测装配失败路径），
  "已生效/未生效/生效失败"三态要分开。
- 两个缺口：必须 `include_evidence=true` 才能显示跳过原因（B3）；必须补编排侧失败码映射（B6）。
- T1–T12 里 T4/T5（`validator_unavailable`、缺 Ruff → critical）在 P0 只读面**不可验收**，应标注"P1 起"，否则验收会落空。

**C3 本提案整体判定：必须先修既有不一致（再按 P0 → P3 分期推进）。**
- 必须先修：**A3-2 漂移静默**（G1 的验收要变成"先做 G1，或先在界面写死未核对"）、**B1 的 content 模式绕过审批**
  （设计缺陷，不是文档问题）；再加一条**零成本项**：B5 的渲染转义规则（前端一行约束 + 一条断言）。
- **反方最强论点（steelman）**：既有不一致都是**文档/注释层面的口径问题**，运行期行为自洽且失败关闭（我实测四态、
  两种 retryable、空集拒绝替换、坏规则整批不加载全部成立）；`hash_drift` 常量与 DTO 死码不改变任何判定结果，
  把 P0 只读阶段按"先修不一致"卡住，是把低风险阶段拖成治理项目；真正该先做的只是给静态内容加转义、把 G1 补上，其余并行。
- **我的回应**：接受"不影响判定"这一半，不接受"因此不阻塞"。本提案的卖点正是"操作平台不撒谎、不绕过门禁"，
  而 A3-2 与 B1 各自打破一条对外承诺：前者让溯源页显示"无漂移"，后者让规则变更"看起来审批过、实际没有审批"。
  这两条不修，P2 一上线就会生产**假的治理证据**——不是"低风险的只读阶段"，而是在治理链上开一个后门。

**C4 本环境无法验证的部分**
1. **504**（`evaluate_timeout` / `retrieve_timeout` / `validate_timeout`）：本机 evaluate < 1ms、`budget_ms=1` 仍 200（实测），
   无法构造自然超时；超时语义只有读码（`runtime.py:542-549` + `errors.py:93-95`）。
2. **503 `policy_busy`**：TestClient 单线程，未构造"占满 8 个并发槽 + 0.5s 等待"。
3. **503 `audit_unavailable` / `idempotency_unavailable`**：需不可写的日志/台账路径或只读文件系统，Windows 上未构造。
4. **CORS 的浏览器实际行为**：我只能证明服务端不发 ACAO、预检 405；"浏览器因此阻断"是 Fetch 规范推断。
5. **多 worker**（`policy_api.cli serve` 多进程）下的限流/幂等口径。
6. **`retrieve` 的 `empty` 状态与 `available=false` 组合**：未能构造（与后端 §7.2 自述相同）。
7. **XSS 的实际利用**：只证明响应原样携带 `<script>` 与控制字符，**没有**做浏览器 DOM 渲染实验。
8. 未跑全量 `pytest`；未执行 `openapi --write`；后端 §3.9 的"规则数 ↔ 响应字节"规模表我**没有重跑**（只复核阈值结论在 6 条规则下成立）。
9. 前端技术形态的性能、无障碍、浏览器兼容性无法评估（仓库没有前端代码可测）。
