## 0. 一句话结论

**能做，但"操作平台"的正确定位是「受控的作者工作台」，不是"文档→规则的转换器"。**

三句话拆开说：

1. **可做的部分**：把七个台阶里除"提炼判断"以外的**操作、约束与证据**搬进界面——镜像与哈希状态、语料登记、
   分块与索引、checker 选择、规则草稿的结构化编写、加载与门禁预演、审批与生效、溯源查询。
   这些今天的载体是 8 条 CLI 命令与手写 YAML（`docs/architecture/规则文档转化为规则.md:290-331`）。
2. **不能做也不应做的部分**：**"把文档喂进去自动产出规则"**。仓库把"不能自动判定"当作安全属性：
   台阶 4 是整条链路里**唯一没有代码自动完成**的一步，且**刻意不引入 LLM**
   （`规则文档转化为规则.md:116-129`；`功能清单.md:253` 明确"LLM 调用 / MCP / 向量数据库：至今没有引入"），
   来源必须是本地的（`source.kind` 只接受 `project-policy` / `standard`，C20）。
3. **一条不可逾越的红线**：界面不得拥有自己的"生效写入"路径。改规则文件的既有受控入口是
   `registry/tool-registry.yaml:317` 的 `orc.policy.edit`（`risk: reversible_write`、`approval: required`、
   路径白名单 `^policies/[A-Za-z0-9._/-]+$`、四个 post_check、**审批必须与 `action_hash` 绑定**），
   而 **API 没有 enforce 路由**（AGENTS.md 第 39 条）——所以"提交并生效"只能经由 Phase 4 受控执行链，而不是控制台自己写文件。

因此：**平台的价值不是"少想一步"，而是"把 C1–C33 变成界面上看得见的约束"**——降低偶发难度（YAML 形状、命令顺序、
checker 与验证器的对应关系），保留本质难度（"这段原文是否真的可判定"这一次人类判断）。

## 1. 事实基座：今天的"文档 → 规则"是怎么走的

七个台阶、三道硬门禁、一个约定（出处：`规则文档转化为规则.md` 全文；条件编号沿用该文 §4 的 C1–C33）：

| 台阶 | 今天的载体 | 强制门禁 | 谁在拦 |
| --- | --- | --- | --- |
| 1 镜像与哈希登记 | `tools/mirror_docs.py` → `docs/<mirror>/manifest.json` | 目录 + manifest + `pages` 列表 | C1–C4；哈希漂移 → `verify` 退出 1（C6，**不许静默**） |
| 2 语料登记 | `knowledge/corpus.yaml` 的 `datasets.entries` | 条目必须能在 manifest 里找到、`license` 必填 | C1–C5（加载失败即退出码 2） |
| 3 分块与索引 | `src/retrieval/` → `.tmp/retrieval/index.sqlite3` | 幂等：同输入两次摄取 chunk_id/text_hash 一致 | C7–C10 |
| 4 **提炼** | **人读原文，手写规则字段** | 没有代码门禁——这是唯一的人工步骤 | 无（正是本节的重点） |
| 5 规则文件 | `policies/<domain>/<ID>.yaml` | 字段/枚举/维度/规则体与 checker 一致 | C13–C21（模型校验） |
| 6 验证器覆盖 | `validation/validators.yaml` | 每个受支持 checker 至少一个验证器声明供证 | C25（注册表整体加载失败） |
| 7 生效 / 溯源 / 变更 | `policy.loader` 原子加载 → `RuleSet.identity`；`corpus.yaml` 的 `rule_sources` | 一条坏 = 整批不加载；审计身份 = `rule_id@version` | C22–C24、C30–C33 |

三个必须如实说出来的现状落差（不是修辞，是可核对的事实）：

- `rule_sources` 溯源登记**当前是空列表**，所以"由镜像文档提炼"的规则（如 `DOC-001`）今天查不回原文 chunk
  （`规则文档转化为规则.md:285-288`）。
- `source.path` 只做形状校验，**不校验文件是否存在**（`规则文档转化为规则.md:237-238`）——
  "来源指回真实文件"目前靠评审，不靠代码。
- `功能清单.md:256`：审批"首版是人工门禁写下的结构化记录，**不做签名与独立审批人名册**"——
  角色分离（作者 ≠ 审批人）今天**没有**任何机制强制，界面也不许假装强制。

服务侧的现状同样要摆清楚：Phase 7 的 HTTP 路由只有六个
（`src/policy_api/runtime.py:73`：`evaluate` / `retrieve` / `validate` / `health` / `readiness` / `metrics`），
令牌与角色来自 `api/policy-api.yaml`（演示值 `local-dev` / `dsh-agent` / `ops-monitor`；
角色只有 `developer` 与 `ops`）。**仓库没有任何前端资源**（`git ls-files` 里没有 html/js/ts），
唯一的静态页先例是 `tools/mirror_docs.py` + `tools/dora_site.py` 生成的镜像站点。

## 2. 逐台阶能力矩阵：界面能做什么、不能做什么

| 台阶 | 界面**能**做（且不违反不变量） | 界面**不能**做（必须结构性拦住的诱惑） | 需要的后端能力（缺口） |
| --- | --- | --- | --- |
| 1 镜像 | 查看每个镜像的 `fetched_at`、逐页 `sha256`/`bytes`；跑一致性检查并显示退出码 0/1 | 在界面上编辑镜像原文；手改哈希"让它对上" | 镜像状态读取（今天没有对应路由） |
| 2 语料 | 以受控字段登记 dataset/entries（`tier`/`visibility`/`license` 下拉，不允许自由文本）；保存前跑清单预检 | 登记 manifest 里不存在的页面；缺 `license` 硬提交；把条目写成"外部 URL"当来源 | 语料读取 + 清单预检（无） |
| 3 索引 | 查看索引版本与文档/chunk（`heading_path`、`text_hash`）；发起重建（长任务）；按 chunk 检索 | 直接改 chunk 正文（chunk 是**产物**）；把哈希漂移当"提示"忽略 | 作业模型（索引是子进程，今天 API 无 job 概念）+ 复用 `retrieve` |
| 4 **提炼** | 结构化表单：从 chunk 出发，`checker` 6 选 1、`scope` 6 维、`severity` 4 值、规则体随 checker 变形、`message` 必填、`source` 指回该 chunk；**边填边跑门禁** | "一键从文档生成规则"；把"建议/尽量"的段落转成规则；没有 checker/验证器覆盖的要求落成规则；任何 LLM 裁决 | 草稿存储 + 校验预演（无） |
| 5 规则文件 | 草稿编辑、diff 预览、`version` 递增提醒、加载预演（**不替换现网规则集**） | 直接写 `policies/`；原地改已发布规则却不递增 `version`；"强制启用"开关 | `policy.loader` 预演路由（无） |
| 6 验证器覆盖 | 展示"该 checker 由哪个验证器供证、是否 `critical`、`requires` 阶段、外部工具探针是否就绪" | 在界面上把未覆盖的 checker 标成"可用"（C25 在加载阶段就会失败，界面不该装作可选） | 注册表只读视图（`validators.cli registry` 已有 CLI，无 HTTP 面） |
| 7 生效/溯源 | 显示生效前后 `rule_set_hash` 与影响面（检索缓存、Phase 7 观测摘要、Phase 8 checkpoint 兼容性）；提交审批并展示 `action_hash`、diff、post_check、回滚能力；登记 `rule_sources` | 跳过原子性；把"审批通过"当自动的（图到达审批节点 ≠ 用户批准）；跨租户查看/提交 | 规则集摘要与生效预览、溯源读写、审批与提交（走 Phase 4） |

## 3. 辩证：UI 化 ≠ 自动化，而且"顺手"本身是风险

**正题**：这条链路今天要人背下 6 个 checker、C1–C33 的条件表、YAML 形状与 8 条命令；
把它做成界面，能显著降低"偶发难度"（记住形状、抄对格式、跑对顺序）。

**反题**：仓库的设计**故意**把"不能自动判定"当作安全属性——来源必须本地（C20）、
未知字段/枚举/checker 一律报错（C17、C21）、判定必须由确定性证据给出（`ARCH-001` 的注释写明"不得由 LLM 裁决"）。
把这些约束"藏进漂亮界面"，就可能在无意中把"这是人的判断"变成"这是系统的产出"。

**合题**：界面不替人做判断，而是让**判断的约束与后果即时可见**——把知识变成界面形状
（选不出不存在的 checker、填不出不合法的 scope、门禁失败当场显示"整批不加载"），
同时把"这一段原文是否可判定"留给人。

必须提前回击的三个反对意见（都不弱，别绕过）：

| 反对意见 | 强在哪 | 回答 |
| --- | --- | --- |
| 单人仓库维护前端，边际成本高于收益 | 是真的：多一套界面就多一处会漂移的资产（`文件:行` 之外又多"界面:文案"） | 采用**零构建**形态（静态 HTML + 原生 JS，由 API 同源托管；先例 `tools/dora_site.py`），不引入 Node 工具链；P0 只做只读与预演 |
| 有界面就有绕过门禁的入口 | 也是真的：任何"写入"按钮都是新的攻击面 | 反过来看：**现状下手写 YAML 直接落盘是没有审批的**，只有"加载门禁"；走 `orc.policy.edit`（`approval: required` + `action_hash` 绑定）反而**多一道**门禁。前提是控制台没有第二条写路径 |
| 控制台会变成"第二份业务逻辑" | AGENTS.md 第 30 条的正面禁止：判定只有 `policy.engine.evaluate` 一条路径 | 结构性约束：前端不做任何判定；所有校验都必须调用后端同一套代码（`policy.loader` / `validation` 注册表 / `engine`），接口只返回它们的结论 |

## 4. 设计红线（不变量）

| # | 不变量 | 依据 | 界面上必须长成的样子 | 破了会怎样 |
| --- | --- | --- | --- | --- |
| R1 | 判定只有一条路径 | AGENTS.md 30 | 界面上任何"结论"都来自 API 的 Decision 载荷，前端不重算 | 本地与经 API 的结论分叉，审计失去意义 |
| R2 | 证据只由服务端流水线产出 | AGENTS.md 32、20 | 界面**不能**上传/编辑 `EvidenceBundle`，只能触发验证器 | 客户端自证通过 |
| R3 | 租户只来自令牌 | AGENTS.md 32/33 | 租户切换器只是**显示**；越权即拒绝，不是隐藏按钮 | 跨租户读写规则 |
| R4 | 生效写入必须人工审批且绑 `action_hash` | AGENTS.md 38/39、`tool-registry.yaml:317-345` | 审批页展示 `action_hash`、diff、post_check、回滚能力；参数一变旧审批作废 | "点了通过"被当成通用许可 |
| R5 | 规则集加载是原子的 | C22/C23 | 门禁失败显示"**现网规则集未被替换**"，而不是"部分生效" | 半套规则生效，判定不可重放 |
| R6 | `skipped_rules` ≠ 通过 | 文档 §1、`README.md:50-58` | 跳过与通过用不同视觉与不同文案；跳过必须写明原因 | "没规则管它"被读成"它合规" |
| R7 | 关键验证器不可用 = critical 阻断 | C27/C28、AGENTS.md 20 | 工具缺失/超时/输出非法显示为**阻断**，不是警告 | PASS 抵消 critical |
| R8 | 超时 / 503 / 504 ≠ allow | AGENTS.md 33 | 网络与超时状态只能是"未知/失败"，永远不渲染成绿色 | 失败关闭被界面抹平 |
| R9 | 哈希漂移不许静默 | C6、AGENTS.md 12 | 漂移是显式行项 + 退出码 1，且拒绝"忽略"按钮 | 溯源链悄悄断裂 |
| R10 | 观测与审计只记摘要，且不可写时失败关闭 | AGENTS.md 34、16 | 审计页展示的是脱敏摘要链；写不进日志时操作失败 | 无审计的受治理动作 |
| R11 | 审计身份 = `rule_id@version` | C30 | 改语义必须递增 `version`，界面不允许"同名覆盖" | 快照与证据对不上 |
| R12 | 不引入 LLM 判定 | 文档 §1、`功能清单.md:253` | 界面不得出现"AI 生成规则/自动判定"入口（辅助检索可以，判定不行） | 不可确定性重放 |

## 5. 分期建议

> 下表已按 §9 的评审结论修订：新增 **P-1 期**（先修两个阻塞项），P0 收窄为"反向代理同源的只读骨架"。

| 期 | 范围 | 新增后端能力 | 契约影响 | 风险 |
| --- | --- | --- | --- | --- |
| **P-1 先修阻塞项**（强制，先于一切） | ① B1 新建规则文件的审批绕过（`nodes.py:93-97` + `tool-registry.yaml:293-315`）；② B2 HTTP 面漂移静默（`runtime.py:679`）；③ 控制台的不可信文本转义约束 | ①② 属修复而非新增；③ 前端一条约束 | ① 需补契约测试；② 需让 API 读真实漂移结果 | **高**：两者都是"对外承诺已被打破"的缺陷 |
| **P0 只读骨架**（今天就能做） | 反向代理同源承载静态页 + 直接调用现有六条路由：模型/语料状态只显示"**未核对**"，分块浏览借 `retrieve` 命中片段间接完成，健康看 `/v1/health/ready` | **零新增** | **零** | 低；代价是体验残缺（G1/G2/G5/G6 都没有 HTTP 面）。若必须单进程，则用同源静态挂载（不进 OpenAPI `paths`，**但要避开 `/` 挂载点**并补回归测试） |
| **P1 草稿与结构化编写** | 台阶 4/5 的受限表单（结构性字段不可编辑，AVP 模式）+ 草稿存储 + 实时门禁反馈 | 草稿 CRUD、校验预演（G3） | 新增路由与 DTO；草稿**不是**规则，不得进 `policies/` | 中：必须先定义"草稿 id/版本"与 C22 `version`、C30 `rule_id@version` 的对应关系 |
| **P2 审批与提交** | 提交走 `orc.policy.edit`（审批 + `action_hash` + 台账 + post_check）；`action_hash` **只能由 Phase 4/编排层产出** | 无新写路径；控制台只做"发起 + 展示"（G7） | 与 Phase 4/8 的审批语义对齐（不得自造） | 高：这是唯一能改动判定依据的动作；必须先修 B1，否则"新建"绕过审批 |
| **P3 溯源与漂移治理** | `rule_sources` 登记与查询（把当前的空列表补起来）、文档版本漂移对规则的影响面分析 | 溯源读写（G1/G2） | 与 `corpus.yaml` 的 `rule_sources` 语义一致 | 中：登记后解析不到 chunk 会让索引 run 失败（C10/C33），必须先预检 |

**P0 是零风险的起点**：它不加写路径、不新增判定逻辑、不碰契约，就能回答"前后端能不能连"这个问题。
**P-1 是它的前提**：不修 B1/B2，P0 的只读页会显示"无漂移"，P2 的提交会绕过审批。

## 6. 前后端连接：实测结论与契约要点

> 本节是 [后端契约与连接证据](文档转规则操作平台-后端契约与连接证据.md) 的摘要；原始命令、响应与限制条件见该文 §3、§8。
> 【实测】= 在 `PYTHONPATH=src`、Python 3.13.11 下真跑出来的；【读码】= 从源码读出的结论。

**连接结论：独立源前端今天连不上这个 API。**

| 探测 | 结果 |
| --- | --- |
| `OPTIONS /v1/policy/evaluate`（`Origin: http://127.0.0.1:5173` + 预检头） | **405** + `Access-Control-Allow-Origin` = **null**【实测】 |
| 带同源头的 `GET /v1/health/live` / `POST /v1/policy/evaluate` | 200，但响应**同样没有** ACAO 头【实测】 |
| `app.user_middleware` | **`[]`**（全仓库 `src/` 下 `CORSMiddleware` / `StaticFiles` 命中 **0 处**）【实测 + 读码】 |
| `/console`、`/assets/app.js`、`/index.html` | 全部 **404 `not_found`**（应用不托管任何静态文件）【实测】 |

也就是说：**今天只有一个可行形态——同源**。要么把静态资源挂进 API 进程，
要么加 CORS 中间件（同样是契约与安全面变更）。这条结论直接否决了"先随便开一个独立端口的前端"这条路。

其余五条前端必须知道的事实：

1. **认证与租户**：无令牌 / 错令牌 → **401 `unauthenticated`**；令牌授权多个租户却不声明 `tenant` →
   **403 `token_scope_mismatch`**；跨租户声明 → **401**。演示令牌 `local-dev-token` 正是多租户令牌，
   所以控制台**必须**带租户选择器（但租户的最终裁决权在令牌，不在请求体）。
2. **契约快照是硬门禁，但静态挂载不吃这一刀**：`contract.py` 用 `paths == served` **全等**比较，
   所以新增任何**走 `runtime.handle` 的 API 路由**都必须同步 `ENDPOINTS` + `ROUTES` +
   `api/openapi.json`（`openapi --write`），新 POST 补 `_ROUTE_STATUS_CODES`，新 DTO 进 `handshake_models()`；
   【实测】在内存里加一条 `/v1/policy/draft`，`snapshot_diff` 立即报 1 处漂移。
   **但静态挂载（`app.mount`）实测不进入 `openapi()["paths"]`**，因此同源托管控制台**不需要** `openapi --write`
   （契约测试按 `route.name` 过滤，`tests/contract/test_api_protocol.py:174-178`）。
   ——这条是 Lead 综合时采纳的子任务自我更正：早前一版把它写成"静态路由也要三件套"，是错的。
3. **幂等陷阱（会静默丢结果）**：带 `idempotency_key` 重放时，凡是**超过 8192 字节**的响应都会变成
   **HTTP 200 + `Idempotency-Replayed: true` + 正文 `{}`（2 字节）**——根因是
   `src/policy_api/idempotency.py:33` 的 `_MAX_RESPONSE_BYTES = 8192` 与随后的降级写空体。
   【实测】`retrieve` 实测 10282 字节 → 重放 2 字节；**`evaluate` 同样会越界**，且阈值是"规则数的函数"：
   `include_evidence` 下 6 条规则 2052 B、50 条 15854 B、300 条 91857 B。
   界面不能把"重放"渲染成"结果为空"：要么客户端自己缓存上一次正文，要么改用 `request_id` 查询。
4. **预算是硬边界**：`evaluate_ms = 2000` / `retrieve_ms = 2000` / `validate_ms = 10000`；
   `max_concurrency = 8`；`max_request_bytes = 65536`、`max_response_bytes = 262144`。
   超预算 → **503 `request_budget_exceeded`**（不是 504；`budget_ms` 越界是 400）。
5. **失败关闭是完整的**：未配索引 → 503 `knowledge_unavailable`；`validate` 关键验证器失败 →
   **200 + `blockers[]` + `block`**（不是 allow）。**没有任何一条路径会退化成 allow**。

补充的三条第二轮实测（都会直接影响界面设计与安全评审）：

- `/v1/openapi.json` **匿名可读**，且服务端那份与仓库快照内容**不同**（快照有 4 个 `x-*` 版本钉，服务端那份没有）。
- **限流发生在认证之后、DTO 校验之前**，格式错误的请求同样消耗令牌桶，且 429 **不带 `Retry-After`**——
  界面不能靠"重试即安全"。
- 观测 JSONL 实测 19 个字段、101 条记录里**没有令牌与绝对路径泄漏**（符合 AGENTS.md 34）；
  但**重放行的 `decision` 是 Python `repr` 字符串**，界面过滤前必须归一化。

**缺口清单（提案，尚未实现）**：后端子任务给出 G1–G8，并给出一个与直觉相反的实测结论——
**"必须新增异步作业模型"在当前规模下不成立**（全量索引重建 27 文档 / 535 片段 `duration_ms = 149`，
四个门禁 CLI 均 < 1s），故 G8 明确**建议暂不新增**，只记录触发条件。
建议优先级：G6 会话身份 → G4 规则集**预演**（shadow load，对应 C23 原子性）→ G1+G2 状态与溯源 →
G3 草稿校验 → G5 门禁聚合 → G7 提交链路。

**最重要的一条架构结论（G7）**：提交与审批的接入点**不开在 `policy_api` 里**——
AGENTS.md 第 39 条（API 没有 enforce 路由）、第 30 条（API 不是第二份业务逻辑）、
第 35 条（删掉 `src/orchestration/` 平台照常独立运行）三条同时指向"另起一个只读 BFF / 编排层入口"。
代价是多一个进程或一个只读文件视图，**收益是契约影响为 0**。

## 7. 前端用户操作逻辑要点

> 本节是 [前端交互逻辑](文档转规则操作平台-前端交互逻辑.md) 的摘要；状态机全表、12 行失败语义对照表、
> 六张文字线框见该文 §3–§7。

**（1）草稿生命周期状态机**：`D0 新建 → D1 校验失败 → D2 可加载 → D3 证据已覆盖 → D4 门禁预检通过 →
D5 待审批 → D6 已提交/已驳回 → D7 已生效`，每一步的进入条件都对应到具体条件编号（C13–C21、C25–C28、C23）。
"没有跳过门禁的路径"由三条结构性事实保证：①六条路由没有任何写路径，
且 `orc.policy.edit` 的 `approval: required` 是**数据**（`registry/tool-registry.yaml:317-345`），
pre-check 十项任一 FAILED 即 block；②状态前进只能由后端结论驱动（界面不自己算）；③C23 原子性 + 空集拒绝替换
（`services.py:88-94`）让"部分生效"在语义上都不可表达。

**（2）两个实测出来的界面陷阱**（这是本节最有价值的部分）：

- `evaluate` 缺 `language` 时返回 `allow` + `matched_rules = 0` + `skipped_rules = 6`——
  **"没规则管它"绝不能被渲染成"它合规"**；
- `include_evidence` 缺省时响应里**根本没有** `skipped_rules` 这个键——界面必须把"未请求"与"确认为空"分开显示。

**（3）失败关闭的界面语义（12 行对照表的核心）**：504 / 503 / 429 一律显示"**没有结论**"；
`evidence_unavailable` 在 API 上目前不可达（只由 Phase 6 / 编排层产出，不可假装能展示）；
原子加载失败 = **现网规则集未被替换**；哈希漂移 → `verify` 退出 1；
验证器缺失/超时/输出非法 → critical 阻断。**没有任何一种失败被画成绿色。**

**（4）反模式清单（10 条）**：AI 一键生成规则、忽略门禁/强制启用、就地改已发布规则不升 `version`、
把"建议/尽量"写成规则、跨租户查看或提交、客户端自带证据或决策、自由文本 YAML 编辑器、
"保存即生效"、把审批通过当通用许可、用摘要链冒充防篡改日志——每条都给出了"诱人之处 / 为什么禁止 / 正确去向"。

**（5）技术形态**：推荐 **A 同源静态 HTML + 原生 JS**（零构建、无新依赖，先例 `tools/dora_site.py`；
也是 §6 结论下**今天唯一零改动可用**的形态）；B 独立 SPA 必须先解决 CORS（并付 Node 工具链的
README/CI/`.gitignore` 同步成本，AGENTS.md 第 307 行附近的清单）；C 桌面壳/CLI 包装
**与红线冲突**（等于给控制台第二条写入路径），只允许做纯只读查看。

**（6）附带发现的既有不一致**（不是本提案引入的，但在做界面之前必须先收敛，否则界面会把它们放大）：

| 发现 | 位置 | 为什么要先修 |

**横向模式**：以上产品没有一个允许"在 UI 里写规则并直接上线"——**改规则**留在 Git/PR + CLI，
**看影响 / 审批 / 开关**才放进 UI〔I，基于上表一手事实〕。这条外部经验对本提案有直接约束：
控制台的第一性形态应是**规则集与证据的只读视图 + 影响面 + 审批面板**，
而不是一个自由文本 YAML 编辑器；起草能力如果做，也必须做成**结构性字段不可编辑**的受限表单（AVP 模式）。

对接口设计的四条可迁移结论：

1. **"试运行"必须是显式模式，不能是暗默认**（Gatekeeper 的 `dryrun` 默认关闭）。
   对应到本仓库：加载预演必须显式声明"**不替换现网规则集**"，
   而 `allow_with_warnings` 才是"报告但不改变行为"的那个档位。
2. **决策 → 规则集版本**这一层有先例：OPA 的决策日志逐条带 `bundles.<name>.revision`〔V〕。
   本仓库对应物是 `RuleSet.identity`（`rule_set_hash`）进 Phase 7 观测摘要、进 Phase 8 checkpoint 兼容性判定。
3. **规则 → 原文条款**这一层**没有先例**：在上述六家的一手文档中都没有"规则回指原始文件条款"的内建字段〔I〕。
   本仓库的 `corpus.yaml.rule_sources` 是自建的一等领域模型——而它**当前是空列表**
   （`规则文档转化为规则.md:285-288`）。这恰好说明：这一层不是抄来的，是这个平台真正的增量与真正的欠账。
4. **不要把"打包签名"当防篡改**：[in-toto Bundle 规范](https://raw.githubusercontent.com/in-toto/attestation/main/spec/v1/bundle.md)
   自述 "Bundle is not authenticated as a whole"（可被删条、重放、注入）〔V〕——与本仓库
   `功能清单.md:254`"审计链是摘要链、删尾或整链重写发现不了"的自述是同一个诚实的边界。

**治理控制台可引用的外部义务**（供控制台自身的安全设计取用）：

- [OWASP ASVS 5.0](https://raw.githubusercontent.com/praetorian-inc/ASVS/c2a083487cca52a2759c7969574e402ea766b64e/5.0/en/0x17-V8-Authorization.md)
  **V8.3.1**：授权必须在可信服务层执行，不得依赖客户端 JS 之类可被不可信消费方操纵的控制
  ——这条直接否决"前端判断能不能提交"的任何设计；
  **V8.4.1 / V8.4.2**：管理界面需要跨租户控制与多层访问控制（网络位置/可信端点不得作为唯一因素）；
  **V16.2.1 / V16.2.5**：日志含 when/where/who/what 元数据、凭据与敏感数据不得记录或须脱敏
  ——对应本仓库"观测只记摘要"（AGENTS.md 34）。
- 自动化决策的人类监督：EU AI Act **Article 14(1)** 要求人工可有效监督〔V，第三方整理站点，正式引用需以 EUR-Lex 为准〕。
  需要注意的分寸：本仓库**刻意不引入 LLM 判定**（`功能清单.md:253`），因此这条不因"判定"而自动适用；
  但一旦 P3 引入"AI 辅助起草"，"人类可监督的界面"就从可选变成义务。
- 可争议性（contestability）：NSPW'22 论文主张"规范由代码执行时，可争议性是问责的必要组成部分"〔V，
  [arXiv 2205.03925](https://ar5iv.labs.arxiv.org/html/2205.03925)〕——对应本仓库
  `matched_rules` / `skipped_rules` 的逐条解释：界面上必须能回答"为什么拦我 / 为什么没拦我"。
- 变更控制：NIST SP 800-53 的 `CM-3` 可作为锚点，但调研**未能取到 NIST 站点原文**（待核对），
  本提案不据此下结论；同理 SP 800-218（SSDF）与 SP 800-162 的条目**尚未核实**。

**调研局限（如实声明）**：Styra DAS 文档域名在本环境 DNS 不可达，未采信；
NIST CSRC / nvlpubs 对非浏览器请求返回 406 或依赖 JS，除 `CM-3` 片段外的控制陈述句未取到原文；
SLSA 现行版本为 v1.2（v1.1 已标 Retired），但它是**构建产物**的溯源等级，不是策略包签名规范。

### 9.3 其他必须收窄的结论（评审发现，两份文档都没写）

| 发现 | 影响 | 处置 |
| --- | --- | --- |
| 静态挂载到 `/` 会改变错误语义：未知 POST 由 404 变 **405**、真实路由错方法由 405 变 **404** | 统一错误信封对未知路径不再成立 | 挂载点避开 `/`（如 `/console/`），并写成回归测试 |

### 9.4 前端操作逻辑的三个缺口（评审 C2）

1. **草稿存储不存在** → 状态机 D0–D6 今天没有载体；"草稿 id/版本"与 C22 `version`、C30 `rule_id@version`
   的对应关系必须先定义，否则草稿与审计身份对不上。
2. **D5 的 `action_hash` 归属没写清**：它只能由 Phase 4 / 编排层的 `binding()` 产出；
   前端自算就等于"客户端自带决策"（违反 AGENTS.md 32）。
3. **D7 缺"生效失败"分支**：规则文件变了就整份替换，但装配失败时下一个请求是
   **503 `rule_set_unavailable`** —— "已生效 / 未生效 / 生效失败"三态必须分开，不能合并成一个绿点。

### 9.5 评审的反方最强论点（steelman）与回应

- **反方**：既有不一致都是文档/注释层面的口径问题，运行期行为自洽且失败关闭（租户四态、两种 `retryable`、
  空集拒绝替换、坏规则整批不加载全部实测成立）；`hash_drift` 常量与 DTO 死码不改变任何判定结果，
  把 P0 只读阶段按"先修不一致"卡住，是把低风险阶段拖成治理项目。
- **回应（评审给出，Lead 采纳）**：接受"不影响判定"这一半，**不接受"因此不阻塞"**——
  本提案的卖点正是"不撒谎、不绕过门禁"，而 B2 与 B1 各自打破一条对外承诺
  （显示"无漂移"；让规则变更"看起来审批过、实际没有审批"）。
  **这两条不修，P2 一上线就会生产假的治理证据。**

### 9.6 本环境无法验证的部分（评审如实列出，Lead 原样保留）

### 9.8 附带发现：仓库门禁自身的一个既有缺陷（Lead 实测，与本提案无关，但会挡住任何非 ASCII 文件名）

- **现象**：`python tools/ci_local.py` 在本会话报告 3 处失败（Secret scan gate / 测试 / Phase 8 acceptance evidence）。
  其中 Secret scan 命中的是本文档集里的**合成占位令牌**（已按仓库约定在同一行加 `secret-scan: allow` 标记豁免）；
  另外两处是**同一个根因**。
- **根因**：`tests/integration/test_validator_cli.py::test_changed_from_git_uses_the_working_tree` 失败，
  stderr 为 `变更集里的路径不合法：路径包含不支持的字符: '"docs/architecture/\345\212\237...md"'`。
  `git status` / `git diff` 默认 C-quote（`core.quotepath=true`）把非 ASCII 路径输出成 `"…\345\212\237…"`，
  而 `src/validators/pipeline.py:460` 把带引号与反斜杠转义的路径判为"不支持的字符"→ 退出码 2 →
  测试里 `if returncode == 2: assert "git" in stderr` 不成立。
- **决定性对照实验（Lead 亲自跑）**：把本会话的文档改动 `git stash push -u` 之后，同一个测试文件 **11 passed**；
  `git stash pop` 恢复改动后重新变红。即失败由"**工作区里存在非 ASCII 文件名**"触发，与文档内容无关。
  `tools/phase_evidence.py` 的红灯也是同一条：其 `tests/integration` 套件 `result=fail, failures=1`（其余三套 pass）。
- **影响面**：只要工作区或变更集里出现中文文件名——本仓库的约定正是中文文件名（提交 `4b9bcb8`）——
  这两条门禁就会一起变红。它不是本提案引入的，但**会让本提案的产出无法过 `ci_local`**。
- **建议修法（不在本提案范围，未实施）**：给 `--changed-from-git` 的 git 调用加 `-c core.quotepath=false`
  （或对 C-quoted 路径做反转义），并补一条"非 ASCII 路径"的回归测试。
  **Lead 未擅自改 `src/`**：本提案的 diff 只含文档，代码侧的修复应由独立提交与独立评审承担。

## 10. 三个问题的直接回答

1. **能否做成操作平台？** 能——但必须把它当成"**受控作者工作台**"，而且顺序是
   **P-1 先修两个阻塞项 → P0 只读骨架 → P1 起草 → P2 审批提交 → P3 溯源治理**。
   任何"文档自动变规则"的形态都与仓库已验证的设计冲突（台阶 4 人工、来源必须本地、不得 LLM 裁决）。
   评审的整体判定是"**必须先修既有不一致**"（§9.1），Lead 采纳。
2. **前后端连接能不能打通？** **今天可以，但只能同源。** 独立源前端实测不可用：`user_middleware == []`、
   预检 `OPTIONS` → 405 且无 `Access-Control-Allow-Origin`、`/console` 等路径全 404。
   P0 最小形态是**反向代理同源**（零改动、零契约）；若必须单进程则用同源静态挂载
   （实测 `app.mount` 不进入 OpenAPI `paths`，**不需要** `openapi --write`），但挂载点要避开 `/`。
3. **前端操作逻辑要注意什么？** 见 §4 的十二条红线与 §7 的状态机 + 失败语义 + 反模式清单：
   核心是**没有跳过门禁的路径**、`skipped_rules` 与 allow 必须视觉可分、超时/503/504 绝不渲染成通过、
   不可信文本一律转义；三个待补缺口是草稿载体、`action_hash` 归属、`D7` 的"生效失败"分支（§9.4）。
