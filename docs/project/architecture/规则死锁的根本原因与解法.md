# 规则之间的死锁、规则与正常开发相悖：根本原因与彻底解决

> 本文回答一个问题：**43 条规则同时施加在每一次单文件编辑上**，为什么会产生"两条都对的规则合起来无解"这类死锁，
> 以及要彻底解决它，该改哪里。
>
> 口径：本文只做研讨与方案，不改任何规则、验证器或配置。所有读数都由仓库自己的入口现场产出，
> 命令与结果写在 §1.3 与各节的引文里；证不了的写在 §7。**本文与代码冲突时以代码为准。**
>
> 实验产物在 `.tmp/ss3-deadlock/`（未入库）；唯一新增的仓库文件就是本文。

---

## 0. 结论摘要（先读这四句）

1. **形态上，这不是一类问题，是四类**：结论互斥（同一批里两条要求合起来无解）、前提依赖（一条规则的证据前提是另一条规则要求的动作）、
   证据缺失被当成违规（"没查成"与"查了有罪"在 `violations` 里同形）、粒度不匹配（判一次编辑 vs 做一批改动）。四类都有真实实例。
2. **该拦住它却拦住不的是正反例语料门禁**（`tests/integration/test_rule_corpus.py`）。它逐条验、且夹具上下文**必然跳过**两条测试规则
   （实测：`TESTING-001@1`/`TESTING-002@1` 永远在 `skipped_rules` 里）；它对"别条规则也在阻断"是显式容忍的。**没有人验组合，因为没有地方能表达组合。**
3. **根因是判定的时机/粒度与证据适用性模型错了，不是规则写错了**：5.58 的修复（commit `3e230fd`）**一个规则文件都没动**；
   同一个动作、同一份提议内容，只把"批次里还有谁"换一下，结论就从 `block` 变成 `allow`（§4.2 读数 R5）。
4. **彻底解决要两步**：先做**方案 C**（把"证据对本次变更不适用"升格为一等状态，让失败关闭只落在"该查却没查成"上），
   再做**方案 A**（把批次/意图变成显式输入）。**方案 B**（规则组合约束显式建模）不该当主方案——它建模的是规则的交互，
   而实测到的成因是**证据**的交互，且今天一次编辑里就有 253 对阻断级规则共现。

## 2. 形态分类（每一类都给出仓库里的实例或代码位置）

### 类 A：同一批判定里两条规则的结论互斥

**定义**：在一次 `evaluate` 里，两条都命中、都为阻断级的规则，对同一个输入给出无法同时满足的要求。

**先说一个实测事实**：今天 43 条规则**不存在**这种字面意义上的两两矛盾。原因是规则语言本身表达不了"要求"与"禁止"的对偶：
`src/policy/models.py:681-690` 只有六个规则体（`forbidden_dependency` / `missing_docstring` / `style_lint` / `type_check` /
`missing_tests` / `failing_tests`），全部是"禁止某事"或"要求某物存在"；`Rule`（`models.py:696-708`）的字段里
**没有任何一处引用另一条规则**；`engine.evaluate`（`engine.py:147-164`）是一个平铺的 `for rule in evaluated` 循环，
**没有任何一遍是"两条规则一起看"的**；决策表 `expected_decision`（`models.py:1138-1145`）只读聚合后的 severity。
所以"两条禁止"永远不矛盾，"禁止 × 要求存在"才是矛盾可能出现的地方，而这类矛盾只在**证据前提**上落地（见类 B）。

**真实实例（历史上真的发生过的那个）**：5.58 的形状。`TESTING-001`（`policies/testing/TESTING-001.yaml:7-9`）与
`TESTING-002`（`TESTING-002.yaml:7-9`）的 scope **逐字相同**（`language: python`、`operation: [create, edit]`），
因此对任何一次 `operation ∈ {create, edit}` 的判定都同时命中：

- 只改实现 → `TESTING-001` 阻断（R3 实测）；
- 只改测试 → 修前 `TESTING-002` 以 critical 阻断（5.58 登记的读数）；
- **唯一能通过的形态是"实现 + 测试同一笔改动"**。

这就是"互斥"的可观测形态：不是一次 `evaluate` 里两条规则互相否定，而是**这两条规则联合起来把可行动作集合压成了一个点**。
**它今天仍以另一种形态活着**：R1（改 `tests/test_order_service.py` → allow）与 R2（改 `tests/conftest.py` → block）是同一个意图
（"给 order_service 补一个带 fixture 的测试"）下的两步，平台对它们给出相反结论。这不是一次 `evaluate` 内的矛盾，是**意图内**的矛盾——
而意图在平台里没有表示（类 D）。

### 类 B：一条规则的前提是另一条规则要求的动作

**定义**：规则 X 的判定前提 P 只能通过"执行规则 Y 要求你执行的动作 α"来满足，而 α 本身又要先过 X。

**仓库实例（逐条可核）**：

- `TESTING-002`（`checker: failing_tests`）的前提是 `failing_tests ∈ served_checkers`（`engine.py:159`）。
- `failing_tests` 被服务的前提是 `tool.pytest` 真的跑起来（`pytest_runner.py:177-193` 的反面）。
- `tool.pytest` 跑起来的前提是 `selection.nodeids` 非空（`selection.py:253`、`pytest_runner.py:195`）。
- `nodeids` 非空的前提是变更集里有 `test_patterns` 命中的文件（`selection.py:182-184`）。
- 而 `TESTING-001` 要求的动作 α 正是"**新增/修改测试文件**"。

于是：**α 是 Y 要求你做的，而做 α 又必须先满足 X 的前提。** 5.58 修的是这条链的第 4 环（让"变更集里的测试文件"自己成为选择结果），
5.66 是同一环的残余（`conftest.py` 不在这份 `test_patterns` 里），
5.51 更早修的是这条链在**收集期**的那一段（`pytest_runner.py:236-256`：项目内目标不存在 → `pending_implementation`）。

**这一类是本仓库死锁的主体**：5.58 / 5.51 / 5.66 三个实例全部落在这一类的不同环上。
共同结构是：**"要求存在的物" 的判定，依赖于 "为它取证的过程"，而这个过程又以 "它已经存在" 为输入。**

### 类 C：证据链断了却被当成违规

**定义**：平台说不出"这次该不该查"，于是把"没查成"渲染成"违反规则"。

**仓库实例**：R2 的唯一 violation 是
`TESTING-002@1 [critical] value=failing_tests，message=「没有验证器为 checker failing_tests 提供证据，拒绝在没有证据的情况下判定通过」`
（`checkers.py:414-424`）。这句话陈述的是**平台自己的证据供给状态**，但它在载荷里的位置是 `violations`，`rule_id=TESTING-002`，
severity=`critical`。读账本的人读到的是"这次违反了 TESTING-002"，而事实是"这次没有一条证据与 TESTING-002 有关"。

**放大效应（R9）**：`style_lint` 被 39 条规则共用（R8），所以**一次验证器缺口 → 41 条 critical violation、41 个不同 `rule_id`**。
第 20 条"同一批里的其他 PASS 抵消不了它"是对的，但它没有配套的"这条规则这次到底相不相关"的计算，
于是失败关闭的**基数**等于规则集的规模（今天 43，来自镜像的 38 条只会让它继续长）。

**仓库里已经有的三个正确先例**（说明这不是"只能这样"）：

- §51 `PENDING_IMPLEMENTATION`：第三种状态，不进 `served_checkers`、不产生 Blocker，判定侧产出 warning 级**独立发现**
  （`policy/evidence.py:371-412`、`policy/checkers.py:192-222`、`policy/engine.py:154-161`）；
- §47 `language_coverage`：`not_covered_by_design` 是一条**显式判定**而不是错误（`validators/pipeline.py:208-254`）；
- `judgements`（`pipeline.py:176-205`）：`empty` / `unanalyzed` 两个"非判定"口径，理由写在注释里——
  "缺席与'判定过、未发现'长得一样"。

**这三个先例覆盖了"语言不适用""树还在构建"，但没有覆盖"这次变更里没有这个 checker 的适用对象"。** 这正是 5.66 所在的那一格。

### 类 D：判定粒度（单次编辑）与意图粒度（多步改动）不匹配

**定义**：规则的要求是"最终状态"性质（改完生产代码要有测试、测试要过），而判定输入是"一次原子编辑+它之后的那棵树"。

**仓库实例与代码位置**：

- `src/adapters/dsh/pre_evidence.py:672-679`：取证请求写死 `changed_files=(event.file,)`——**Hook 每次只见一个文件**；
- `src/adapters/dsh/pre_evidence.py:92-99`（`TREE_NOTE`）：明文写着"同一批次里其它尚未落地的写入**不在**树里（Hook 每次只见一个文件）"，
  并给出实测后果（先写测试时兄弟模块不存在 → isort 判成第三方 → I001 → STYLE-018 warning，即 §48 / P3）；
- `src/policy/models.py:129`：scope 只有六个维度 `language / layer / module / operation / project / agent`——
  **没有"批次"、没有"意图"、没有"变更集"这一维**；而 AGENTS 第 40 条把"适用范围能用 6 个维度表达"作为规则上线的门槛之一，
  也就是说**就算规则作者想写"只在这次变更完整时判我"，他也写不出来**；
- 5.46 登记的就是这一条：批次状态要跨进程持久化，属"单开一次显式设计"。

**决定性读数 R5**：`edit tests/conftest.py` 这个动作、这份提议内容、这棵影子树，**只换"批次里还有谁"**：
`("tests/conftest.py",)` → block；`("tests/conftest.py","src/shop/order_service.py")` → allow。
结论：**判定结果不是"这份内容"的函数，而是"这次调用怎么申报批次"的函数。** 类 D 因此不是"体验问题"，是**判定语义问题**。

### 四类的关系

类 B 是主类（三个实例）；类 C 是 B 的**呈现层**——B 让证据链断掉，C 把断掉的证据链渲染成违规；
类 D 是 B 的**生成条件**——因为判定按单次编辑做，所以"要求的动作"与"动作的证据"永远不在同一批判定里；
类 A 是 B+D 在账本上的**观感**（同一意图的两步得到相反结论）。四类共享同一个机制：
**平台只有"服务过 / 失败关闭"两态，没有"本次不适用"这一态，也没有"批次"这一维。**

## 3. 为什么现有的检查没拦住它

仓库本来有四道防线。逐道看它该不该拦、为什么没拦住。

| 防线 | 它到底在验什么（代码/数据位置） | 对这类死锁 | 为什么 |
| --- | --- | --- | --- |
| **规则上线四条门槛**（AGENTS 第 40 条） | `source.kind` 与 `source.path` 真实存在；`checker` 是实现过的 6 个之一且 `validation/validators.yaml` 有验证器声明；scope 能用 6 维表达；severity 在四值枚举。机器版本：`policy.loader`（加载期）+ `tests/contract/test_validator_protocol.py::test_every_shipped_rule_is_covered_by_a_validator` | **结构上不可能** | 四条门槛的量化范围是**单条规则**（∀rule：可加载）。它回答"这条规则自己成不成立"，从不回答"两条规则能不能同时被满足"。`TESTING-001`/`TESTING-002` 各自**完全**满足这四条。 |
| **正反例夹具 + `tests/integration/test_rule_corpus.py`** | 每 `standard` 规则一对 `tests/fixtures/rules/<ID>/{good,bad}.py`；走**真实验证器流水线**（真 ruff）+ 唯一判定入口 `policy.engine.evaluate` | **应该拦、但拦不住** | 两处结构性限制：① 夹具上下文固定为 `layer="fixture"`、**operation 不声明**（`test_rule_corpus.py:124-134`），而两条测试规则都要求 `operation ∈ {create, edit}`——实测 R7：`TESTING-001@1`/`TESTING-002@1` **恒在 `skipped_rules` 里**，这对规则在这个门禁里**从来没有被执行过一次**；② 断言是**逐条**的，且显式容忍别条规则的阻断（`test_rule_corpus.py:329-338` 的 `foreign_blocking`："夹具只约束它自己那一条"）。**没有人验组合，因为没有地方能表达组合**——夹具的键是 `(rule_id, good/bad)`，没有"这一批上下文 + 期望决策"的键。 |

## 4. 共同根因

### 4.1 判断：判定的时机/粒度与证据适用性模型错了，不是规则写错了

**依据一：修复动作的落点。** 5.58 的修复只动了验证器与选择逻辑（`3e230fd`，见上），规则文件零改动；
5.66 登记的方向同样只动 `validation/test-layout.yaml` + `TestLayout`/`select_tests`（04-open-work 5.66 的"下一步"列）。
如果根因是"规则写错了"，修复必然要改 `policies/**` 或删规则；事实是一次都没有。

**依据二：修完之后两条规则依然是对的、依然在拦该拦的。** R3 里 `TESTING-001` 仍然以 error 拦住"改了生产文件却没有测试"；
5.58 的验收读数里"把同一测试改成必然失败 → `TESTING-002@1/error` + 真 `failing_tests` 证据"。
**规则的内容没有问题，有问题的是它们被施加的时机与粒度。**

**依据三（最强）：同一个动作有两个相反结论，差别只在批次申报。** R5。这条读数把"结论"从"内容"和"规则"里剥离出来：
`verdict = f(批次声明)`。规则没变、树没变、提议没变，只把 `changed_files` 从 1 个换成 2 个。

**依据四：引擎里根本没有"规则之间"这个对象。** `engine.py:147-164` 是平铺循环；`engine.py:189` 的 `matched_rules` 只收集
`evaluated` 的 id；`expected_decision`（`models.py:1138-1145`）只读 severity 聚合；`Rule` 没有引用其他规则的字段
（`models.py:696-708`）。**"规则之间的死锁"这个说法是一个观察者层面的描述，引擎里不存在一个可以被修复的"规则间"层。**

**依据五（反证）**：如果根因在规则，那么"把规则写对"应当能修好它。5.58 的备选方案②恰好是"改规则 scope"（加 `layer`），
被证据否决了，理由写在 04-open-work 5.58："规则 scope 的 `layer` 按**部署侧层名**精确匹配，写死层名会让 TESTING-002 在别的部署里
静默失效（第 40 条），而且它把「没有证据」换成「规则不适用」——改坏测试也会放行，覆盖面净减少"。
**用规则层的手段去修，要么无效、要么把覆盖面改小。**

结论一句话：
> **根因是"把一份终态性质的规则集，按原子编辑逐条施加，并在拿不到证据时一律失败关闭"这个判定模型；
> 规则内容、规则准入门槛、逐条正反例都不是失效点，因为它们量化的是单条规则，而问题出在"规则 × 时机 × 证据适用性"这个三者之积上。**

### 4.2 "43 条规则同时施加在每一次单文件编辑上"的结构性后果

这不是修辞，是 R6 的读数：**一次 `edit` 命中 42 条（controller 层 43 条），其中 23–24 条阻断级，阻断级两两共现 253 对。**

1. **风险单调不减，收益不随之增长。** 每条阻断级规则都是"失败关闭"的一个独立触发点（`engine.py:159-161`），
   而 `violations` 里**任何一条** error/critical 都给出同一个 `block`（`models.py:1143-1144`）。
   规则集只能变多（覆盖报告：38 条来自镜像，267 篇停在 Guidance 意味着**还有增长空间**），
   于是"可被拦住的动作集合"只增不减，而"能被放行的动作集合"不因为新增证据能力而变大。
   **用一个不精确的比喻：每一次编辑都在为整本规则手册付费，而手册还在变厚。**
2. **单点故障被按规则数放大。** R8/R9：`style_lint` 的扇入是 39:1，一次证据缺口产出 **41 条 critical violation、41 个不同 rule_id**。
   第 20 条的意图（"关键验证器不可用必须阻断，别的 PASS 抵消不了"）是对的，但它**没有配套的适用性计算**，
   于是账本里的 `violations` 不再是对这次改动的陈述，而是对**平台自身健康状况**的陈述——
   而账本读者（包括模型自己，见 5.60）会按 `violations` 理解发生了什么。
3. **"相关"这个词在判定里没有位置。** 42 条命中 = scope 交集非空。scope 只有六个维度（`models.py:129`），
   它们描述的是**文件/操作的类型**，不是**这次改动的意图**。因此"这条规则与这次改动相不相关"这个问题，
   平台**无法**回答——它能回答的只有"这条规则的 scope 命不命中这个上下文"。
   类 D 的 R5 就是这个空洞的直接后果。
4. **失败关闭的两态设计把"不适用"逼成了"违规"。** `EvidenceBundle`（`policy/evidence.py:415-530`）里 checker 只有
   `serves` / `blocker_for` / `pending_for` 三个入口；`engine.py:154-161` 的三分支正是"证据到手 / 待实现 / 其余一律失败关闭"。
   第三分支的语义是"**没能证明它适用**"，但输出是**违规**。§51（pending）与 §47（language_coverage）各自开了口子，
   但都只覆盖了一种"不适用"（树在构建中 / 语言按设计不取证），**没有覆盖"这次变更里没有它的适用对象"**。
5. **批次不可表达，于是"多步意图"必然被拆成"多次单步判定"，而每一次判定都在用终态规则打分。**
   `pre_evidence.py:672-679` 的 `changed_files=(event.file,)` 与 `TREE_NOTE`（:92-99）是同一个事实的两面。
   第 48 条（P3）已经承认了这件事，但它的处理是"把'这是哪棵树'写清楚"，**没有改变"树只有一棵、批次不存在"这件事**。

## 5. 彻底解决：三个互斥方案与取舍

三个方案**互斥**，指它们各自把不同的东西当成"要改的那个东西"。可以叠加，但**必须选一个作为主方案**，
否则会出现"两个半成品互相掩盖"（第 45 条的同一条纪律：仪器必须能失败）。

### 方案 A：把判定粒度换成批次/意图

**改什么。** 让"批次"成为一等输入，而不是 Hook 的隐含状态：

- `pre_evidence` 的取证树 = 当前磁盘树 + **同一批次里所有已提议的文件**（把 5.46 的"批次语义"落地）；
- `changed_files` 从 `(event.file,)` 变成"本批次的变更集"；
- 批次身份进 `PolicyContext`（新增维度）或进 `PipelineRequest` + 审计摘要，且**必须在载荷里**，
  否则违反核心约束 5（相同输入相同结论）——"输入"必须包含批次。

**代价。**

- 需要**跨进程、跨调用的批次状态**（dsh 的 Hook 是每次调用一个新进程），落点、失效、清理都要设计（5.46 已登记"单开一次显式设计"）；
- 取证成本按批次元素线性增长：b-plan 的预算是 `pre_evidence.timeout_ms = 20000`（`dsh-adapter.yaml:55`），
  当前实测"每次编辑约 2 秒"；批次一变大，预算不等式（§42）会先被击穿；
- 批次状态让"重放同一份载荷"不再必然得到同一结论——**必须把批次摘要写进载荷**，否则第 19 条的可重放承诺失效。

**它自己会漏什么。**

- 它**不修**类 C：一个只含测试文件的批次，`select_tests` 仍然返回 `level="none"`（除非同时改 `test_patterns` 或 applicability 模型），
  5.66 照旧；
- 它**不修**扇入放大（R9）；
- 它引入新的失败形态："批次永远不结束"（agent 中途放弃）会让判定一直停在不完整状态；反过来，长批次会**推迟**取证，
  让"动手前"变成"动手后"；
- 它把结论绑定到会话历史，跨会话的同一动作仍会得到不同结论（义务账 §56 已经踩过一次"带不带 session_id"的坑）。

**怎么证明它有效（可落地）。**

1. 场景驱动：在 `.tmp` 里用真实 Hook 跑一个 3 步批次（改实现 → 加测试 → 改 `conftest.py`），断言
   ① 每一步的 `decision` 与"把这三步合并成一次判定"的 `decision` **相等**；② 每条审计记录里都能读到批次摘要；
   ③ 第 3 步不再出现 `TESTING-002 critical / uncovered_checker`。
2. **变异证明（第 45 条）**：在 `git archive HEAD` 的副本上把 `changed_files` 改回 `(event.file,)` → 上面的用例必须变红；
   撤回 → 变绿。做不到就写明"这条检查覆盖不到"。
3. 预算回归：记录批次规模 1/3/10 时的取证墙钟，断言不等式仍成立（否则是**接线自检**应当报红的配置）。

### 方案 B：把规则之间的组合约束显式建模

**改什么。** 新增一份组合层（例如 `validation/rule-interactions.yaml`）声明"规则 X 与规则 Y 在上下文 C 下不可能同时满足"，
引擎在判定后加一遍组合检查，命中就产出 `infeasible_jointly` 而不是两条 block；加载期拒绝"含有未声明不可行对"的规则集。

**代价。**

- 需要有人**写出**这些对。R6 说今天一次编辑里就有 **253 对阻断级规则共现**；要把它们逐一判定为"可行/不可行"，
  等于要求维护者对 43 条规则的组合做人工审查——而这个数字随规则数平方增长；
- 判定"两条规则能不能被同一串动作同时满足"一般不可判定（需要动作语义模型，而平台只有 checker）；
- 它会制造**第二份真相**：规则说"要 X"，组合表说"X 与 Y 不可兼得"。两者漂移时无人发现，
  正是第 50 条"同名两义"在治理层的形态。

**它自己会漏什么。**

- 只覆盖**已声明**的对。下一个死锁会是未声明的三重组（5.58 就是三条规则——两条测试规则 + `select_tests` 的行为——的联合后果）；
- 它**完全不碰**类 C 与类 D：证据缺口照样是 41 条 critical，批次照样不存在；
- 它把"平台的自我矛盾"变成"维护者的待办清单"，而 5.58 证明维护者的清单不是失效点——**规则门禁根本不在修复路径上**。

**怎么证明它有效。**

1. 先用只读仪器把"共现对"变成数据：本文的 `.tmp/ss3-deadlock/scope_matrix.py` 已经是雏形（253 对）。
   没有这份数据，组合表只能是拍脑袋；
2. 造一对**合成**的不可行规则（临时规则目录，不入库）：声明前引擎给出两条 block；声明后给出 `infeasible_jointly`；
   且加载期对"未声明的不可行对"报错；
3. 变异证明同上：把组合检查短路 → 用例变红。

### 方案 C：把"证据对本次变更不适用"升格为一等状态（**推荐做第一步**）

**改什么。** 沿着 §51 与 §47 的既有先例，把 `served` / `失败关闭` 两态扩成四态：

| 状态 | 含义 | 判定后果 |
| --- | --- | --- |
| `served` | 真的查了 | 参与判定 |
| `pending_implementation` | 跑成了、树还在构建（§51） | warning 级独立发现，不阻断 |
| `not_applicable_to_this_change`（**新增**） | **有正面证明**说明本次变更里没有这个 checker 的适用对象 | warning 级独立发现，**不阻断**，且写进审计 |
| 其余（缺失/超时/崩溃/配置错误/无覆盖） | 该查没查成 | 维持第 20 条，critical 阻断 |

关键在"**有正面证明**"：`not_applicable` 不能由"没选到东西"推出，必须由**数据声明的谓词**推出，
否则它会变成一条新的静默放行通道（第 45 条"可能漏、不误报"的反面）。它同时是 5.66 需要的那个**语义决策**的最小平替：
`conftest.py` 该不该算"测试变更"、它该触发哪些测试——这正是 5.66 登记里说"必须先定下来"的那件事。

**代价。**

- 它是**放宽**：每一条错判的 `not_applicable` 都是一次静默放行。因此谓词必须是数据（可评审）、必须带理由（§47 的 `reason` 非空先例）、
  必须进审计、必须有反例夹具；
- 动协议：`EVIDENCE_SCHEMA_VERSION` 1.2→1.3、`PIPELINE_SCHEMA_VERSION` 1.3→1.4（第 55 条），
  `validation/test-layout.yaml` 的 `version`/`schema_id` 1→2（新增第二份路径声明）；
  写死版本号的断言与 tech-detail 生成物要在**同一个提交**里改完；
- `uncovered_checker_violation` 的调用点要重新审：把"没覆盖"与"不适用"分开之后，
  必须证明**没有一条真的缺口**被误判成不适用。

**它自己会漏什么。**

- 它**不修**类 D：批次仍然不存在，"我还没写完所以测试跑不了"与"这个模块永远没有测试"在谓词层面容易混淆
  （前者应是 `pending`，后者才是 `not_applicable`），谓词写不好就会把真问题洗掉；
- 它**不修**扇入放大：一次 ruff 缺口仍然产出 39 条 critical（只是这些 critical 会变得"对得上"一些，
  但账本仍然以 39 条违规的形式呈现一次工具故障）；
- 它**不修**类 A：意图内两步结论相反的问题，只有在批次可见之后才可能被表达。

**怎么证明它有效。**

1. **组合语料（无论最终选哪个方案，这一条都该单独做）**：新建
   `tests/fixtures/rules/_combinations/<name>/manifest.yaml`，键 = `{target, operation, changed[], layer, language, expected_decision, expected_served_checkers}`，
   由一个新的集成用例走**真实流水线 + 真实引擎**。第一批条目就放两个已登记实例：
   `edit tests/conftest.py`（5.66）与 5.58 的"只改测试文件"；
2. **门禁自证（第 45 条）**：在 `git archive HEAD` 副本上把 `test-layout.yaml` 的 `test_patterns` 改回不含新增声明 → 组合语料必须变红；
   撤回 → 变绿。**"跑了、是绿的"不算覆盖**；
3. **反例不许放宽**：5.58 修完后钉住的五个反例（第三方包缺失 / 语法错误 / `conftest` 出错 / 断言失败 / 零用例收集，
   `tests/integration/test_dsh_pre_evidence_hook.py:930-952`）必须逐条保持红；
4. **谓词的漏报面**：为 `not_applicable` 谓词写一份"可能漏、不误报"的缺口标注（§48 `tree_gaps` 的同型），

## 6. 推荐

**推荐：先做 C，再做 A；B 不做主方案（只在 A/C 落地后作为可选补充）。**

理由，按权重排序：

1. **C 打在根因的"语义空洞"上。** 类 B 是主类，而类 B 的每一个实例（5.51 / 5.58 / 5.66）都表现为
   "平台把'这次该不该查'当成了'这次查没查成'"。§51 与 §47 已经证明这条修法在本仓库是可行且被接受的先例，
   C 只是把它们从"两种特例"推广成"一条通道"。
2. **C 是 5.66 的前置条件。** 5.66 的登记明确写着"「改了 conftest 该跑哪些测试」本身是一次**语义决策**，
   必须先定下来"，而"不许用在 tests/ 下就算测试的启发式"（第 49 条）。C 的 `not_applicable` 谓词就是那个被要求"先定下来"的东西；
   先把谓词定下来，`test_support_patterns` 才有地方挂。
3. **A 修的是另一个根因（类 D），但它需要 C 先提供"未完成"的表达。** 没有 C，批次落地后的第一个新问题就是
   "批次进行到一半，测试还跑不了"——那会重新落回失败关闭（也就是把 5.51 的问题从单文件放大到批次）。
   **先 C 后 A，A 落在能说"还不适用"的地基上。**
4. **B 被证据否决当主方案。** 它建模的对象（规则之间的关系）与实测到的成因（证据之间的关系）不是同一个东西；
   它的规模是规则数的平方（今天 253 对）；而且它需要维护者人工判定"两条规则能否被同一串动作满足"，
   而 5.58 证明**规则准入管线根本不在修复路径上**（`3e230fd` 一个 `policies/` 文件都没动）。
5. **无论选哪个，"组合语料"都该单独做**，因为它是唯一能回答"谁来验组合"的机制，成本低、且直接照住已登记的两个实例。

**推荐落地的顺序（三步）：**

1. **组合语料 + 门禁自证**（最小、独立、立刻能红）：把 5.66 与 5.58 写成两条组合用例；先让它**红**（证明它能失败），再修；
2. **方案 C**：`not_applicable` 谓词数据化 + 协议升版 + 反例夹具不动；
3. **方案 A**：批次语义的单开设计（5.46 已登记），以 C 的四态为基础。

- 未运行真实 dsh 进程 + 插件的端到端链路。R4 走的是 `build_pre_evidence` + `policy.engine.evaluate` 的**进程内直调**

  **不含** stdin 载荷解析、退出码与审计落盘。Hook 层的 exit 2 / `uncovered_checker` 读数引用的是
  04-open-work 5.58/5.66 里登记的 Lead 实测（`.tmp/558-tests-only/probe4.py`）。

**没验证的具体断言**

- **"5.58 的修复在别的形状下是否仍成立"**：未验证"变更集里是被删除/改名的测试文件"、
  "变更集里同时有测试文件与不存在的路径"这两种形态。
- **方案 A 的预算影响未测**：把批次全部复制进影子树并跑 ruff+pytest 的墙钟时间没有读数；
  b-plan 的 `pre_evidence.timeout_ms=20000` 是否够用**不知道**（当前单文件实测约 2 秒是配置注释里的历史读数，本轮未复测）。
- **`not_applicable` 谓词的漏报面未设计**：对 `missing_tests` 来说，
  "这个模块是新增的、测试还没写"与"这个模块按设计不需要测试"在证据上今天无法区分——
  这正是 5.51 用 `pending_implementation` 覆盖的那一格，谓词必须与它**互斥且可判定**，本轮没有给出谓词。
- **"规则语言表达不了矛盾"这句话的范围**：它成立于**今天的 6 个 checker + 今天的 43 条规则**。
  加载器不会阻止未来新增一对语义上互斥的规则体（例如某天有人加一个"必须有 docstring"与"禁止 docstring"的规则体组合）——
  这是个**已验证的现状描述**，不是**已验证的不变量**。
- **R6/R7/R8/R9 的口径**：R6、R8 用 `layer=service/module` 的合成上下文（`--layer service`）；
  R9 用 `--validators` 白名单人为制造证据缺口——**它是"如果发生"的形态演示，不是"某次真实运行里发生过"**。
  R7 是读 `matching_rules` 的状态，不是跑夹具用例本身。
- **R11 的口径**：用了 `--layer unknown`。`TESTING-001/002` 的 scope 不含 `layer`，因此层名不影响结论；
  但在 b-plan 的实际配置里该文件会命中 `**/*.py → module`（`examples/dsh/b-plan/dsh-adapter.yaml:25-26`），
  这一点没有单独复跑。
- **类 A 的"严格两两互斥"**：我给出的是**结构性不存在**（规则语言 + 引擎循环 + 决策表的读取范围），
  并**没有**形式化证明 43 条规则的任意子集都可行；R6 的 253 对共现是"可同时命中"，
  不是"可同时满足"——**这两件事的差集没有被算过**，也没有工具算得出来（这正是方案 B 的代价所在）。

**判断不了的**

- **5.66 的语义决策该往哪边落**（`conftest.py` 算测试变更 → 触发同目录测试？还是算支撑文件 → 触发全量？）
  是一个**产品判断**，不是技术判断；本文只给出它能挂在哪里（方案 C 的谓词 + `test-layout.yaml` 的第二份声明），
  没有替它做决定。
- **该不该动第 20 条**。第 20 条本身没有错（"没有验证器为某 checker 提供证据 → critical"是必要的失败关闭）；
  本文的 C 方案主张的是**在它前面加一步适用性计算**，不是删掉它。这个"加一步"是否触及第 20 条的语义边界，
  需要一次显式裁定（参照 §51 的 D-1(b) 先例，写成 04-open-work 的裁定条目）。
