# 规则文档 → 规则：转化覆盖报告

> 本文是 `docs/project/architecture/` 的说明之一，配套 [规则文档转化为规则.md](规则文档转化为规则.md)：那边讲**方法与台阶**，
> 这边记录**一次真实走查的结果**——把 `docs/mirrors/<mirror>/**` 下的离线规范文档逐篇过一遍，判定它能不能成为
> `policies/<domain>/<ID>.yaml` 里的可执行规则；能转的转，转不了的写明为什么。
>
> 判定与数据的口径以代码为准：`src/policy/models.py`（规则 schema）、`src/policy/checkers.py`（6 个 checker）、
> `validation/validators.yaml`（谁产生证据）、`validation/ruff.toml`（诊断码归属）、`knowledge/corpus.yaml`（语料与溯源）、
> `policies/**`（规则本身）。本文与代码冲突时以代码为准。
>
> 复核命令见 §8；本文里的每个数字都可以用那些命令重算。

## 1. 结论

本次走查覆盖六个镜像集合的 284 篇文档。

其中 17 篇被提炼成 38 条可执行规则；其余 267 篇停在 Curated Guidance，逐篇写明了原因。

| 镜像集合 | 篇数 | 产出规则的篇数 | 规则条数 | 停在 Guidance |
| --- | --- | --- | --- | --- |
| `python-pep-code-style` | 14 | 2 | 19 | 12 |
| `owasp-cheatsheets` | 142 | 15 | 19 | 127 |
| `google-eng-practices` | 16 | 0 | 0 | 16 |
| `gitlab-code-review` | 22 | 0 | 0 | 22 |
| `dora-capabilities` | 39 | 0 | 0 | 39 |
| `dotnet-design-guidelines` | 51 | 0 | 0 | 51 |
| **合计** | **284** | **17** | **38** | **267** |

规则集共 43 条。其中 38 条由镜像文档提炼（`source.kind: standard`），5 条是项目自订（`project-policy`）。

三条过程类文档集合（Google / GitLab / DORA）**不是"没读"**。它们确实含有可判定的工程要求，但那些要求在本仓库已被既有规则承载。

具体说：`TESTING-001` 管"改了生产代码必须带测试"，`TESTING-002` 管"相关测试必须通过"。
再写一遍只会得到三条语义重复、严重级别各异的规则。这正是仓库口径里要避免的"看起来在管这件事、实际什么都没查"。
逐篇的判定与原文见 §4。

## 2. 判据：什么才算"转过来了"

一条规则要真的生效，必须同时满足四件事。方法详见 [规则文档转化为规则.md](规则文档转化为规则.md) §1。

1. **来源是本地的**：`source.kind ∈ {project-policy, standard}`，`source.path` 指向仓库里真实存在的文件；
2. **可确定性判定**：`enforcement.checker` 必须是**已实现**的 6 个之一，且有验证器为它声明产证据；
3. **范围可枚举**：只用 `language / layer / module / operation / project / agent` 六个维度表达得出来；
4. **结论落在决策表里**：`severity` 是四值枚举。

另有两约束由代码或环境强制，走查前已实测确认。

| 约束 | 证据 | 后果 |
| --- | --- | --- |
| 每条已发布规则的 `scope.language` 必须是 `python` | `tests/contract/test_validator_protocol.py::test_every_shipped_rule_is_covered_by_a_validator` | 非 Python 的规范**结构性**不能上线（.NET 全本 51 篇即由此淘汰） |
| 本机与 CI 都**没有 mypy** | `python -m validators.cli probe` → `tool.mypy: unavailable` | `type_check` 类规则一律不能启用：工具缺失 = 规则失败关闭，会让所有 Python 文件一次性判红 |

6 个 checker 里这次真正用到的只有 2 个：`style_lint` 与 `missing_docstring`。
前者走 Ruff 0.14.13 的诊断码，后者是内置的 `py.docstring`（标准库 `ast`）。
其余四个各自有明确原因：`forbidden_dependency` 判依赖图，`missing_tests` 与 `failing_tests` 判变更集与测试进程，`type_check` 缺工具。

### 2.1 Ruff 码的归属纪律

规则只声明"要查什么码"，工具**只有被 `select` 的码才会出现在诊断里**。所以：

- **规则声明了没被 select 的码** → 那条规则永远拿不到证据（本次走查真的抓到一次：`S308`）；
- **select 了没有规则归属的码** → 诊断只进 `unmapped_findings` 计数，却不参与判定。

两个方向都由一条契约测试守住，见 `tests/contract/test_validator_protocol.py`：

```text
test_ruff_codes_are_declared_and_selected_in_both_directions
```

`validation/ruff.toml` 顶部的归属表是它的可读版本。`F811`/`F841` 是 Phase 5 遗留（当时选了码但从未有规则归属），在测试里显式登记为豁免，不是给新增留的口子。

## 3. 转化出来的 38 条规则

38 条规则的分布如下。

| 前缀 | 条数 | checker | 来源 |
| --- | --- | --- | --- |
| `DOC-002..DOC-004` | 3 | `style_lint`（D205 / D200 / D401） | `pep-257-docstrings/index.md` |
| `STYLE-003..STYLE-012`、`STYLE-014..STYLE-018` | 15 | `style_lint`（E401/E402/E711/E712/E713/E714/E721/E722/E731/E741、F403/F405、N801/N802/N803/N806/N815/N816、I001） | `pep-8-python-code/index.md` |
| `SEC-001..SEC-012` | 12 | `style_lint`（S102/S307、S301/S302、S303/S324、S105/S106/S107、S323/S501、S506、S602/S605/S607/S609、S608、S313..S318、S310、S311、S308/S611/S701） | 15 篇 OWASP Cheat Sheet |
| `SEC-014/015/017/018/019/021/022` | 7 | `style_lint`（S113、S110/S112、LOG015、TRY400、S104、S312/S321、S612） | 同上 |
| `DOC-001`（既有） | 1 | `missing_docstring` | `pep-257-docstrings/index.md` |

每条规则都配了一对正反例夹具。

- `tests/fixtures/rules/<RULE-ID>/bad.py`：必须命中本规则；
- `tests/fixtures/rules/<RULE-ID>/good.py`：必须不命中本规则。

这条不是靠自律，而是 `tests/integration/test_rule_corpus.py` 的门禁。
它遍历 `policies/` 自发现规则，对每条 `source.kind == standard` 的规则断言两个夹具都存在。
随后走真实验证器流水线（真子进程 Ruff），判定三件事：反例必须命中、正例必须通过、两条都不能被 `skipped_rules` 吞掉。

38 条溯源都登记在 `knowledge/corpus.yaml` 的 `rule_sources` 里。
每条写的是 `dataset + source_path + heading_path`，索引器把它解析成 `chunk_id` 写进 `rule_sources` 表。
于是可以双向查：

```powershell
$env:PYTHONPATH = "src"
python -m retrieval.cli rules --rule SEC-008   # 规则 -> 它来自哪一段原文
python -m retrieval.cli rules --chunk <chunk_id>  # 反向：这段原文被哪条规则引用
```

## 6. 回写：三个真实修正

走查不是单向的。它把三处代码或数据的问题翻了出来，都按失败关闭的原则修掉。

1. **`source.path` 指不了中文目录**（真缺陷，已修）。`src/policy/models.py` 的 `_REPO_PATH_RE` 原本只允许 ASCII。
   OWASP 镜像的分类目录却是中文（`02_输入验证、注入与文件处理`）。
   于是任何指向镜像原文的规则都会以"路径包含不支持的字符"加载失败。这不是"能不能写中文"的偏好问题：不改它，`source.path` 就只能写不存在的假路径，
   整个"文档 → 规则"的溯源前提塌掉。`src/retrieval/models.py` 早就为同一原因放宽过一次并留下了注释分歧。
   现在两边都允许非 ASCII，结构拒绝与路径元字符的限制保持不变。
   回归用例 `test_repo_path_accepts_non_ascii_segments` 钉住这两个方向。
2. **`S308` 没被 select**。规则声明了它，工具却不会报——那条规则永远拿不到证据。已补进 `validation/ruff.toml`，
   并把这条不变量写成了契约测试（§2.1）。
3. **`select` 与规则归属不一致会静默失效**。同一件事的另一半：新加的契约测试双向检查，
   历史遗留的 `F811`/`F841` 显式登记为豁免而不是假装不存在。

## 7. 现有 6 个 checker 覆盖不到、值得补的五条

按"补上之后能立刻把哪些镜像原文变成规则"排序。**这些是下一步的输入，不是本次的欠账。**

1. **`commit_message`（读 Git 元数据）**。要求来自 `merge_request_workflow/index.md`：提交主题与正文之间要有空行，主题不超过 72 字符。
   `cl-descriptions.md` 另外要求首行是简短摘要、用祈使语气。
   这是整批镜像里最可机器判定的一组要求，而且与 `AGENTS.md` 已有的提交信息约定同向。目前只有人读的约定，没有可执行的规则。
2. **变更体量闸门**：`small-cls.md` 的 100 / 1000 行阈值、`merge_request_workflow` 的 "not contain more than 10 commit messages"。
   需要能读 diff 统计量的 checker。
3. **文档同步**：`looking-for.md` "If a CL changes how users build, test, interact with, or release code, check to see that it also updates associated documentation"。
   `missing_docstring` 只判 Python 对象，判不到"文档文件有没有随代码改"。
4. **`missing_docstring.changed_only`**：给规则体补一个布尔开关（与 `missing_tests.changed_only` 对齐），
   §5 里那条 GitLab 的方法级 docstring 要求就能立刻上线而不误伤存量代码。
5. **凭据与权限类 checker**。`ai/ai-accessible-internal-data.md` 要求：不得用超级用户模式或共享服务账号把 AI 工具接到内部数据上。
   `development/permissions/review_guidelines/index.md` 要求：权限条件只能减权，不能扩权。
   两条都是硬约束。但 Ruff 的 `S1xx/S5xx` 只覆盖"调用了哪个标准库函数"，覆盖不到"用哪个账号连数据"或"策略是否只减不增"。

| **severity 标定不完全一致**：同为 "always" 的原文，STYLE-004 取 warning、STYLE-009 取 error；原文是 "should" 的 SEC-003 取 error；原文无禁止措辞的 DOC-005 已删除 | severity 是**项目政策**，不是文档给出的事实。复查给出的是"按字面措辞应取哪一档"的建议；是否采纳要连同"阻断面有多大"一起决定。全部差异已列在复查报告里，留给下一次专门标定 |
| **`scope` 无法表达"只在授权路径上生效"**：`RuleScope` 的六个维度里没有 path，所以 SEC-015/SEC-009/SEC-011 这类规则会作用在测试与工具脚本上（复核实测 13 个真实文件里 9 个 block，多数是误报） | 加 path 维度是**平台级改动**（要动 `KNOWN_SCOPE_DIMENSIONS`、`PolicyContext`、scope 访问器与契约测试）。按仓库口径，这类"缺一个维度"应当先设计再实现，而不是把规则硬塞进现有维度 |
| `SEC-006` 会把 `class _StrictLoader(yaml.SafeLoader)` 判成 unsafe loader（工具只比对字面量 Loader）；`SEC-021` 会把加密的 `FTP_TLS` 判成明文协议 | 工具行为，规则改不了。两条的"覆盖边界"已写明，豁免走 `validation/ruff.toml` 的 `per-file-ignores`（本仓库既有的显式豁免口径） |
| `scope.language` 不是受控枚举（`language: cobol` 能通过模型校验） | 由契约测试兜住（每条已发布规则必须是 `python`），属既有设计取向、非本轮引入 |

## 10. 二次分析：转化率、特征与价值复核（2026-09）

§1–§9 记录的是"哪篇文档变成了哪条规则"。本节回答另外三个问题：**转化率到底是多少**、**转化与未转化的内容各有什么特征**、
**哪些没转化的值得转化、哪些已转化的不值得当规则**。方法：四路只读子会话（量化 / 已转化方特征 / 未转化方特征与理由校验 / 价值判断）
＋ Lead 的两组运行时实测。所有数字都能按 §8 的命令重算；本节引用的外部证据在 §10.5 列出来源。

### 10.1 转化率：四个口径

| 口径 | 分子 / 分母 | 转化率 |
| --- | --- | --- |
| 文档级 | 17 篇产出规则 / 284 篇镜像文档 | **5.99%** |
| 字节级 | 369,686 B / 4,067,028 B | **9.09%** |
| 行级 | 4,679 行 / 52,972 行 | **8.83%** |
| 需求级（严格） | 38 条规则 / 141 条"强情态＋代码锚点"句 | **26.95%** |

按镜像拆开，转化并不是均匀的：

| 镜像集合 | 篇数 | 产出规则的篇数 | 文档率 | 字节率 | 行率 |
| --- | --- | --- | --- | --- | --- |
| `python-pep-code-style` | 14 | 2 | 14.29% | 22.78% | 27.01% |

四个零产出集合占 **45.07% 的文档、25.22% 的字节**——文档率与字节率的差（5.99% vs 9.09%）说明被转化的文档平均更长、更集中。

**需求级漏斗**（口径：按 `.`/`!`/`?` 断句后匹配情态词集合 `must|must not|should|never|always|do not|required`，同句内含反引号片段即计"带锚点"；Lead 另用一套更窄的正则独立复核过数量级）：

```text
284 篇镜像文档
  → 17 篇（5.99%）
  → 5,473 条规范语句（must / should / never / always / do not / required …）
  → 684 条同时含反引号代码锚点（12.50%）
  → 141 条强情态（must / must not / never / always）且带锚点
  → 38 条上线规则
```

- 5,473 → 38 是 **144 : 1**；但收敛到强情态＋锚点的 141 → 38 只有 **3.71 : 1**。**分母选择本身就在讲故事**：
  拿全部规范语句当分母，"转化率不足 1%"；拿可判定的强情态句当分母，四分之三已经上线的部分并不低。
- **"有代码锚点"≠"可判定"**：684 条带锚点句里只有 85 条（12.4%）的锚点是 Python 记号，
  其余 87.6% 是 HTTP 头、cookie 属性、C#/Java/JS 符号。这条实测是本次最重要的口径警告：
  任何"按锚点密度找漏转化"的榜单都只能用来看方向，不能当判决。

**已转化与未转化的分布差异**（按篇中位数）：带锚点句密度 14.13 vs **0.00**（每千行），规范语句 34 vs 11，行数 214 vs 104。
密度比体量更能区分两组；但两组在第 90 百分位几乎重合（41.77 vs 34.13），即**高密度的未转化文档确实存在**——这正是 §10.3 的入口。

### 10.2 特征：转得过来的长什么样，转不过来的卡在哪

**已转化的 38 条（17 篇来源）**——五条特征，括号里是命中条数：

1. **判定不出单文件**：单文件语法 32 ＋ 单文件语义 6，跨文件 / 跨提交 / 需人类判断 **0 条**。这是唯一 100% 成立的不变式；
2. **谓词在原文里可命名**：语法构造 17、点名 API 13、命名形态 5，原文没点名 3（`SEC-018/021/022`）→ 锚定率 92.1%；
3. **引文可核**：101 条引文主张里 81 条在 `source.path` 逐字命中，15 条在**已在注释里写明的**另一篇镜像命中，5 条两处皆无（3 条是 Ruff 自身文本并注明来源，2 条是提取伪影）；
4. **落在已有工具码上**：37 条走 `style_lint`（Ruff），1 条走内置 `py.docstring`——6 个 checker 只用到 2 个；
5. **联合判别式**：谓词锚定 ∩ 单文件 ∩ 引文可核 = **34/38（89.5%）**。

**情态不是门槛**：禁止 14 / 义务 13 / 建议 11。有 11 条来自 should / consider 措辞，其中 3 条取 `error`——
这说明"能不能转化"与"该不该阻断"是两件事（见 §10.4）。

**同篇内对照**（最强实验，控制了文档、来源与语言）：PEP 8 镜像 8 个节产出 15 条规则，进 67 行正文、不进 163 行（**29.1%**）；
PEP 257 进 26 行、不进 16 行（61.9%）。同一句话也能只取一半：PEP 257:33 的
"Public methods … should also have docstrings" 被 `DOC-001` 的 `targets` 砍掉方法一级——
与 §5 拒绝 GitLab 方法级 docstring **同因**（`missing_docstring` 缺 `changed_only`）。
**转化粒度实际上是工具码的粒度，不是文档条款的粒度。**

**未转化的 267 篇**——理由代号分布（多代号行 70 行，占 26.2%，故合计大于 267）：

| 代号 | 含义 | 处数 | 占比 |
| --- | --- | --- | --- |
| a | 流程 / 组织 / 文化 / 自述 | 103 | 38.6% |
| c | 缺工具或 checker | 96 | 36.0% |
| b | 非 Python 语言 | 78 | 29.2% |
| d | 6 个 scope 维度表达不了 | 52 | 19.5% |
| f | 已由既有规则承载 | 6 | 2.2% |
| e | 只是建议 / 考虑 | 2 | 0.7% |

主卡点按集合各不相同：`.NET` 51 篇里 41 篇卡 b（80.4%）；OWASP 127 篇里 85 篇卡 c（66.9%）；Google 13/16、DORA 26/39 卡 a。
**分层抽样 59 篇逐篇打开原文校验**（覆盖 a–f 每类，e/f 是全表覆盖）：理由成立 48（81.4%）、部分成立 10（16.9%）、不成立 1（1.7%）。
唯一的"不成立"是 OWASP `00_索引与标准/` 的 7 篇索引页被标成 c（缺工具），而正文写的是"不含可直接判定的条款"——应记 a。

**不可判定的结构性原因**可以归成七类（T1–T7）：证据在运行/部署态（CSP 头、会话熵、容器 profile）；
跨时间跨人的经验数据（"一个工作日内响应"、文档感知度问卷）；判定标准本身就是裁量
（`small-cls.md:32` 原文自述 "no hard and fast rules … it's up to the judgment of your reviewer"）；
主语是评审者的动作（`looking-for.md:42` "check to see that…"）；主语是别的技术栈；依赖外部随时间变化的数据（CVE 库）；
格言（`pep-20:29` "Errors should never pass silently."）。抽样里 T1/T2/T3/T4/T6 占 67.8% 且不含任何可判定条款——
**这不是"没做好"，是这类文本的信息压根不在代码制品里。**

**判别式**（可操作性小结）：一条条款能转化 ⟺ ① 有已实现的 checker 且验证器为它声明产证据；
② 能落到**已被 `select` 的**诊断码（稳定但未 select → 先决定归属；preview → 停）；
③ 谓词在原文里可命名；④ 判定不出单文件；⑤ 引文能在 `source.path`（或注释里写明的另一篇）逐字命中。
情态只影响 severity 的建议值，不影响可转化性。

### 10.5 判据、来源与本次回写

把 §2 的四条上线条件换成"四道门"的说法更容易看出**卡在哪一道、以及哪种卡是结构性的**：

| 门 | 判据 | 本次卡住的规模 | 性质 |
| --- | --- | --- | --- |
| 语言门 | 主体是不是本平台治理的语言（Python） | 128 篇零产出集合的主体 | **结构性**，改工具也过不去 |
| 可判定门 | 谓词是不是机器可观测制品上的性质 | 抽样里 67.8% 属 T1–T7 | **结构性**（Rice 定理：非平凡语义性质不可判定，只能逼近） |
| 工具门 | 有没有验证器为这个 checker 产出证据 | 96 处代号 c | **工程缺口**，可补（也是 §10.3 的全部内容） |
| 规范力门 | 严重级能不能落在决策表上 | 11 条"建议"措辞上线、3 条取 error | **政策选择**，需要显式标定 |

这个划分有两处理论支撑，也解释了为什么"应该多转化一点"这个直觉在这里不成立：
NIST SP 800-53A 把评估方法分成 examine / interview / test 三种，**只有"对可机读制品的 examine/test"能自动化**，
"interview"（组织实践、人员能力）在定义上就不是代码检查的对象——DORA 的 39 篇、Google 的评审流程篇正落在这一侧；
RFC 2119 又给了情态分级（MUST = 绝对要求，SHOULD = 可以有正当理由忽略），
**把 SHOULD 变成阻断规则，是把"默认"当成了"绝对"**。所以真正的目标不是提高文档级转化率，
而是在"可判定 ∩ 有证据源"这个交集里**把精确率做上去**——静态分析文献给的正是这条经验：
Johnson 等（ICSE 2013）的现场研究把误报与"不可行动"列为采纳的主要障碍，
