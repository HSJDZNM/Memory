## §2 编号对照表

三套编号**正交**：台阶是链路步骤，Phase 是交付批次，①②③ 是三道通过条件。

| 台阶 | 名称 | 门禁 | 主要 Phase | 对应文件 / 目录 |
| --- | --- | --- | --- | --- |
| 台阶 1 | 镜像与哈希登记 | 不挂门禁（产物被 ① 校验） | 无 Phase（镜像流水线） | `docs/mirrors/<mirror>/**` + `manifest.json`、`tools/mirror_docs.py` |
| 台阶 2 | 语料登记 | ①（校验台阶 1 的产物） | Phase 3 消费 | `knowledge/corpus.yaml`、`src/retrieval/corpus.py` |
| 台阶 3 | 分块与索引 | ②（执行时依赖台阶 7 的登记） | Phase 3 | `src/retrieval/chunker.py`、`indexer.py`、`store.py` |
| 台阶 4 | 提炼（唯一人工步骤） | 无 | 无 Phase | 人工；`src/policy/models.py` 的 `SourceRef` |
| 台阶 5 | 规则文件 | ③（loader 加载门禁） | Phase 0 / 1 | `policies/<domain>/<ID>.yaml`、`src/policy/loader.py` |
| 台阶 6 | 验证器覆盖 | 无（注册表加载即报错） | Phase 5 | `validation/validators.yaml`、`src/validators/` |
| 台阶 7 | 生效、溯源与变更管理 | 无 | Phase 1 + 传播 3 / 7 / 8 | `RuleSet.identity`、`retrieval.cli rules` |
| 判定与消费（**不是台阶 8**） | 台阶 7 里内嵌的一步：规则生效后的判定与消费方 | 无 | Phase 1 / 4 / 7 / 8 | `policy.engine.evaluate`、`src/enforcement/`、`src/policy_api/`、`src/orchestration/` |

三点必须写清，否则"台阶 ↔ 门禁"会被读成并列关系：

1. **门禁 ① 挂在台阶 2**：校验的是台阶 1 的产物（条目在不在 manifest 里、许可文件在不在、sha256 一致），
   所以 ① 落在台阶 2，台阶 1 自己不挂门禁（`src/retrieval/corpus.py`）。
2. **门禁 ② 由台阶 3 执行、依赖台阶 7 的登记**：登记了 `rule_sources` 才强制。当前已登记 38 条规则 → 原文 chunk 的溯源
   （2026-09 起不再是空表），解析不到 chunk 会让索引 run 失败。
3. **门禁 ③ 只覆盖台阶 5**：台阶 6、7 与「判定与消费」都不挂门禁——台阶 6 的失败发生在验证器注册表加载时，
   判定侧的失败关闭另算；台阶 1、4 不挂门禁的原因写在 §2 表内。两组门禁概念见下（不许混算）：
**"两道加载门禁"与"三道通过条件"是两组概念**（见 [规则文档转化为规则.md](规则文档转化为规则.md) §1）：

| 说法 | 指什么 | 编号关系 |
| --- | --- | --- |
| 门禁 ①②③ | 转化链路上的三道**通过条件** | 落点见上表：① 台阶 2、② 台阶 3、③ 台阶 5 |
| 两道**加载**门禁 | **加载阶段**就报错的语义类别：规则加载器、验证器注册表 | 规则加载器**就是 ③**；验证器注册表门禁（`RegistryError`）落在判定侧失败关闭，**没有 ①②③ 的编号** |
| 合计口径 | 引用时写"**3 道编号门禁 + 1 道无编号的注册表加载门禁**" | 不要数成"4 道门禁"，也不要漏掉第 4 处硬失败点；两套计数不许混 |

Phase 侧（`功能清单.md` §1.1 的主题列，落点目录可实测）：

## §3 判定链路术语

| 术语 | 一句话定义 | 锚点 |
| --- | --- | --- |
| 判定（Decision） | 六层里唯一会给出结论的产物 | `src/policy/models.py:255` |
| 严重级别 → 判定 | 无违规 `allow`；`info` / `warning` `allow_with_warnings`；`error` / `critical` `block` | `src/policy/models.py:172`、`:972` |
| 证据（EvidenceBundle） | 验证器产出的确定性事实，只产证据、不判定 | `src/policy/evidence.py`、`src/policy/checkers.py:42` |
| 授权（action_hash） | 覆盖工具 schema、规范化参数、主体、权限与上下文摘要的短时效凭据 | `src/enforcement/action.py` |
| 台账（ledger） | 记录"这个 `action_id` 已执行过"的追加写 JSONL，拦重复执行；`pre_state` 里另存**请求视图**（存留口径见下方第四条） | `src/enforcement/ledger.py` |
| 摘要链（audit chain） | `sequence` + `prev_digest` 的追加写链；能发现中间改动，**删尾与整链重写发现不了** | `src/enforcement/audit.py` |
| 跳过（skipped_rules） | 规则没参与判定，必须写明维度原因；**跳过不是通过** | `src/policy/checkers.py:33`、`src/policy/engine.py` |
| 失败关闭 | 缺证据、工具不可用、版本未知一律取更严结论，绝不默认放行 | 逐层检查，如 `checkers.py` 的 `uncovered_checker_violation` |
| 能力上限 | Adapter 的 `manifest` 只声明上限；写类动作仍需证据 + allow + pre-check | `adapters/<agent_id>/manifest.yaml`、`AGENTS.md` 第 29 条 |
| 证据不足与不一致 | 事后验证缺证据记 `repair_required` / `inconsistent`，回滚能力缺失写 `unsupported` | `src/enforcement/postcheck.py` |

四条容易混的口径：

- **`skipped_rules` ≠ 通过**：Phase 2 的 Hook 只给上下文，证据类 checker 的规则进 `skipped_rules`；
  Phase 6 的写类动作没有 evidence provider 时直接 `evidence_unavailable` 阻断。
- **「跑不了」 ≠ pass**：`tools/dsh_sandbox_loop.py` 环境不具备时按环境跳过（退出码 0 + reason + 复现命令）。
- **判定结果与 CLI 措辞分开**：状态名只写三个枚举；`policy.check` 输出的 `PASS` 字样是措辞，不是口径名。
- **台账（ledger）落的是「扣留疑似密钥，其余按原文」**：`pre_state` 的请求视图里，
  注册表声明 `secret: true` 的参数、以及取值里出现确定形态凭据的参数，只留类型 / 长度 / 摘要
  （此时 `values_withheld: true`）；**其余参数按原文落盘**（`params[].value` 可以是整份 `content`），
  `request.workspace` 落的是**绝对路径**。口径由本轮冻结（07 号报告 §4 **P6**，改自述不改行为，
  见 `src/enforcement/ledger.py` 与 `src/enforcement/action.py::redacted_request_payload` 的自述）：
  PostToolUse 要拿这份载荷重建 `ActionRequest`（`src/adapters/dsh/enforcement.py::_restore_request`），
  而 `action_hash` 覆盖 `workspace` 与规范化参数（`src/enforcement/models.py::_ACTION_HASH_FIELDS`）——
  扣掉取值或把 workspace 换成占位，重建恒不对等，事后核对就只能永远判「证据不足」，
  等于把 G2（事前事后成对 + `post_validated`）打掉。**边界**：这不是 AGENTS 第 16 条的违反——
  第 16 条管的是 `audit.jsonl` 摘要链的脱敏（08 轮对 baseline 导出件的独立复算：**164 条记录、
  0 处绝对路径、0 处凭据**；07 号报告 §4 P6 记的是 160 条，是同一份追加写文件更早一次读数，
  两次都是 0 命中），台账是**另一份产物**；要改这条口径，得先解决「事后核对靠什么重建请求」。

## §4 退出码与终态

三个层次不要混：判定结果是业务结论，退出码是 CLI 结论，编排终态是工作流结论。
锚点是 `src/policy/check.py:71`–`73` 与 `src/orchestration/errors.py:127`。

| 退出码 | 含义 | 锚点 |
| --- | --- | --- |
| `0` | `allow`；或命令成功 | `src/policy/check.py:71` |
| `1` | `block` / `allow_with_warnings`（含需人工审批的 block）；或漂移 / 无结果 | `src/policy/check.py:72`、`exit_code_for` |
| `2` | 配置或执行错误：规则损坏、上下文不完整、未知 checker、请求非法、审计链损坏 | `src/policy/check.py:73` |

注意：`allow_with_warnings` 与 `block` 都退 `1`，脚本不能靠退出码区分二者，要用 `--json` 读载荷。

**`tools/ci_local.py` 只有 `0` / `1`**：它把子步骤的非零码收敛成自己的 `1`（`tools/ci_local.py:253`–`:285`），
不是 `0 / 1 / 2` 口径的所有者。引用这三值时锚 `src/policy/check.py:71`–`73`，不要锚 `ci_local.py`。

| 终态（RunStatus） | 什么时候出现 | 例子（`FailureCode`） |
| --- | --- | --- |
| `blocked` | 平台侧说不清，禁止继续 | `POLICY_UNAVAILABLE`、`EVIDENCE_UNAVAILABLE`、`TRACE_FORGED` |
| `needs_human` | 上限击穿或审批要人来决定 | `APPROVAL_MISSING`、`LIMIT_REPAIR_ROUNDS`、`SIDE_EFFECT_UNKNOWN` |
| `failed` | 编排自身损坏 | `STATE_VERSION_UNKNOWN`、`CHECKPOINT_CORRUPT`、`ENGINE_UNAVAILABLE` |

未登记的失败码一律按 `failed` 处理（`src/orchestration/errors.py:161` 的 `status_for`），不猜、不放行。

**实测退出码样例**（canon 2026-09-21 16:40，命令 + 结果）：

| 命令 | 退出码 | 为什么是这个码 |
| --- | --- | --- |
| `python -m policy.check --check-rules` | `0` | 43 条规则全部加载成功 |
| `python -m retrieval.cli rules --rule SEC-008` | `0` | 已登记的溯源：`SEC-008@1 <- 02_输入验证、注入与文件处理/SQL_Injection_Prevention_Cheat_Sheet.md#…` |

| `python -m retrieval.cli vector \"code review\"` | `1` | `status: unavailable (index_missing)` —— 检索不可用是显式状态 |

**退出 0 ≠ allow**：`python -m adapters.cli inspect` 实测退出 `0` 但 `outcome_code=context_error`（失败关闭发生在载荷里）。
读退出码只能判断"命令有没有跑到最后"，结论要看决策载荷的 `decision` 或 `outcome_code`。
