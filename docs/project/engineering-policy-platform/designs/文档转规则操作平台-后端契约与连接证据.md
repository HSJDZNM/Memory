## 1. 结论摘要

1. **独立源前端连不上**：应用没有注册任何 CORS 中间件（`src/policy_api/app.py:172-182` 全文无
   `add_middleware`），实测预检 `OPTIONS` 返回 **405 且无 `Access-Control-Allow-Origin`**，
   简单 GET 与实际 POST 的响应同样没有该头。浏览器会拒绝这类跨源请求的响应。
2. **应用不托管任何静态文件**：`/`、`/index.html`、`/console`、`/assets/app.js` 实测全部
   **404 `not_found`**；`app.routes` 只有 6 条业务/运维路由 + `/v1/openapi.json`。
3. **六个路由全是"判定/查询"语义，没有一个"写"**：`ROUTES`（`src/policy_api/runtime.py:73`）不含
   任何规则、语料、草稿、任务概念；这符合 AGENTS.md 第 39 条"API 没有 enforce 路由"，但也意味着
   操作平台的**写入侧必须走编排层，控制台不能自己写文件**。
4. **认证语义有两处会直接决定 UI 结构**：【实测】无令牌 / 错令牌 → **401 `unauthenticated`**；
   令牌被授权多个租户却不声明 `tenant` → **403 `token_scope_mismatch`**；跨租户声明 → **401**（不是 403）。
   演示令牌 `local-dev-token` 正是两租户令牌，控制台**必须**带租户选择器。
5. **幂等有一个会把结果悄悄丢掉的陷阱**：【实测】`retrieve` 响应 10282 字节，带 `idempotency_key` 重放时
   服务端返回 **HTTP 200 + `Idempotency-Replayed: true` + 正文 `{}`**（2 字节）。
   根因是 `src/policy_api/idempotency.py:33` 的 `_MAX_RESPONSE_BYTES = 8192` 与 `:250-259` 的降级写空体。
6. **失败关闭语义完整且可用**：`retrieve` 未配索引 → 503 `knowledge_unavailable`；
   `budget_ms` 超路由默认 → 503 `request_budget_exceeded`；`validate` 关键验证器失败 →
   200 + `blockers[]` + `block`（**不是 allow**）。超时/忙碌是 504/503，**没有一条路径会退化成 allow**。
7. **契约快照工具链是硬门禁且很灵敏**：【实测】`python -m policy_api.cli openapi --check` 退出 0；
   在内存里给文档加一条 `/v1/policy/draft` 路径，`snapshot_diff` 立刻报 1 处漂移。
   且 `src/policy_api/contract.py:144-151` 用 `paths == served` **全等**比较，新增任何路由都必须同步改
   `ENDPOINTS`、`ROUTES`、`api/openapi.json` 三处。
8. **"必须新增异步任务模型"在当前规模下得不到实测支持**：全量索引重建（27 文档 / 535 片段）
   run 报告 `duration_ms = 149`，四个 CLI 门禁均在 1 秒内完成。真正的约束不是"慢"，
   而是**"没有写入/重建的路由"**与 `max_concurrency = 8`、`validate_ms = 10000` 这两个硬边界。

### 2.2 `evaluate` —— 只算决定

- **请求**：信封 + `principal`（subject/roles）+ `context`（`file`/`layer` 必填）+ `include_evidence`
  （`src/policy_api/models.py:230-235`）。
- **响应**（`src/policy_api/runtime.py:552-573`）：`api_version`、`tenant`、`decision`（核心决策载荷原样透出）、
  `summary{decision,violations,matched,skipped,required_action}`、

  `include_evidence=true` 时追加 `skipped_rules`。
- **【实测】** 200，`summary.decision = "allow"`，`rule_set.rules = 6`，
  `identity = [ARCH-001@1, DOC-001@1, STYLE-001@1, STYLE-002@1, TESTING-001@1, TESTING-002@1]`，
  正文 1375 字节，响应头 `X-Elapsed-Ms: 15`。
- **台阶定位**：台阶 7 的"判定"出口；不触碰台阶 1–6。
- **控制台可用**：做"改这条规则之前，现在的行为是什么"的基线对照。
- **不足以支撑编写与生效**：它只反映**当前已加载**的规则集；没有"如果加上这条草稿会怎样"的口子。

### 2.3 `retrieve` —— 检索 + 组装 Engineering Context

  `decision_ref`（只能指向本服务算过的 `request_id`，`src/policy_api/runtime.py:701-732`）。
- **响应**（`src/policy_api/runtime.py:662-686`）：`status` / `reason` / `detail` / `query` / `plan` /

- **【实测】**（租户启用检索后）200，`status = "ok"`，`method = "fts5"`，3 条命中；

  `text` / `text_hash` / `char_count` / `truncated` / `oversized` / `citation` / `citation_source`；

  也不提供按文档、按 heading 浏览的分页接口。

### 2.4 `validate` —— 产出验证器证据（可选顺带判定）

- **请求**：信封 + `principal` + `context` + `target`（缺省取 `context.file`）+ `changed[]` + `only[]` +

- **响应**（`src/policy_api/runtime.py:784-806`）：`report`（含 `evidence[]`）、`blockers[]`、

- **【实测】**（租户 `fixture-shop`，目标文件不存在）200，

### 2.7 为什么六个路由不足以支撑"文档 → 规则"的编写与生效

按七个台阶逐条对照（台阶定义见 `docs/project/architecture/规则文档转化为规则.md:71-189`）：

| 台阶 | 控制台需要问的问题 | 现有 API 能否回答 | 依据 |
| --- | --- | --- | --- |
| 1 镜像 + 哈希登记 | 这篇文档在镜像里吗？sha256 与 manifest 一致吗？ | **不能**。没有任何路由暴露 `manifest.json` / sha256 / 漂移 | 路由表 `src/policy_api/app.py:43-51` |
| 2 语料登记 | 它属于哪个 `dataset`？许可/tier/visibility 是什么？ | **不能**（只能通过检索命中间接看到单条片段的这些字段） | `src/policy_api/runtime.py:940-950` |
| 3 分块与索引 | 它被切成哪些块？索引是哪一代？ | **部分能**：`retrieve` 返回 `index` 摘要与命中片段；但要先有一次检索 | `src/policy_api/runtime.py:674-683` |
| 4 提炼（唯一人工步骤） | 我挑出的要求该配哪个 checker？ | **不能**。没有 checker / 验证器 registry 的只读接口 | `src/policy_api/runtime.py:73` |
| 5 规则文件 | 我写的 YAML 合法吗？会和现有规则撞 id 吗？ | **不能**。没有规则文件读写，也没有单文件校验路由 | 同上 |
| 6 验证器覆盖 | 这条规则的 checker 有人产证据吗？它会怎么判？ | **部分能**：`validate` 能用现网规则集跑证据；不能对"候选规则"预演 | `src/policy_api/runtime.py:736-806` |
| 7 生效 / 溯源 / 变更 | 新规则集能原子加载吗？这条规则从哪来？ | **不能**。没有 shadow load；`retrieve` 无 `rule_sources` 查询 | `src/policy_api/runtime.py:583-699` |

**现有 API 的能力边界可以一句话概括**：它把**已经生效的规则集**服务化得很好
（判定、检索、证据、观测、健康），但完全没有覆盖"规则集**将要**变成什么样"这条路径。

### 3.1 认证

| 场景 | 请求 | 实测结果 |
| --- | --- | --- |
| 无 `Authorization` | POST /v1/policy/evaluate | **401** `{"code":"unauthenticated","detail":"缺少 Authorization 头","retryable":false}` |
| 错误令牌 | `Bearer not-a-real-token-xxxxxxxx`（合成占位值，非任何真实凭据；secret-scan: allow） | **401** `unauthenticated` / "令牌未通过认证" |
| 错误方案 | `Token abc` | **401** `unauthenticated` / "Authorization 头必须是 'Bearer <token>'" |
| 令牌被授权多租户但未声明 `tenant` | `local-dev-token` | **403** `token_scope_mismatch` / "该凭据被授权多个租户，必须显式声明 tenant（不得由服务端替你选一个）" |
| 跨租户声明 | `dsh-agent-token` + `tenant: local-dev` | **401** `unauthenticated`（**不是 403**，刻意避免租户名成为探针） |

读码对应：`src/policy_api/auth.py:60-68`（Bearer 解析）、`:91-107`（常量时间比对 sha256）、
`:164-178`（多租户必须显式声明）、`:167-170`（越权租户对外是 401）；
状态码推导见 `src/policy_api/errors.py:73-107`。

> **控制台含义**：401 与 403 的语义是"这个令牌不能用"与"这个令牌能用但你选错了范围"，
> 而**跨租户也被折叠进 401**。所以 UI 不能靠 401/403 区分"令牌过期"与"租户越权"，
> 只能靠受控错误码 `code`。

#### 3.1.1 租户 / 项目错误的唯一口径（实测补齐）

上表只覆盖了 401 与 403；**"租户看起来不对"一共有四种不同结果**，实测如下
（`.tmp/console-probe/probe6.py`：在探测配置里新增一个 `enabled: false` 的 `retired-shop` 租户，
并把它加进 `local-dev` 令牌的 `tenants`）：

| 情况 | HTTP | 错误码 | 实测 detail |
| --- | --- | --- | --- |
| 租户已声明且 `enabled: true` | 200 | — | 正常判定（`allow`） |
| 租户在令牌的 `tenants` 里，但部署配置里 `enabled: false` | **404** | `tenant_not_found` | "请求的租户边界不可用"，`retryable: false` |
| 租户 `enabled: true` 但**装配失败**（如 `project_root` 不存在） | **404** | `tenant_not_found` | `retryable: true`，detail = 装配失败原因："tenant 'broken-shop' 的 project_root 不存在: does-not-exist-dir" |
| 租户**不在**令牌的 `tenants` 里 | **401** | `unauthenticated` | "令牌未通过认证" |
| 令牌被授权多个租户却没声明 `tenant` | **403** | `token_scope_mismatch` | "该凭据被授权多个租户，必须显式声明 tenant" |
| `context.project` 不在令牌的项目范围内 | **403** | `project_not_allowed` | "该凭据没有被授权这个项目边界" |

**【读码】** 判定顺序解释了这张表（`src/policy_api/auth.py:164-186`）：
先比对令牌 → `tenant ∈ client.tenants` 否则 401（`:167-170`）→ 多租户未声明则 403（`:172-178`）
→ 再查配置里是否存在且启用，否则 404（`:180-182`）→ 最后查项目边界（`:184-186`）。

**与仓库注释的出入（读码；代码是唯一事实来源）**：

- `src/policy_api/errors.py:7-9` 写"跨租户/不存在永远是 404"——实测**越权租户是 401**，
  只有"被禁用 / 未装配"才是 404；
- `api/README.md:99` 写"租户不存在、越权租户对外同样是 401"——实测**被禁用租户是 404**，
  只有"不在令牌范围"才是 401。

两句话各对一半。**不存在一个统一的 401 或 404 口径，只存在一个"判定顺序"的口径。**

**两个 404 生产者、两种 `retryable`**（实测，`.tmp/console-probe/probe10.py`）：

| 生产者 | 触发条件 | detail | `retryable` |
| --- | --- | --- | --- |
| `src/policy_api/auth.py:180-182` | 租户被禁用 | "请求的租户边界不可用" | `false` |
| `src/policy_api/services.py:290-295` | 租户装配失败（进入 `TenantStore._errors`） | 装配失败原因（只含名字、不含绝对路径） | `true` |

**同一个错误码、两种重试语义**——界面若只看 `code` 会踩到：装配失败被标成可重试，而重试永远不会成功
（它是部署数据问题）。**UI 必须以 `retryable` 字段为准，不能按码猜。**

**【实测】装配失败还会把 readiness 打成 degraded**：加入 §broken-shop§ 之后 `/v1/health/ready` → **503**，
`state = "degraded"`，`detail = "部分租户不可服务：broken-shop"`，`assembly_errors` 带着同一条原因
（`src/policy_api/ops.py:141-154`）；健康的 `local-dev` 仍 200。

**附带实测**：被禁用租户**不进入** readiness（`src/policy_api/services.py:219-220` 跳过
`enabled: false` 的租户），因此加了 `retired-shop` 之后 `/v1/health/ready` 仍是 `ready`——
**"readiness 全绿"推不出"你手上的租户名可用"**。

> **控制台含义**：UI 必须为这四种情况给出不同文案，且不能只按状态码分类：
> 404 在这里表示"这个租户边界不可用"，**不是**"路由写错了"。

### 3.2 CORS（本评估最关键的连接结论）

| 探测 | 结果 |
| --- | --- |
| `OPTIONS /v1/policy/evaluate`，`Origin: http://127.0.0.1:5173`，`Access-Control-Request-Method: POST`，`Access-Control-Request-Headers: authorization,content-type` | **405**，正文 `method_not_allowed`；`Access-Control-Allow-Origin` = **null**，`Allow-Methods` = null，`Allow-Headers` = null |
| `GET /v1/health/live`，带同一个 `Origin` | **200**，`Access-Control-Allow-Origin` = **null** |
| `POST /v1/policy/evaluate`，带同一个 `Origin`（令牌与租户都正确） | **200**（服务端确实处理了），`Access-Control-Allow-Origin` = **null** |
| `app.user_middleware` | **`[]`**（空列表，没有任何中间件） |

**【读码】** 根因：`create_app`（`src/policy_api/app.py:172-182`）构造 `FastAPI(...)` 时没有调用
`add_middleware`；`docs_url` / `redoc_url` 被显式设为 `None`，但没有配置 CORS，也没有挂载静态文件。
全仓库 `src/` 下 `CORSMiddleware` / `add_middleware` / `StaticFiles` 的检索结果为 **0 处命中**。

**【规范推断】** 按 Fetch 规范：带 `Authorization` 头的请求属于"非简单请求"，浏览器必须先发预检；
预检响应缺少 `Access-Control-Allow-Origin`（且状态是 405）→ 预检失败 → 浏览器**不会发出**真正的 POST。
即便是 `GET /v1/health/live` 这种简单请求，服务端虽然返回 200，但响应缺少 ACAO 头，
浏览器也不把响应交给脚本。

> **结论：一个跑在 `http://127.0.0.1:5173` 的独立前端，今天无法读取 Policy API 的任何响应。**
> 这不是"要不要加 CORS"的取舍问题，而是"当前形态下独立源前端等于不可用"。

### 3.4 预算 / 并发 / 限流

- 部署数值（`api/policy-api.yaml:18-36`）：`max_request_bytes: 65536`、`max_response_bytes: 262144`、
  `max_context_bytes: 32768`、`max_prompt_chars: 8000`、`max_concurrency: 8`；
  `budgets: evaluate 2000 / retrieve 2000 / validate 10000`；`rate_limit: capacity 60, refill 10.0/s`；
  `idempotency_ttl_seconds: 900`。
- **【实测】**
  - 70000 字节请求体 → **413** `body_too_large` / "请求体超过上限 65536 字节"。
  - `budget_ms = 600000` → **503** `request_budget_exceeded` / "调用方请求的预算 600000ms 超过本路由的上限 2000ms"。
  - `budget_ms = 10`（只能调小）→ **200**，正常返回。
  - 连续 75 次合法 evaluate → **`{200: 51, 429: 24}`**（令牌桶按 (客户端, 租户) 计）。
  - 429 响应体：`{"code":"rate_limited","detail":"请求速率超过该凭据的上限；稍后重试","retryable":true}`；
    响应头只有 `x-elapsed-ms` / `content-length` / `content-type`——**没有 `Retry-After`**。
- **【读码】** 限流发生在认证之后、DTO 校验之前（`src/policy_api/runtime.py:306` 调 `_authenticate`，
  其内部 `:479` 调 `rate_limiter.check`，而 DTO 校验在 `_dispatch` 的 `:526` 才发生）。
  即**格式错误的请求也消耗令牌**（probe2 中表现为 62 次 400 与 28 次 429 交替）。
- **【读码】** 并发闸门：取不到信号量即 503 `policy_busy`（`src/policy_api/runtime.py:482-495`），
  等待上限 0.5 秒，**不排队**。

### 3.5 幂等：语义与一个必须知道的陷阱

**契约（读码）**：键是 `(client_id, api_version, route, idempotency_key)`（`src/policy_api/idempotency.py:142-144`）。

- 同键 + 同请求摘要 → 返回**原来那份响应**并加 `Idempotency-Replayed: true`
  （`src/policy_api/runtime.py:326-357`）；
- 同键 + 不同摘要 → **409** `idempotency_key_conflict`，不覆盖不合并（`src/policy_api/idempotency.py:216-220`）；
- 台账不可读写 → 503 `idempotency_unavailable`（`:166-171`、`:310-315`）；
- **429 / 500 / 503 / 504 不落台账**（`src/policy_api/runtime.py:932-937`）——"重试看的还是同一个失败"没有意义。

**【实测】**

| 探测 | 结果 |
| --- | --- |
| evaluate + 同键同体，调用两次 | 200 / 200，`Idempotency-Replayed: true`，**两次响应逐字节相同**，且重放那次键按字母序排列（`_canonical_body`，`src/policy_api/runtime.py:918-925`） |
| evaluate + 同键换 `request_id` | **409** `idempotency_key_conflict` |
| **retrieve + 同键**（首次 10282 字节） | 首次 200 / 10282 字节；**重放 200 / 2 字节，正文 `{}`**，`Idempotency-Replayed: true` |
| 台账库级：7012 字节的响应 | 重放完整保留（1 个键） |
| 台账库级：9012 字节的响应 | **重放为空对象**（0 个键） |

**根因（读码）**：`src/policy_api/idempotency.py:33` `_MAX_RESPONSE_BYTES = 8192`；
`:250-259` 序列化超过该值时 `stored_body = {}`；`:221-226` 重放时把空字典原样返回，
**状态码仍是 200**。也就是说：大响应的"幂等重放"是一次**结构合法但内容为空**的 200。

> **控制台含义（重要）**：`retrieve`（10277 字节）与可能更大的 `validate` 响应都落在阈值之上。
> 前端**不要**给 `retrieve` / `validate` 带 `idempotency_key`；若带了，必须在重放路径上显式识别
> `Idempotency-Replayed: true` 且正文为 `{}` 并重新发起一次不带键的请求，否则会把"没有结果"
> 显示给用户。这一点在 `api/README.md` 与 Phase 7 文档里都没有写。

### 3.6 观测 JSONL：控制台"审计/回放"页能显示什么

**【实测】** `.tmp/console-probe/audit.jsonl` 共 **101 条**记录，字段固定 19 个

### 3.7 长任务缺口：API 没有 job / 异步概念

**【实测 + 读码】** 证据三条：

1. 路由层面没有任何作业概念：6 条路由全是同步请求-响应；`src/policy_api/` 全包检索
   `job` / `202` / `background` / `asyncio.create_task` → **0 处命中**。
2. 真正的"长"操作都活在 CLI 里，且**当前规模下并不长**：
   - `python -m retrieval.cli index --db .tmp/console-probe/index.sqlite3 --json`
     → 退出 0，run 报告 `duration_ms = 149`、`documents_indexed = 27`、
     `index_version = sha256:9752ab54…`、**`rule_sources: []`**；进程总墙钟 570ms。
   - `python -m retrieval.cli index --check` → 退出 0，"index is up to date for this corpus input"。
   - `python -m retrieval.cli verify` → 退出 0，336ms，"corpus: knowledge/corpus.yaml v1 | datasets=6 entries=27 | OK"。
   - `python -m policy.check --check-rules` → 退出 0，308ms，"PASS: 规则集校验通过，共 6 条规则"。
   - `python -m policy_api.cli self-check` → 退出 0，758ms。
   - `python -m policy_api.cli openapi --check` → 退出 0，654ms，"与快照一致（api_version=1.0）"。
3. 硬边界不是时间而是**并发与预算**：`max_concurrency = 8`（`api/policy-api.yaml:24`）、
   并发等待 0.5 秒即 503 `policy_busy`（`src/policy_api/runtime.py:486-491`）、
   `validate_ms = 10000`（`api/policy-api.yaml:29`）。

> **判断（实测支撑）**：今天缺的是**"写入/重建/预演"的路由**，不是"异步"。
> 因为重建只要 149ms，"必须新增 job 模型"的说法在现有语料规模上**得不到实测支持**。异步化的触发条件是：
> 语料规模大到重建超越 `validate_ms` 预算，或控制台要同时跑多个外部工具（Ruff/mypy/pytest）。
> 届时最小形态见 G8。

### 3.9 `evaluate` 的响应体规模敏感性（实测）

Lead 追问："幂等空体陷阱会在哪一类请求上真实触发？`evaluate` 会不会也超 8192？"
**答案是会。** 实测（`.tmp/console-probe/probe9.py`：用生成的规则文件抬高租户的规则数，
`include_evidence: true`，同一份上下文）：

| 规则数 | 响应体字节 | `summary.skipped` | 是否越过 8192 |
| --- | --- | --- | --- |
| 6（仓库现状 `policies/`） | 2052 | 6 | 否 |
| 10 | 3694 | 10 | 否 |
| 50 | 15854 | 50 | **是** |
| 120 | 37137 | 120 | **是** |
| 300 | 91857 | 300 | **是** |

- 跨界点落在 **10 与 50 条规则之间**（只测了这四个点，不做内插断言）；
- 增量来自 `skipped_rules` 明细（每条含 `rule_id` + `reasons` 文案），即
  `src/policy_api/runtime.py:572-573` 那一段；
- 仓库现状（6 条规则）**不会**踩到阈值：不带 `include_evidence` 实测 1375 字节，带了也只有 2052 字节。
  但这是**规则数量的函数，不是常数**。

> **控制台含义**：不能把"evaluate 很安全"当成"任何路由都能带幂等键"的通行证。
> 判据是**响应体是否可能超过 8192**，而它随规则集增长。稳妥规则只有一条：
> **幂等键只用在"响应体可证明很小"的请求上**，且所有路由都要能处理"200 + 空体 + 重放头"。

### G1 语料与镜像状态读取

- **为什么必须**：台阶 1–3。控制台要让用户"从文档出发"，就必须能回答 C1–C6（镜像目录与 manifest、
  条目在 manifest 中、`source_url` 非空、`license` 必填、**sha256/字节数与 manifest 一致**）
  与 C7–C10（索引是否含该文档、分块结果）。
  今天 C6 的漂移检测只活在 `python -m retrieval.cli verify`（退出码 1）里，API 侧唯一的痕迹是
  `retrieve` 响应里**硬编码**的 `hash_drift: []`（`src/policy_api/runtime.py:679`）。
- **最小设计**：
  - `GET /v1/knowledge/status?tenant=…`（只读，无需 body；或沿用 POST 信封保持一致）
  - 响应：`datasets[] {name, tier, visibility, license, entries}`、
    `documents[] {source_path, source_url, sha256, manifest_sha256, bytes, size_ok, hash_drift}`、
    `index {index_version, corpus_input_hash, documents, chunks, quarantined, generation}`、
    `verify {issues[], ok}`。
  - 实现上**直接调用** `retrieval.corpus.verify_corpus` / `ChunkStore.stats`——它们已在进程内可用，
    无需子进程（`verify` 实测 336ms，其中大半是解释器启动）。
  - 权限：租户边界内可用；不需新角色。
- **验收条款（与 §2.3 的落差对应）**：G1 上线前，界面**不得**把 `retrieve` 响应里的
  `index.hash_drift` 当作漂移证据——它今天是 `src/policy_api/runtime.py:679` 的硬编码 `[]`；
  漂移的唯一机器可读来源必须是本路由调用的 `retrieval.corpus.verify_corpus`（返回 `issues[]` +
  期望/实际 sha256）。只要这条没落地，漂移列只能显示"**未核对**"，不能显示"无漂移"。
- **契约影响**：`ROUTES` +1、`contract.ENDPOINTS` +1、`api/openapi.json` 需要 `--write`、
  `_ROUTE_STATUS_CODES` +1。
- **不做会怎样**：控制台只能让用户"盲选来源"；C6 的哈希漂移在 UI 上永远看不见，
  而这正是 AGENTS.md 第 12 条要求"不许静默"的那一条。

### G2 分块浏览与规则溯源读取

- **为什么必须**：台阶 3 与台阶 7。C10 要求 `rule_sources` 的 `heading_path` 能匹配到分块结果；
  C33 是"约定（非强制）"的溯源登记。**现状是空的**：`knowledge/corpus.yaml:129` 为 `rule_sources: []`，
  实测 `python -m retrieval.cli rules --rule DOC-001` → **退出 1**，"DOC-001: 没有登记的来源溯源"；
  索引 run 报告的 `rule_sources` 字段同样是 `[]`。
- **最小设计**：
  - `GET /v1/knowledge/documents/{source_path}/chunks`（分页：`cursor` + `limit ≤ 50`，
    返回 `chunk_id` / `heading_path` / `heading_anchor` / `ordinal` / `text_hash` / `char_count` / `truncated`；
    正文是否需要返回由"是否需要阅读原文"决定，`retrieve` 已经在返回 `text`，因此不构成新的信息暴露面）。
  - `GET /v1/policy/rules/{rule_id}/sources`（正向溯源）+ `GET /v1/knowledge/chunks/{chunk_id}/rules`（反向）。
    返回 `rule_id` / `rule_version` / `dataset` / `source_path` / `heading_path` / `chunk_id`；
    **未登记时返回 200 + `sources: []` + `registered: false`**，不要把"约定未登记"变成 404——
    那会把"当前仓库就是这样"误报成"这条规则不存在"。
  - **必须实现的校验**：返回的 chunk 必须来自 `ChunkStore` 的既有分块（C10 的"能匹配到分块结果"），
    而不是重新分块一次。
- **契约影响**：同上三件套；无需新错误码（未登记不是错误）。
- **不做会怎样**：控制台无法回答"这条规则引自文档的哪一段"，台阶 7 的溯源在 UI 上等于不存在；
  C33 的落差会继续只存在于 CLI 的退出码里。

### G3 规则草稿校验（不落盘）

- **为什么必须**：台阶 4 + 台阶 5。C13–C21 共 9 条字段/枚举/一致性校验（`id` 形状、`scope` 已知维度、
  `severity` 枚举、`enforcement.type`、`checker` 未知即报错、**规则体键名必须与 checker 一致**、
  规则体 schema、`source.kind` 枚举与 `source.path` 形状、未知顶层字段 `extra="forbid"`），
  再加上 C22（同 id 唯一）。这些目前**只有在文件被写进 `policies/` 之后**才能被发现。
- **最小设计**：
  - `POST /v1/policy/drafts/check`：请求带 `{yaml_text, tenant}`（或 `{rule: {...}}` 的结构化形态），
    服务端在内存里把文本写成 `.tmp/` 下的临时文件、用 `policy.loader` 的单文件解析路径校验，
    返回 `{ok, violations: [{rule_id?, field, line?, column?, message}], canonical_id, checker, checkers_available[]}`。
  - **绝不落进 `policies/`**：临时目录写在 `.tmp/` 下（AGENTS.md「临时文件与产物」一节），
    校验完即删。
  - 权限：新增角色 `policy-author`（否则任何 developer 都能拿服务端当 YAML 解析器，
    虽然只读但会把错误分类的细节暴露出去）。
- **契约影响**：三件套 + `_ROUTE_STATUS_CODES`。**不新增错误码**：YAML 语法错误也是
  200 + `ok:false`（"草稿不合法"是正常业务结果，不是传输错误）。
- **不做会怎样**：用户要在"改文件 → 过门禁 → 看报错 → 改回来"的环里迭代，
  而这恰好是最需要前置反馈的一组条件（C13–C21 每条都有明确的行列或字段位置可报）。

### G4 规则集加载预演（shadow load，本清单里最重要的一条）

- **为什么必须**：C23 —— **"整批文件全部成功才替换规则集；任一文件失败则整体不加载"**。
  这条是三道硬门禁里代价最高的一条：一条坏规则会让**整个规则集**不可加载
  （`policy.loader` 的原子性，`docs/project/architecture/规则文档转化为规则.md:235`）。
  今天唯一的预演手段是 CLI `python -m policy.check --check-rules`（实测 308ms，退出 0），
  它跑的是**磁盘上的现网规则集**，无法回答"加上我这条会怎样"。
- **最小设计**：
  - `POST /v1/policy/rule-set/preview`：
    请求 `{tenant, changes: [{action: "add"|"replace", path, content}]}`。
  - 服务端流程：把现网规则目录**复制**到 `.tmp/policy-preview/<run>/`（或只读 + overlay）→
    应用 changes → `policy.loader.load_rule_set([...], repo_root=…)` → 返回
    `{ok, rule_set_hash, rules: [canonical_id…], identity_changed: bool, diff: {added[], removed[], changed[]}, errors: [{path, line, column, message}], live_rule_set_hash}`。
  - **硬约束（必须写进实现的注释与测试）**：
    1. **绝不触碰** `LoadedTenant._rules` / `_rules_signature`（`src/policy_api/services.py:73-97`）；
    2. 预演返回的 `rule_set_hash` 是"**假如生效会是这个值**"，响应里必须有
       `applies_to_live: false` 之类的显式字段——否则控制台会把它当成已生效的哈希；
    3. 预演**不写** `.tmp/retrieval/` 索引、不刷新 readiness 缓存、不进幂等台账
       （否则"预演"会变成一种副作用）；
    4. **读取边界是 `repo_root`，不是 `rules_root`**——见下面的实测。

**【实测】`policy.loader` 的边界证据**（`.tmp/console-probe/probe9.py`）：

| 调用 | 结果 |
| --- | --- |
| `load_rule_set([".tmp/console-probe/rules-large-3"], repo_root=仓库根)` | **成功**（`GEN-001@1..GEN-003@1`）——`.tmp` 在仓库内，**即使不是租户的 `rules_root` 也照读** |
| `load_rule_file(".tmp/console-probe/rules-mixed/GEN-002.yaml", repo_root=".tmp/console-probe/rules-large-10")` | `LoaderError`："规则文件 … 不在规则目录 … 之内，拒绝加载" |
| `load_rule_set([".tmp/console-probe/rules-mixed"], repo_root=".tmp/console-probe/rules-large-10")` | 同一条 `LoaderError`（目录级同样受锚点约束） |
| `load_rule_set([".tmp/console-probe/rules-mixed"], repo_root=该目录本身)` | **成功**——锚点放宽到候选目录自身后，逃逸检查就失去意义 |
| 目录里同时放 `.hidden.yaml` / `notes.txt` / `GEN-002.yaml` | 只加载 `GEN-002@1`：隐藏文件与非 `.yaml`/`.yml` 后缀被跳过（C11） |

【读码】判定实现在 `src/policy/loader.py:79-90`（`_relative_to_root`：`path.resolve().relative_to(anchor)`）。

> **因此 G4 有三条硬性边界要求**：
> ① 规则目录列表只能是 **现网目录 + 候选文件的副本**，且候选副本必须落在 `tenant.root` 之内；
> ② `repo_root` 必须固定为 `LoadedTenant.root`（`src/policy_api/services.py:248`），
> **绝不能**放宽到临时目录——否则等同于关掉逃逸检查（上表第 4 行即反例）；
> ③ 预演目录里**不要混放**无关文件（`collect_rule_files` 会 `rglob` 整个目录），
> 单文件变更应传文件而不是目录。
  - 权限：`policy-author`；**审批不需要**（只读预演）；但要限流（内置令牌桶已按客户端计）。
  - 预算：需要一个独立预算键（例如 `budgets.preview_ms`），当前 `budgets` 只有三个键
    （`src/policy_api/config.py:83-88`），新增键会让 `api/policy-api.yaml` 与配置模型同步变化。
- **契约影响**：三件套 + `Budgets` 模型新增字段 + 部署配置新增字段。**这是唯一一条会改到
  `src/policy_api/config.py` 的缺口。**
- **不做会怎样**：控制台的"提交"按钮等于让用户**用现网规则集做实验**；
  C23 的原子性会从一个保护机制变成一次线上事故的来源。

### G5 门禁预检聚合

- **为什么必须**：台阶 6/7 的门禁不是一条命令，而是四条（实测全部 <1s）：
  `python -m policy.check --check-rules`（C11–C23）、`python -m retrieval.cli verify`（C1–C6）、
  `python -m validators.cli registry`（C25）、`python -m policy_api.cli openapi --check`（契约）。
  控制台要在"提交前"给出一张检查清单，靠前端逐个起子进程是不可接受的（浏览器起不了进程）。
- **最小设计**：
  - `POST /v1/policy/gates/precheck`：服务端**在同一进程内**依次跑上述四项（它们都是纯读取），
    返回 `{ok, checks: [{name, ok, detail, code?}], rule_set_hash, index_version, corpus_input_hash}`。
  - **不要**复用 `policy_api.cli` 的子进程：`contract.self_check` 已经是现成的进程内实现
    （`src/policy_api/contract.py:219-249`），`retrieval.corpus.verify_corpus` 与
    `validators.registry.load_config` 同样可进程内调用。
  - 预留一个"重活"开关：若将来某项超过预算，改为返回 202 + 作业 id（见 G8）。
- **契约影响**：三件套 + `_ROUTE_STATUS_CODES`；需要一个新的预算键（或复用 `validate_ms` 的 10s）。
- **不做会怎样**：控制台只能把"过门禁"交给用户自己在终端跑，操作平台的"可控"承诺落空。

### G6 会话身份读取

- **为什么必须**：【实测】`local-dev-token` 被授权两个租户，不声明 `tenant` 直接 403；
  而 API **没有任何接口告诉客户端"你这个令牌能用哪些租户/角色/项目"**。
  `/v1/ops/metrics` 的 `tenants` 是全部装配租户（`src/policy_api/runtime.py:822`），拿它当选择器会
  立刻在下一个请求上撞 403。控制台连"该显示哪几个租户"都无从得知。
- **最小设计**：`GET /v1/session`（带 Bearer，无需 body）→
  `{client_id, subject, roles[], tenants[], projects[], tenant_hint_required: bool, api_version}`。
  `tenants` 必须是**该令牌被授权的集合**（即 `ClientSpec.tenants`），
  `tenant_hint_required = len(tenants) > 1`（对应 `src/policy_api/auth.py:172-178` 的分支）。
  **不返回**令牌任何形式（连 sha256 也不返回；`token_ref` 已经出现在日志里，响应里没有必要）。
- **实现约束（由 `ux-logic` 指出并经读码核实，必须写进实现与测试）**：`/v1/session` **不能**
  直接按 `route="session"` 调 `authorize()`——那会走到 `src/policy_api/auth.py:172-178` 的
  "多租户必须显式声明 tenant"分支，**恰好把本端点要服务的那个令牌挡成 403 `token_scope_mismatch`**。
  必须像 `metrics` 一样，在 `src/policy_api/auth.py:154-162` 增加一条"跨租户路由"早返回分支
  （返回 `tenant=""`，保留 `client_id` / `roles` / `projects`）。连带决定三件事：
  ① `ROUTES`（`src/policy_api/runtime.py:73`）是否收录 `session`：收录则进指标/日志口径，
  不收录则 `contract.py:140-142` 的子集检查不受影响；
  ② 限流键 `f"{auth.client_id}:{auth.tenant}"`（`src/policy_api/runtime.py:479`）在 `tenant=""` 时
  退化为 `"<client_id>:"`，语义仍正确，但必须在测试里钉死；
  ③ **改 `auth.py` 属于敏感改动**（它是"租户只来自令牌"这条信任规则的实现处），必须补契约测试：
  多租户令牌 + 不带 `tenant` 调 `session` → 200；同一令牌调 `evaluate` 仍 → 403。
- **契约影响**：三件套。**敏感度**：这条路由把"令牌的可达范围"回显给调用方——
  这是它自己的信息，不是别人的，**不违反** `errors.py` "不泄露资源是否存在"的原则
  （原则针对的是**别的**资源，见 `src/policy_api/errors.py:7-9`）。
- **不做会怎样**：控制台要么硬编码租户名（部署一变就坏），要么让用户猜、靠 403 报错试出来。

### G7 提交与审批的接入点：**不开在 `policy_api` 里**

- **为什么必须**：AGENTS.md 第 39 条明确"编排层的写入仍然走 Phase 4 的受控执行链（**API 没有 enforce 路由**）"。
  规则文件的唯一合法写入路径是注册表里的 `orc.policy.edit`
  （`registry/tool-registry.yaml:317-345`）：`risk: reversible_write`、**`approval: required`**、
  `path` 必须匹配 `^policies/[A-Za-z0-9._/-]+$`、`post_checks: [content_matches, file_changed, file_syntax, diff_recorded]`、
  `rate_limit: {max_calls: 10, window_seconds: 60, ...}`，
  notes 写明"审批必须与 `action_hash` 绑定"。
  `action_hash` 覆盖工具 schema 哈希、规范化参数、主体、权限与上下文摘要
  （`src/enforcement/action.py:9-10`），授权短时效、单次使用，
  pre-check 逐位复验（`src/enforcement/executor.py:6`、`:434`）。
- **最小设计（架构约束，不是路由）**：
  1. **控制台不写文件**：前端把"要不要改、改成什么"表达成一次工具调用意图；
  2. 提交交给 `src/orchestration/`：`Change.tool_id` 在路径以 `policies/` 开头时**自动**选择
     `orc.policy.edit`（`src/orchestration/nodes.py:93-97`，常量 `:68`），
     说明"改规则需人工审批"这件事在编排层已经是**结构化**的，不需要控制台重新发明；
  3. 审批文件由 Phase 4 的 `ApprovalRecord` 复验（`src/enforcement/approvals.py:70-131`），
     编排层只是调用方；"图到达了审批节点"**不等于**用户批准；
  4. 控制台需要的**只读**视图（审批收件箱、运行状态、checkpoint 摘要）应来自**编排层的产物目录**
     或一个**独立的 BFF 进程**，不要把 `src/policy_api` 与 `src/orchestration` 缝合——
     AGENTS.md 第 35 条要求"删掉整个 `src/orchestration/`，平台照常独立运行"，
     第 30 条要求"`policy_api` 只做协议 → 领域模型 → 协议"。
- **契约影响**：0（`policy_api` 的路由表不变）。代价是控制台多一个后端进程/一个只读文件系统视图。
- **不做会怎样（反面）**：若把写路由加进 `policy_api`，会同时破坏三条约束——
  第 30 条（API 变成第二份业务逻辑）、第 39 条（出现 API 侧 enforce 路径）、
  第 35 条（平台与编排层耦合）；而且审批与 `action_hash` 的绑定关系会在 HTTP 边界上被重新实现一次，
  这正是"参数变一个字符旧授权即失效"最容易失效的地方。

### G8 任务 / 作业模型：**建议暂不新增**，但记录触发条件

- **实测依据**：索引重建 27 文档 `duration_ms = 149`；四个门禁 CLI 全部 <1s（§3.7）。
  因此"操作平台必须先有异步作业模型"这一说法**在当前规模下不成立**。
- **触发条件（任一满足再立项）**：
  1. 语料规模增长到单次重建超过路由预算（`validate_ms = 10000`，`api/policy-api.yaml:29`）；
  2. 控制台要在一次交互里串行跑多个外部工具（Ruff / mypy / pytest），
     而它们受 `max_concurrency = 8` 与并发闸门 0.5s 的限制（`src/policy_api/runtime.py:486-491`）；
  3. 需要"提交 → 审批 → 执行 → 回滚"的跨请求状态机。
- **届时最小形态**：`202 Accepted` + `Location: /v1/jobs/{job_id}`，
  作业状态放在**编排层 checkpoint**（已有原子替换 + 状态摘要，`src/orchestration/checkpoint.py`），
  不要另起一套；并且必须遵守 AGENTS.md 第 36 条"图状态里不放正文"。
- **不做会怎样**：今天不做，代价是"预演/门禁"这类操作只能同步返回；而它们实测都在 1 秒内，
  代价可以接受。

## 5. 治理路径（已实现事实 + 提案接入点）

**唯一合法写入路径**（全部为已实现事实）：

1. 规则文件位于 `policies/<domain>/<ID>.yaml`，文件名只是约定，规则 ID 只由 `id` 字段决定
   （`docs/project/architecture/规则文档转化为规则.md:156-158`；C11 要求文件在显式规则目录内、后缀
   `.yaml`/`.yml`、非隐藏、不逃出 `repo_root`）。
2. 写入动作只能由 `orc.policy.edit` 执行（`registry/tool-registry.yaml:317-345`），
   它是 `approval: required`、`path` 白名单 `^policies/[A-Za-z0-9._/-]+$`、带四项 post-check。
3. 审批是 Phase 4 的 `ApprovalRecord`，绑定 `action_hash`；参数变一个字符旧授权即失效
   （AGENTS.md 第 14/38 条；`src/enforcement/executor.py:6`）。
4. 副作用前后写台账与审计链；审计/台账不可写时**不执行**（AGENTS.md 第 16 条）。
5. 规则集变更后 `RuleSet.identity` 变化，向外传播到 Phase 7 观测摘要与 Phase 8 checkpoint；
   恢复时会清掉旧 trace 与旧验证结果、重新评估，**不沿用旧 allow**
   （`docs/project/architecture/规则文档转化为规则.md:185-189`）。

**AGENTS.md 第 39 条（"API 没有 enforce 路由"）对控制台架构的含义**：

- 控制台**不能**通过 `policy_api` 写文件——不是因为"没实现"，而是因为这是**刻意的边界**：
  `ROUTES`（`src/policy_api/runtime.py:73`）里永远不该出现 `enforce` / `write` / `apply`。
- 控制台的"提交"是一次**意图**，不是一次文件写。意图必须经过
  Policy Engine 判定 → Phase 4 pre-check（含审批复验）→ 受控驱动 → post-check 这条链。
- 因此操作平台至少是**两个后端**：`policy_api`（判定/检索/证据/健康，只读语义）
  + 编排与执行侧（写语义，已有 CLI 与产物目录）。把它们合成一个进程会让
  "API 是传输边界"这条约束失效。
- 对控制台前端的影响：**"提交成功"的判定点是台账/checkpoint 的终态，不是 HTTP 200**。
  UI 必须把"已提交待审批"、"审批已过期"、"参数已变化（`approval_param_mismatch`）"、
  "副作用状态未知（`side_effect_unknown`）"当成**不同的可见状态**
  （失败码见 `docs/project/engineering-policy-platform/phases/phase-8-langgraph-orchestration.md:119,130`）。

## 6. 前端对接要求

### 6.1 错误码 → UI 状态映射（依据 `src/policy_api/errors.py:29-107`）

统一响应形状（`src/policy_api/errors.py:152-165`）：

    {"error": {"code": "…", "detail": "…", "retryable": true|false, "request_id": "…", "trace_id": null}}

| HTTP | 错误码 | UI 语义与建议动作 |
| --- | --- | --- |
| 400 | `schema_version_missing` / `schema_version_unknown` | **前端 bug**：信封漏了 `api_version` 或版本不匹配。不得重试，报"客户端版本与服务端不兼容" |
| 400 | `body_invalid` | 表单校验失败。`detail` 已压缩成"字段位置: 原因"（最多 5 条，`src/policy_api/runtime.py:963-972`），可直接展示 |
| 400 | `context_invalid` / `query_invalid` / `target_invalid` | 上下文维度非法（如未知 `operation` 枚举） |
| 401 | `unauthenticated` / `token_expired` | **含"跨租户"**：【实测】越权租户对外就是 401。UI 应提示"重新登录或检查租户选择"，**不要**显示"租户不存在" |
| 403 | `token_scope_mismatch` | 令牌被授权多个租户但没带 `tenant`：【实测】必须先让用户选租户，然后**重发同一请求**（请求体唯一变化是 `tenant`） |
| 403 | `forbidden` / `project_not_allowed` / `metrics_forbidden` | 权限不足，功能入口应隐藏（指标页仅 `ops` / `service-admin` / `metrics_clients`） |
| 404 | `tenant_not_found` / `not_found` | 展示为"服务端不认识这个边界/路由"，不要区分二者 |
| 405 | `method_not_allowed` | 前端 bug |
| 409 | `idempotency_key_conflict` | **必须换新键重发**；同键换体永远不会成功 |
| 413 | `body_too_large` | 输入过大（`max_request_bytes = 65536`），提示用户裁剪 |
| 415 | `unsupported_media_type` | 前端 bug（必须是 `application/json`） |
| 429 | `rate_limited`（`retryable: true`） | 退避重试。**【实测】响应没有 `Retry-After` 头**，需要前端自己做指数退避 |
| 500 | `internal_error` | 显示 `request_id` 供排查，可重试 |
| 503 | `knowledge_unavailable` / `validator_unavailable` / `rule_set_unavailable` | **依赖不可用**：功能级降级提示，**不得**显示为"没有结果"或"通过" |
| 503 | `audit_unavailable` | 服务端拒绝返回决定（日志不可写）；提示"服务暂不可用" |
| 503 | `policy_busy`（`retryable: true`） | 并发已满，退避重试 |
| 503 | `request_budget_exceeded`（`retryable: false`） | **前端 bug**：`budget_ms` 只能调小 |
| 503 | `idempotency_unavailable` | 台账不可用，退避重试 |
| 504 | `evaluate_timeout` / `retrieve_timeout` / `validate_timeout`（`retryable: true`） | **没有结论**。UI 必须显示"未得出结论"，**绝不能**渲染成 allow |

**同一类"参数不对"有两级失败面（实测）**：

| 输入 | 结果 | 依据 |
| --- | --- | --- |
| `budget_ms = 5000`（路由默认 2000，DTO 上限 600000 之内） | **503** `request_budget_exceeded` | `src/policy_api/runtime.py:134-149` |
| `budget_ms = 600001` | **400** `body_invalid`（"Input should be less than or equal to 600000"） | DTO 上限 `src/policy_api/models.py:188` |
| `budget_ms = 0` | **400** `body_invalid`（"greater than or equal to 1"） | 同上 |
| `validate` 请求里带 `include_evidence` | **400** `body_invalid`（"Extra inputs are not permitted"） | 该字段只属于 `EvaluateRequest`（`models.py:235`） |
| `evaluate` 请求里带 `include_decision` | **400** `body_invalid` | 该字段只属于 `ValidationRequest`（`models.py:288`） |

即：**"值超过路由预算"是 503，"值超出 DTO 范围"或"字段串了路由"是 400**。
控制台的滑块上限若写成 600001，用户会拿到 400 而不是预算错误——两个数必须成对写进本地校验。

**三条硬规则**：

1. **只用 `code` 做分支，不用 `detail` 文案**（`detail` 是服务端生成的可读文本，
   且被截断到 240 字符，`src/policy_api/errors.py:109-118`）。
2. **`retryable` 是服务端给的唯一重试信号**，前端不得自行把 403/400 变成可重试。
3. **504 / 503 一律不等于 allow**（AGENTS.md 第 33 条；实现见 `src/policy_api/runtime.py:543-549,654-660,769-775`）。

### 6.2 分页与大对象

- **没有分页机制**：没有任何路由接受 `cursor` / `offset`。可行的替代：
  - `retrieve` 的 `limit ≤ 50`（`src/policy_api/models.py:250`）；
  - `validate` 的证据条数被服务端截断到 **512 条**并给出 `truncated_evidence` 计数
    （`src/policy_api/runtime.py:779-783,975-976`）——UI 必须显式显示"还有 N 条未返回"；
  - 请求侧上限：单字段 `max_context_bytes = 32768`（**逐字段**检查 `file`/`module`/`task`/`git_diff`，
    见 `src/policy_api/runtime.py:158-180`）、`max_prompt_chars = 8000`、整体 `max_request_bytes = 65536`。
- **【实测】响应可以很大**：`retrieve` limit=3 就有 10277 字节；`validate` 实测 6143 字节，
  上限 `max_response_bytes = 262144`。因此：
  - 前端**必须**能在 409/幂等重放路径上处理 `{}`（见 3.5）；
  - 控制台若要展示大对象，应把"大列表"拆成多次小查询，而不是一次拉回 262144 字节。

### 6.3 幂等与重试

| 场景 | 建议 |
| --- | --- |
| `evaluate`（响应 1375 字节，远小于 8192） | **可以**带 `idempotency_key`，重放逐字节相同，安全 |
| `retrieve`（实测 10277 字节）/ `validate`（可能更大） | **不要**带 `idempotency_key`：重放会返回 200 + `{}` |
| 一次逻辑提交的重试 | 用**同一个**键（幂等语义正确）；**改了请求体的任何字段后必须换新键**，否则 409 |
| 收到 409 | 生成新键重发，不要复用 |
| 收到 429 / 503 / 504 | 台账不记录这些失败（`src/policy_api/runtime.py:932-937`），可直接重试；建议指数退避（无 `Retry-After`） |
| 响应头 | `Idempotency-Replayed: true` 时必须显式判断"正文是否为空对象" |

### 6.4 CORS / 同源：两种部署形态的取舍

| 形态 | 需要做什么 | 代价 | 现状 |
| --- | --- | --- | --- |
| **A. 同源托管**（前端由 Policy API 进程托管） | 新增静态挂载路由 + `ROUTES` / `contract.ENDPOINTS` / `api/openapi.json` / `_ROUTE_STATUS_CODES` 同步；前端与 API 同端口 | 前端与"判定传输边界"耦合进同一进程；刷新静态资源要走 `--write` 更新契约快照（因为新增了路径）；**不需要** CORS | **不存在**（实测 404） |
| **B. 独立源 + CORS**（前端 `:5173`，API `:8088`） | 注册 `CORSMiddleware`，显式白名单 origin（**不能 `*`**：要带 `Authorization` 头，且 `*` 与凭据语义相冲）；必须处理 `OPTIONS` 预检；暴露 `X-Elapsed-Ms` / `Idempotency-Replayed` 需要 `expose_headers` | 多一个可被攻击的跨源入口；origin 白名单成为新的部署数据（应进 `api/policy-api.yaml`，与 `clients` 同级）；**必须有契约变更**（新配置字段） | **不支持**（实测无 ACAO、预检 405） |
| **C. 反向代理同源**（前端静态由 Nginx/Caddy 提供，`/v1/*` 反代到 API） | 不改动 `policy_api` 一行代码 | 需要一个额外部署组件；但 `policy_api` 的契约快照完全不变 | **不存在**，但**零代码改动** |

**建议**：优先 C（零契约变更、零 `policy_api` 改动），其次 A，最后 B。
无论选哪种，**`docs_url` / `redoc_url` 已被显式关闭**（`src/policy_api/app.py:179-180`），
控制台不要指望服务端提供交互式 API 文档；而 `/v1/openapi.json` 是匿名可读的（§3.8）。

### 6.5 其他前端必须知道的形状

- `context.file` 必须是**仓库相对路径**（`normalize_repo_path`，`src/policy_api/models.py:115-121`），
  绝对路径会被拒。
- `principal` 是**必填**（`src/policy_api/models.py:230-235`）——`subject` 由客户端声明，
  服务端不从路径或载荷推断（AGENTS.md 第 6 条）。UI 必须有"我是谁"的显式输入或登录态。
- `tenant` 是**提示**，不是权威边界；权威来自令牌（`src/policy_api/runtime.py:497-504`）。
- 空字符串与 `null` 不是一回事：`idempotency_key: "  "` → 400 `body_invalid`
  "空字符串与 null 不是一个意思：没有值就写 null"（`src/policy_api/models.py:219-227`）。
- 未知字段 → 400（`extra="forbid"`，`src/policy_api/models.py:10`）；**前端不能给请求体加自定义字段**。
