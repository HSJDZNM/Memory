> 目的是回答"外部框架有哪些切分策略、它们的默认口径是什么、本项目的 `markdown-sections-2` 该学什么、不该学什么"。
> 结论以**主源**（官方文档 / GitHub 源码）与**本仓库语料上的实测**为准；不确定项集中写在 §8。
>
> **本次快照（2026-09-23，§4 三张表全部按它重算）**：`knowledge/corpus.yaml` 6 数据集 / **42 条目**、
> 索引 **1013 片段**（`truncated=0` / `oversized=8`）、`index_version` 前缀 `sha256:91599f3e`、
> `CHUNKER_VERSION = markdown-sections-2`、评测集 **v3**（`tests/fixtures/retrieval_eval/baseline-v3.json`）。

## 2. 外部框架策略速览

### 2.1 LangChain（基类默认：`chunk_size=4000`、`chunk_overlap=200`、`length_function=len`，**单位是字符不是 token**）

| 策略 | 依据 | 关键默认 | overlap | 结构 | ID |
| --- | --- | --- | --- | --- | --- |
| CharacterTextSplitter | 字符 | `separator="\n\n"` | 有 | 无 | 无（可加 start_index） |
| RecursiveCharacterTextSplitter | 字符 | `separators=["\n\n","\n"," ",""]`、`keep_separator=True` | 有 | 仅段落→句→词边界 | 无 |
| MarkdownHeaderTextSplitter | 标题行 | `headers_to_split_on` **必填**、`strip_headers=True`、**无 chunk_size** | **无** | 标题栈 → metadata，标题不进正文；**围栏感知**（\`\`\` / ~~~ 内不识别标题） | 无 |
| MarkdownTextSplitter | 字符 | = Recursive + Markdown 分隔符表 | 有 | 同上 | 无 |
| ExperimentalMarkdownSyntaxTextSplitter | 行 | 默认 `#`…`######`，代码块单独成块 | 无 | Header/Code 元数据 | 无 |
| TokenTextSplitter | tiktoken token | `encoding_name="gpt2"` | 有 | 无 | 无 |
| HTMLHeader / HTMLSection | DOM 元素 / 标签+字号 | `headers_to_split_on` 必填 | 无 / 有 | 祖先标题 → metadata | 无 |
| RecursiveJsonSplitter | JSON | `max_chunk_size=2000` | 无 | 保留 key 路径 | 无 |
| SemanticChunker（experimental，README 自述 sunset） | 句子 embedding 距离 | `breakpoint_threshold_type="percentile"`、`buffer_size=1`、**无 chunk_size 上限** | 无 | 无 | 无 |

要点：**LangChain 的 Markdown 切分器是围栏感知的**（源码 `in_code_block`/`opening_fence`），但它逐行
`line.strip()` 后再入块——**缩进会被抹掉**（本语料以空白开头的行有 2507 行，全部受影响）。它也没有 `chunk_size`：
超长小节只能靠后接别的 splitter。

### 2.2 LlamaIndex（长度单位是 **token**）

| 策略 | 依据 | 关键默认 | overlap | 结构 | ID |
| --- | --- | --- | --- | --- | --- |
| TokenTextSplitter | token | `chunk_size=1024`、`chunk_overlap=20`、`separator=" "`、`backup_separators=["\n"]` | 有（按 token 回填） | 无 | `uuid4` |
| SentenceSplitter | 段落→句子→次级正则→空格→逐字符，按 token 计长 | `chunk_size=1024`、`chunk_overlap=200`、`paragraph_separator="\n\n\n"`、`secondary_chunking_regex` 含中文标点 `。？！`、分句靠 nltk punkt | 有 | 无 | `uuid4` |
| CodeSplitter | tree-sitter AST | `language` 必填、`max_chars=1500`、`max_tokens=512`；`chunk_lines=40`/`chunk_lines_overlap=15` 在 main 的切分逻辑里**未被读取** | 无 | 无 | `uuid4` |
| MarkdownNodeParser | 行级 `^(#+)\s` 标题 | **无 chunk_size/overlap**；`\`\`\`` 内不识别标题 | 无 | `metadata["header_path"]`（只含父级） | `uuid4` |
| SemanticSplitterNodeParser | 相邻句组 embedding 距离，取第 95 百分位为断点 | `breakpoint_percentile_threshold=95`、`embed_model` 必填 | 无 | 原句入 metadata | `uuid4` |
| SentenceWindowNodeParser | 一句一节点 + 窗口 | `window_size=3` | 无 | window/original_text 入 metadata | `uuid4` |
| HierarchicalNodeParser | 多级 SentenceSplitter | `chunk_sizes=[2048,512,128]` | 每级 20 | PARENT/CHILD 关系 | `uuid4` |
| IngestionPipeline + docstore | 增量/去重 | `docstore_strategy=UPSERTS` | — | docstore 存 `{doc_id: node.hash}` | 见下 |

要点：**LlamaIndex 默认不给稳定 ID**（`default_id_func = str(uuid.uuid4())`），同一段原文重建索引
node_id 会变；内容哈希是另一个字段（`TextNode.hash = sha256(text + metadata)`），docstore 靠它判重。
`AutoMergingRetriever` 的 `simple_ratio_thresh=0.5`：命中的子节点数达到父节点子节点总数一半时，
用**父节点**替换子节点——这是"分层召回"的现成实现。

### 2.3 其他（精选）

| 方案 | 依据 | 关键默认 | overlap | 稳定 ID |
| --- | --- | --- | --- | --- |

| Chonkie SemanticChunker | 句 + embedding 相似度（Savitzky-Golay 平滑） | `threshold=0.8`、`similarity_window=3`、默认模型 `potion-base-32M` | 无 | 无 |
| Chonkie NeuralChunker | 分类模型直接预测切点 | `mirth/chonky_distilbert_base_uncased_1`、`stride=256/512` | 无 | 无 |

| Chonkie LateChunker | 边界同 Recursive，**改 embedding 计算方式** | `chunk_size=2048` | 无 | 无 |

### 2.4 三个共性结论

1. **没有一家默认给"位置稳定 ID"**：LlamaIndex/Chonkie 是 uuid4；LangChain 的 indexing API 用
   `uuid5(sha1(内容)+sha1(metadata))`（同一内容+同一 metadata 稳定，**改 metadata 就换 ID**）；
   只有 Unstructured 是按内容哈希派生的确定性 ID。**都没有"内容变了但位置不变"的语义**。
2. **默认参数不通用**：LangChain 4000 字符 / LlamaIndex 1024 token / Chonkie 2048 / Unstructured 500 字符
   / Docling = 所选模型的 max_seq_length。跨框架抄默认值没有意义。
3. **CJK 默认都不覆盖**：LangChain 的 `Language` 枚举无 zh，官方建议手动把 `。` `，` 等加进
   `separators`；LlamaIndex 的 `secondary_chunking_regex` 虽然含 `。？！`，但默认 nltk punkt 是英文模型，
   中文会退化成逐字符兜底；Chonkie 需要切到 `lang="zh"` 配方。

## 3. 本项目的分块与索引（对照基线）

六条规则（详见 `src/retrieval/chunker.py` 模块头与 `docs/project/architecture/规则文档转化为规则.md` 台阶 3）：
剥 front matter（元数据转存 `documents.front_matter`）→ 围栏外识别标题（标题行**只进** `heading_path`）→
空行为界块化（代码块为原子）→ 按 `max_chunk_chars=1200` 打包，段落超预算时**先按句读拆**
（英文 `.?!` 后跟空白、中文 `。！？；…`；自 `markdown-sections-2` 起），只有"再也拆不开的单元"超过
`hard_max_chunk_chars=8000` 才截断并记 `truncated + original_chars` →
`chunk_id = hash(document_id | anchor | part_index)`、`text_hash = sha256(原文)` → 幂等重建（只动相关 chunk）。

**本项目当前快照的实测**（下列数字全部由 §8 的命令在同一批语料上重算，旧版报告里的 27 篇 / 535 片段已过期）：

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| 索引片段数 | 1013 | 与 `baseline-v3.json` 的 `index.chunks` 一致；42 篇文档 |
| 逐篇无损 | 42 / 42 篇 compact 相等 | 参考文本 = 非空章节的块（标题行本就不进 chunk） |
| `truncated` / `oversized` | **0** / 8 | oversized 全是无法切开的原子代码块（> 1200 字符且 ≤ 8000） |
| 幂等重建（库副本上重跑 `index`） | `created=0 updated=0 unchanged=1013 removed=0` | 未变的文档连分块都不重跑 |

与外部框架的三个结构差异：

| 维度 | 外部主流 | 本项目 |
| --- | --- | --- |
| 身份 | 内容哈希（LangChain）/ uuid4（LlamaIndex、Chonkie） | **位置 ID + 内容哈希分离**：改字不改 `chunk_id`，只改 `text_hash`/`revision` |
| 边界 | 窗口/句子/语义模型 | **章节 + 字符预算**：不跨章节，代码块永不切断（记 `oversized`） |
| 重叠 | 默认 200 字符/token（LangChain、LlamaIndex） | **无 overlap**：Context 层按 `text_hash` 去重，重叠会与去重语义打架 |
| 溯源 | 无（元数据可选） | `rule_sources(rule_id, rule_version, chunk_id)` 表 + 标题路径前缀解析 |

## 4. 实测：同一份语料、同一套指标

**本次快照指纹**：语料 **42 条目** / 索引 **1013 片段** / `index_version` 前缀 **`sha256:91599f3e`** /
`CHUNKER_VERSION = markdown-sections-2`。下面三张表的每一行都由这一次同批计算产生。

**指标定义**（全部在本仓库语料上计算）：

- **切断代码块**：chunk 文本内围栏计数为奇数的 chunk 数（围栏感知扫描）。
- **正文残留标题行**：chunk 内（围栏外）出现的 ATX 标题行数。含义随策略而变：对无结构策略（recursive、token 窗口）
  意味着该 chunk **跨了章节边界**；对 `MarkdownHeaderTextSplitter` 意味着 `####` 及更深的标题**没参与切分**（默认只配 `#`/`##`/`###`）；
  本项目为 0 是设计结果——标题行只进 `heading_path`，正文里一行都不留。
- **字符产出比**：所有 chunk 去空白字符数 ÷ 参考文本去空白字符数。>1 = 有重复（overlap）；<1 = 有内容未进块。
  参考文本按策略口径取：**本项目 = 非空章节的块**（标题行本就不进 chunk），**外部策略 = 全文**（含 front matter）。
- **均长 / p95 / 最长**：`len(chunk.text)` 的均值、最近秩 p95（升序第 ⌈0.95n⌉ 个）与最大值，单位是字符不是 token。
- **编辑稳定性（变化率）**：在**每篇**文档的**第 0 字节**插入同一段固定文本（294 字符）后，"文本在旧集合里找不到"的 chunk 占比。
  插入位置与上一版一致（**在 front matter 之前**，对每个策略用同一次插入），文本逐字见 §8。
  表中数值是**变化率**——**越低越好**；"稳定性"是它的补数，但两者只在"每篇各自算比例再平均"这一种聚合下严格互补
  （见 §4.2 的聚合口径说明）。
- **聚合口径**：比率类指标必须写明是"每篇算比例再平均"还是"总体相除"——本项目 6.2% 属前者，换成后者是 4.0%，
  两者都不算错，但不可混用（同一个测量会因为聚合方式不同而给出不同数字）。

### 4.1 结构保真（6 数据集 / 42 篇）

| 策略 | chunk 数 | 均长 | p95 | 最长 | 切断代码块 | 正文残留标题行 | 字符产出比 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **本项目 markdown-sections-2** | 1013 | 636 | 1163 | 3846 | **0** | **0** | 1.00 |
| LC recursive 4000/200（框架默认） | 222 | 3107 | 3974 | 3996 | 24 | 817 | 1.01 |
| LC recursive 1000/200（教程常用） | 996 | 729 | 987 | 999 | 54 | 939 | 1.07 |
| LC markdown-header（忠实复现） | 662 | 984 | 3266 | **16090** | 0 | 106 | 0.97 |
| token-window 1024/200（tiktoken） | 188 | 4348 | 5362 | 5627 | 12 | 927 | 1.20 |

读法：LangChain 默认的 4000 字符窗口在这份语料上只产出 222 块（均长 3107），**817 处正文残留标题行**
意味着大量 chunk 跨章节；Markdown 切分器不切代码块（0 处切断）但**没有尺寸上限**（最长 16090 字符），
并逐行 `strip()` 把缩进抹平；token 窗口重复率最高（1.20——200 token 的 overlap 会被解码回原文）。
本项目那三列是同一件事的三面：标题只进 `heading_path`、代码块是原子单元、打包无损——1.00 的产出比
是"一个字符都没丢、也没重复"的实测结果（`produced == reference == 547144`），不是取整。

口径命令：`python .tmp/chunking-report/measure.py --protocol prefix-raw`（一次性脚本，方法与日志见 §8）。

### 4.2 编辑稳定性（变化率，越低越好）

| 策略 | 文本变化的 chunk 占比 | 新增 chunk（全库） | 平均 chunk 数（改前） |
| --- | --- | --- | --- |
| **本项目** | **6.2%**（每篇 +1 个） | +42 | 24.1 |
| LC recursive 4000/200 | 46.0% | +2 | 5.3 |
| LC recursive 1000/200 | 19.8% | +8 | 23.7 |
| LC markdown-header | 9.4% | +0 | 15.8 |
| token-window 1024/200 | 100% | +2 | 4.5 |

读法：窗口类策略的边界是**位置**的函数，开头插入内容会让后面所有窗口整体位移（token 窗口 100% 全变）；
本项目与 Markdown 切分器的边界是**结构**的函数，只有被改的那一节会变——这正是"只动相关 chunk"能成立的前提。
注意 Markdown 切分器的占比（9.4%）高于本项目（6.2%）**不是因为它更不稳**：两者都是"每篇恰好 1 个 chunk"，
差别只在分母（它平均 15.8 块、本项目 24.1 块）——同一个绝对工作量，块切得越细看起来越"稳定"。

**不要只看百分比**："变化 chunk 占比"的分母是块数，块切得越细，同一个改动看起来越"稳定"。用字符级口径复核
（插入内容 294 字符，"放大系数" = 变化字符数 ÷ 294）：

| 策略 | 变化 chunk 占比 | 变化**字符**占比 | 变化 chunk 数（绝对值） | 变化字符数（绝对值） | 放大系数 |
| --- | --- | --- | --- | --- | --- |
| **本项目** | 6.2% | 6.4% | 1.00 | 596 | **2.03×** |
| LC markdown-header | 9.4% | 6.4% | 1.00 | 596 | 2.03× |
| LC recursive 1000/200 | 19.8% | 20.2% | 2.26 | 1766 | 6.00× |
| LC recursive 4000/200 | 46.0% | 47.7% | 1.79 | 5844 | 19.9× |
| token-window 1024/200 | 100% | 100% | 4.52 | 19839 | 67.5× |

结论：两种口径给出**同一排序**（本例中分母陷阱没有翻盘），所以增量成本应按"变化字符数"读——
它才是重写数据库行、重建 FTS 行与推进 `revision` 的实际工作量。变化字符数的下界是"被改段所在块的大小"
（所以本项目 ≈ 2×：新块同时包含插入文本与原前言），而窗口/重叠策略会把改动**放大到后续所有块**。

**本项目的 6.2% 是怎么算出来的**：42 篇文档**每篇恰好变化 1 个 chunk**（分布 `{1: 42}`），逐篇变化率从 1.4%（大文档）
到 25.0%（只有 4 个 chunk 的文档）不等；
**口径 A（每篇变化率求平均）= 6.17%**（即表中的 6.2%），**口径 B（42 ÷ 1055 总体相除）= 3.98%**。
所以正确的读法是"**变化率 6.2%，即 93.8% 的 chunk 一字未动（平均意义）**"，而不是"稳定性 6.2%"。
绝对量同向：全库只多出 42 个 chunk（1013 → 1055），变化字符 596 ≈ 2×294——下界就是"新块含插入文本原前言"。

**这组数不是新口径**：把同一协议放回 v2 时代的 27 篇语料重跑，本项目得到
`变化 chunk 7.80% / 变化字符 8.12% / 1.00 块 / 593 字符 / 2.02×`，与上一版报告的
`8% / 8% / 1.0 / 593 / 2.0×` 逐项对上——所以表里的差异来自语料扩到 42 篇，不是口径改动。

**这张表最重要的一行是"五个策略全部满分"**：在本仓库自己的 7 条查询、门槛 hit@5 = support@5 = 1.0 的
评测集上，**分块策略分不出胜负**（recall 的细微差别来自 chunk 大小，不构成选型依据）。
这与学术证据一致（§5）——换策略的收益不稳定，**决定性的差异在结构保真、可追溯、增量重建这些工程属性上**，
而那正是本项目的设计目标。

三条把这张表读得更准的事实（都来自 §8 的同一次运行）：

1. **recall 的全部差异来自 Q2**：五个策略的 recall 只有 0.914 与 0.886 两个取值，
   区别只是 Q2 的 5 个期望文档里有 2 个（0.4）还是 1 个（0.2）挤进 top 5；其余 6 条查询五个策略完全相同（recall 全 1.0）；
2. **precision@5 反而分得开**：本项目 0.800（= `baseline-v3.json` 记录值），recursive 4000/200 与 token 窗口 0.743，
   recursive 1000/200 与 markdown-header 0.771；本项目 `Q3/Q6/Q7` 的 precision 是 0.6–0.8，说明"检索到对的文件"不等于"片段都在这一节"；
3. **本项目这一行是对着真实索引校验过的**：把五个策略分别写进同 schema 的独立 SQLite 后，
   本项目那份库的 `chunk_id` 集合（1013 个）与文本**逐条等于** `.tmp/retrieval/index.sqlite3` 的真实索引，
   指标也与 `baseline-v3.json` 的 fts5 记录逐项相等（hit 1.0 / support 1.0 / precision 0.800 / recall 0.914286）。

口径命令：`python .tmp/chunking-report/retrieval_metrics.py`（每个策略一个独立库，口径直接复用
`tools/retrieval_eval.py` 的 `evaluate_method`；不写 baseline、不动真实索引）。

## 6. 结论与建议

### 6.1 建议采纳

| 优先级 | 变更 | 依据 | 成本/风险 |
| --- | --- | --- | --- |
| **P0** | **已修复**（`CHUNKER_VERSION = markdown-sections-2`，2026-09-23）：`_pack()` 的段落超预算分支改为调用 `_split_prose()` 并**原样透传** `truncated / original_chars`，`_prose_pieces()` 已删除 | 本仓库自己的不变式"丢了多少必须能算出来"被破坏；实测（§7）已发生 2 次：DORA 的 1253 字符长行丢 **44** 个非空白字符、OWASP 的 1218 字符长行丢 **17** 个，run 报告却写 `truncated_chunks=0` | 已付：修复 + `tests/unit/test_chunker.py` 新增 4 条单元测试（长行句读拆分无损、拆不动的单元如实记账、CJK 句读、段落内单行超预算），`python -m pytest tests/unit/test_chunker.py -q` → 25 passed |
| **P1** | **已随 P0 一并解决**：句读兜底在 `markdown-sections-2` 里就是主路径——`SENTENCE_END_RE` 覆盖英文 `.?!`（后跟空白）与中文 `。！？；…`，切点后还要过字素簇检查，只有"再也拆不开的单元"超硬上限才截断 | 本语料最长单行 1253 字符（英文，触发过 P0）；中文文档常整段无换行，是**系统性**问题。外部三家都把 CJK 标点放进分隔符集（LangChain 官方建议、Chonkie `zh` 配方、LlamaIndex `secondary_chunking_regex` 默认含 `。？！`） | 已付：无损（切点落在句读上，片段是原文的连续子串），ID/哈希语义不变；`test_cjk_long_line_is_split_at_cjk_punctuation_without_loss` 守着 |
| **P2** | 若出现"答案跨片"的失败样本，做**同章节邻片/父块扩展**（命中 child → 用整节或相邻 `part_index` 补齐） | LlamaIndex `HierarchicalNodeParser + AutoMergingRetriever`（`simple_ratio_thresh=0.5`）是成熟做法；本项目已有 `heading_path`/`part_index`/`ordinal`，不需要新基础设施 | 中：改召回层，不改切分；当前 support@5 = 1.00，**没有证据支持现在做** |
| **P2** | 引入 embedding 时再评估 **token 预算 / late chunking** | LangChain 用字符、LlamaIndex 用 token、Docling 用实际 embedding 分词器计预算 | 现在就改没有收益（FTS5 无 token 概念，Context 预算本身就是字符） |

### 6.2 明确不采纳

| 不采纳 | 理由 |
| --- | --- |
| 语义/LLM 切分（SemanticChunker、SemanticSplitter、Slumber、Neural） | 学术证据显示收益不稳健且真实文档常被固定长度反超；需要模型依赖，违反核心层"只依赖标准库/pydantic/PyYAML"的约束与失败关闭要求；边界随模型版本漂移，破坏"相同输入相同结论" |
| 盲目加 overlap | Context 层按 `text_hash` 去重，重叠文本会被判重丢弃；且"每个字符只落进一个 chunk"是增量 diff 与无损不变式的基础 |
| 用内容哈希当 chunk ID | 内容一改 ID 就变，规则溯源会断；本项目"位置 ID + 内容哈希分离"更适合"文档 → 规则"的溯源语义 |
| 让框架接管索引/增量 | 外部框架的 docstore/upsert 解决的是"向量库同步"，本项目的需求是"重建幂等 + 删除失效 + 溯源级联"，已有闭合实现与测试 |
| 摘要层（RAPTOR 式） | 实测报告约 4% 摘要含幻觉；治理语料不得改写 |

### 6.3 本项目已经领先的地方（对照外部默认）

- **位置稳定 ID + 内容哈希 + `revision`**：外部默认没有（§2.4 结论 1）；
- **围栏原子 + 章节边界 + 预算三者同时成立**：外部通常只有其中一两项（MarkdownHeader 有边界无预算，
  Recursive 有预算无边界）；
- **截断/超长/空章节/漂移全部计数进 run 报告**（§7 那处缺陷已在 `markdown-sections-2` 修掉）；
- **规则溯源表**（`rule_sources`）与隔离清单（`quarantine`）在主源框架里没有对应物。

## 7. 曾经的缺陷：一处**静默截断**（已修复：`CHUNKER_VERSION = markdown-sections-2`）

> 本节保留修复前后的完整历史证据。上一版把它写成"待修"；2026-09-23 已修，验收证据在下面的"修复后"一段。

**现象（修复前，`markdown-sections-1`）**：`docs/mirrors/dora-capabilities/core/continuous-integration.md` 里有一行 1253 字符，
大于 `max_chunk_chars=1200`。索引后该行**只留下前 1200 字符**，所在 chunk 的 `char_count=1200`、`truncated=0`、
`original_chars=NULL`；全库 `truncated=1` 的 chunk 数为 0，run 报告写 `truncated_chunks=0`。**53 个字符无记录地消失。**

**同一根因的第二处**（上一版只报了 DORA 一处，逐篇复核时才发现）：
`docs/mirrors/owasp-cheatsheets/06_授权与访问控制/Authorization_Cheat_Sheet.md` 的 1218 字符长行（所在段落 3252 字符）——
截到 1200，丢 18 个原始字符，同样 `truncated=0`。

**根因**：`src/retrieval/chunker.py` 的 `_pack()` 在"单块超预算的段落"分支调用 `_prose_pieces()`，
而 `_prose_pieces()` 只返回文本、**丢掉了 `_split_prose()` 返回的 `(text, truncated, original)` 三元组**；
随后的 `emit(..., truncated=False, original=None, ...)` 把这次截断硬写成"没截断"。
（代码块路径不受影响：超硬上限的代码块走另一分支，会正确记录 `truncated + original_chars`。）

**为什么没有测试拦住**：无损不变式 `blocks_are_preserved()` 只在单元测试里被调用，
**索引运行期不校验**；测试夹具也没有"单行 > `max_chars`"的用例。

**影响面（修复前）**：当前语料 2 行，去空白口径是 DORA 段丢 **44**、OWASP 段丢 **17** 个非空白字符；
中文语料"整段无换行"会**成片触发**——与 §6.1 的 P1 是同一个根因。

**修复**（`markdown-sections-2`，2026-09-23，就是把上一版的两条建议一起做掉）：

1. `_pack()` 的段落超预算分支直接调用 `_split_prose()`，把 `truncated / original_chars` **原样透传**进 `emit`；
2. 同一分支先按**句读**切分（原 §6.1 P1），只有"再也拆不开的单元"超过硬上限才截断并记账；
3. `_prose_pieces()` 删除（它唯一的作用就是吞掉那两个字段）；
4. `tests/unit/test_chunker.py` 新增 4 条测试：长行句读拆分无损、拆不动的单元如实记账、CJK 句读、
   段落内单行超预算——`python -m pytest tests/unit/test_chunker.py -q` → **25 passed**。

**修复后（实测，2026-09-23）**：

| 文档 | 修复前（`markdown-sections-1`） | 修复后（`markdown-sections-2`） |
| --- | --- | --- |
| DORA `core/continuous-integration.md` | 15 片；长行截到 1200，丢 44 个非空白字符；`truncated=0` | **16 片**；长行拆成 1172 + 81 两片，丢 **0** |
| OWASP `06_授权与访问控制/Authorization_Cheat_Sheet.md` | 41 片；段落被截，丢 17 个非空白字符 | **40 片**；段落拆成 1155 + 1132 + 964 三片，丢 **0** |
| 全库（42 篇） | —— | `truncated=0`；42 / 42 篇 compact 口径逐字相等 |

**两行长行都能逐字拼回**——注意这里必须换口径：修复后它们**落在多个片段里**，"整行出现在某一单独片段内"这个旧判据
现在必然为假。正确判据是：`split_front_matter` 取正文后，长行的**去空白**形式是"该文档全部 chunk 按序拼接文本"的
**子串**。实测：DORA 那行由第 7、8 片共同承载（1172 + 81 原始字符；去空白 998 + 67 = 1065 = 整行去空白长度），
OWASP 那行跨第 22、23 片（1155 + 1132；之后第 24 片是段落的第三片）。命令：`python .tmp/chunking-report/verify.py`。

**还剩什么没变**：无损不变式 `blocks_are_preserved()` **仍然只在单元测试里被调用**（`grep blocks_are_preserved src/`
只有定义处），索引运行期依旧不校验——本轮的 42 篇逐篇核验是一次性脚本做的（§8）。这一条记成**已知边界**，不是已解决项。
