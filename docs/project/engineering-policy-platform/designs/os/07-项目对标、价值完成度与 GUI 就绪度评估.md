### 1.4 诚实定位

**行业 commodity（不应作为卖点）**：策略引擎与规则语言（OPA/Cedar/Cerbos）；Hook 阻断契约（`exit 2` 是 Claude Code 既有语义）；审批 / 指纹绑定 / 追加写审计 / 摘要链（jev-proxy、Bernstein、in-toto 更早更完整）；代码检查器（Ruff / mypy / Semgrep / Checkov / Trivy，证据交换有 SARIF）。

**组合差异点**（单点都不新，串起来未见对手）：

```text
镜像文档 ──(显式、可评审的提炼；source.path 必须真实存在；chunk 必须可解析)──> 43 条规则
  └─ 每条 standard 规则必须带正反例夹具，且走真实验证器流水线（good 不中 / bad 必中）
      └─ 判定只有 policy.engine.evaluate 一条路径（三值 + skipped_rules 显式记录"没证据"）
          └─ 验证器只产证据、不判定；关键验证器不可用 → critical 阻断
              └─ 受控执行：action_hash 绑参数+主体+权限+上下文，审批一次性，台账+审计链双拦重放
                  └─ 多 Agent：能力声明是数据 + 已审核哈希；拦不住写类动作 → read_only，绝不"跳过治理"
                      └─ 写入前 Hook（exit 2），失败关闭由 Hook 自己兜底
```

**未找到对标（"没找到" ≠ "不存在"）**：① 能力上限由已审核哈希的声明推出（`src/adapters/models.py:142-174`，Lead 已核）；② 「没有任何验证器为某 checker 供证」本身是一条 violation；③ 规则必须声称真实存在的本地文件 + 可解析到 chunk，否则只能停在 Curated Guidance；④ 审计链**主动声明自身不可防的攻击面**（"这是摘要链不是防篡改日志"）。

**一句话定位**：本项目不是"更好的策略引擎"，也不是"更好的 Agent 护栏"；它是**把规范性文档转成带溯源的可执行规则、并让这条规则在唯一判定内核与受控执行链上失败关闭地生效**的平台——最稀缺的不是任何单点机制，而是**「声明与能力必须一致，对不上就降级而不是放行」这条贯穿全链的纪律**。

### 1.5 检索方法与局限

- 6 轮 24 条中英文 query；**Lead 亲自复核**了上表 5 个仓库：`raw.githubusercontent.com/<owner>/<repo>/main/README.md` 全部 **200** 且正文与描述一致。
- **不可核**：`github.com` 与 `api.github.com` 在 `web_fetch` 下报 "resolves to a non-public IP"，**星数与活跃度一律不可核**；只读了 README，**未审源码**，所以"核心机制"属**对方自述**。
- 对老牌 / 商业产品（Terraform Sentinel、AWS Config、Azure Policy、Backstage）召回为空，属检索局限。
- 学术侧：Prose2Policy（arXiv:2603.15799）摘要已核实但**未找到公开代码仓库**；FSE 2026 的 *Still Manual?* 只见到标题，**未打开原文，不作为事实使用**。

### 1.6 最该补的两件事（对标给出的）

1. **observe / dry-run 模式**：策略照跑、deny 全降级为 warn（抄 dsh 生态护栏）——今天没有这个模式，导致"先观察再收紧"没有中间档。
2. **审计链 opt-in HMAC + 离线 verify**（抄 Bernstein）——今天的摘要链自己承认"删尾或整链重写发现不了"。

## 2. 问二：主要价值、完成度，以及"能否 100% 遵守执行"

### 2.1 转化率：先给五个口径（Lead 独立复算，与会话/报告逐字一致）

**Lead 当场复算**（2026-09-25，命令见 §5）：`docs/mirrors/**` = **284 篇**（6 套镜像：dotnet 51 / owasp 142 / dora 39 / gitlab 22 / google 16 / pep 14）；`policies/**` = **43 条**，其中 `source.kind: standard` **38** 条、`project-policy` **5** 条；17 篇来源文档的 `source.path` 全部 `isfile=True`。

| 口径 | 分子 / 分母 | 转化率 | 说明 |
| --- | --- | --- | --- |
| **篇 → 规则**（会话与报告用的口径） | 17 / 284 | **5.99%** | "多少篇文档产出了规则" |
| 字节 | 369,686 / 4,067,028 | 9.09% | 被覆盖正文的体量占比 |
| 行 | 4,679 / 52,972 | 8.83% | 同上，行口径 |
| **章 → 规则**（全库，会话没有） | 38 / 4,658 | **0.82%** | 用仓库自己的 `retrieval.chunker.find_sections` 数出全库章节数 |
| **章 → 规则**（仅 17 篇来源文档内） | 38 / 442 | **8.60%** | 剔除"根本没打算转"的文档后的口径 |
| `rule_sources` 实际指到的章 | 30 / 4,658 | 0.64% | 登记了溯源、且能解析回来的章 |
| 需求级（强情态 + 代码锚点句） | 38 / 141 | 26.95% | **不可核**：分母依赖一套情态词正则，会话未留可复跑脚本 |

**读法**：这五个数没有一个是"错的"，但它们回答的是**不同的问题**。要说"转化率"就必须先声明分母——**5.99% 与 26.95% 之间差的不是精度，是定义**。

### 2.2 "没转化"不是一件事——它有三种完全不同的原因

| 原因 | 规模 | 性质 |
| --- | --- | --- |
| **既有规则已承载**（重复） | Google 16 + GitLab 22 + DORA 39 = **77 篇** | **不是不可行**。那些要求已被 `TESTING-001` / `TESTING-002` 等承载，再写只会得到语义重复、级别各异的规则——这正是约束 40 要避免的 |
| **精确率不够 / 需要上下文** | OWASP 127/142 停在 Guidance | 可解一部分：先修误报再扩面 |
| **语言门** | .NET 51 篇 | 平台今天只有 `python` 一种语言（`validation/project.yaml:9-13`） |

**所以 5.99% 同时低估又高估**：低估（77 篇是"不需要转"）、高估（.NET 那 51 篇是"转不了"）。把三种原因混在一个百分比里，会得出错误的结论。

### 2.3 主要价值（每条带可核实落点）

1. **"没有结论"是一等公民**：`skipped_rules` 逐条带原因、退出码 0 ≠ allow、超时 / 503 / 504 / 429 / 未评估全部是"没有结论"（`src/policy/engine.py` 三值 + `skipped`）。同类项目里这是最容易被含糊掉的一层。
2. **验证器与判定**权责分离：验证器只产证据，判定权唯一归引擎；**"没有任何验证器为某 checker 供证"本身就是一条 critical violation**（`src/policy/engine.py:142-149`）。
3. **受控执行链闭合**：`action_hash` 绑参数 + 主体 + 权限 + 上下文；授权一次性；台账与审计链**两处**拦重放；注册表是数据且有已审核哈希（改注册表必须重新审核）。
4. **能力上限由声明推出**：`post_only` / 未声明 pre-hook ⇒ 降级 `read_only`，受治理写动作得 `capability_unavailable`，**绝不"跳过治理"**（`src/adapters/models.py:142-174`）。
5. **规则的来源必须可核**：`source.path` 必须指向真实本地文件、chunk 必须可解析，否则只能停在 Curated Guidance；`standard` 规则必须带正反例夹具并走真实验证器流水线。
6. **文档对自己的攻击面诚实**：审计链明说"是摘要链不是防篡改日志"；覆盖报告 §9.2 自己列出"读者会误以为没报=没问题"这类缺陷。

**价值成立的前提**（必须一起说）：① 有人先把规范**显式提炼**成规则（这是**设计上唯一的人工步骤**，不是缺陷）；② 被执行的条款属于"**可确定性判定 ∩ 有证据源**"的交集；③ 装配侧愿意提供判定所需的维度（不给 `operation`，两条 TESTING 规则会被**跳过**而不是失败关闭——"判定存在 ≠ 判定生效"）。

### 2.5 真给一份企业内部开发规范文档，能否 100% 遵守执行？——**不能**

**能力地板（Lead 已独立复算）**：6 个 checker（`forbidden_dependency` 1 条 + 证据类 5 类）；6 个 scope 维度但**实用只有 3 个**（language 43 / layer 1 / operation 2）；4 个 severity（error 24 / warning 19）；**1 种语言（Python）**；**`style_lint` 39 条 = 90.7% 全部押在同一个外部二进制 `tool.ruff` 上**。

**第一道折扣：覆盖率**
- **代码类条款 ≈30%（估，区间 25%–40%）**；
- **全文口径 ≈12%（估，区间 10%–15%）**（流程 / 组织类条款占非转化理由的 **38.6%**，是最大一类）。
- 方法与局限：拿不到真实的"企业内部规范文档"，改用仓库**已完成的 284 篇逐篇非抽样走查**作代理样本；**这是估计，不是实测**。

## 4. 三问连起来看：这套东西现在的真实位置

1. **它不是一个"更好的策略引擎"，也不是唯一的 Agent 护栏**——六个能力面每一个都有对标，其中两个是 commodity。它的稀缺性在于**组合**与**贯穿全链的一条纪律**（声明与能力必须一致，对不上就降级而不是放行）。
2. **它的输入端是受限的**：文档→规则这条链只能覆盖规范里"可确定性判定 ∩ 有证据源"的那一部分（估 12%–30%），而且就在这部分里精确率也不高（误报 73% 量级的安全命中、两条已上线规则互相矛盾）。**这不是实现不到位，是问题的性质**——三类障碍里有两类是结构性的。
3. **它的输出端还没上线**：GUI 今天连一次可信的重建都做不到，而这条链**没有任何门禁**。但好的一面是：**阻断面全部集中在生成器与前端守卫，不在平台内核**——内核的自动化程度（唯一判定入口、原子加载、受控执行、四条闭环全过）足以支撑 P0/P1 只读操作台。

**所以对"要不要进入 GUI 阶段"的答案是**：**要，但顺序不能反**——先做 G-1…G-5（它们是 P-1 的收尾），再做 P0 只读面；**不要**在没有失败关闭的生成器上叠一个新的、更好看的界面，那只会把"不可信"包装得更容易被相信。
