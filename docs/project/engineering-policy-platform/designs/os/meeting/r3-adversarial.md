## A. 是否还有地方引入第二判定（含间接）？

### R3-A1【阻断】03 §7 的绿色门槛在**正常 API 调用路径**上可以被满足，而 41/44 条规则从未被评估

- **攻击步骤**：实现者照 03 §7 第一段写渲染函数——`allow` 且 `matched>0` 且 `every(skipped_rules[].reasons)` 非空 且请求带 `include_evidence=true` → **绿**「本批规则判定通过」。
- **证据**：
  1. src/policy_api/runtime.py:540 的判定调用是 `evaluate(rules, context)`，**不传 evidence**；
  2. src/policy/engine.py:129-136：`bundle is None` 且 checker 不属于 `CONTEXT_CHECKERS`（= 仅 `forbidden_dependency`，src/policy/checkers.py:30）的规则不进评估，改记 `extra_skipped`，原因文案见 engine.py:59-62；
  3. R5 实测（与 runtime.py:540 同一调用形态）：**allow / matched=1 / skipped=43 / 其中 41 条是"需要验证器证据"** → 绿门槛求值 **True**。
- **后果**：界面会打出一个**假的绿色结论**——它不是文案错，而是**门槛的充要条件不成立**：本批 6 个 checker 里有 5 个的证据类规则一条都没跑，界面却说"本批规则判定通过"。这是本设计最高红线（skipped ≠ 通过）最隐蔽的一种形态。
- **最小修法**：绿色门槛再加一条硬条件——**没有任何 `skipped_rules[].reasons` 命中"需要验证器证据"**（等价地：本批命中的证据类 checker 必须被 report 的 `served_checkers` 覆盖）。若不愿在前端做中文串匹配，就让后端在 summary 里多给一个布尔字段；在那之前绿只能退化为「上下文类规则通过，证据类规则未评估」。这条必须进 V4/V5 的断言。

### R3-A2【应收敛】03 §3 P2 的 `operation` 五值没有来源行号，与同页 `layer` 的处理不对称

- **攻击步骤**：照 P2 线框实现表单——`层[capability v] 语言[python v] 操作[edit v]`。`layer` 旁写了来源（`src/policy/check.py:77-92` 的 12 值 + unknown），`operation` 只写"五值"。
- **证据**：R6——`Operation` 在 src/policy/models.py:226-233，恰 5 值；03 §3 P2 的"元素与来源"只写"五值 `operation`"，未给 file:line。
- **后果**：实现者只能**抄一份枚举**——这正是我 R1 X7 / D7 要禁的那类缺陷（生成器抄 severity 四值 → 后端扩张即静默不一致）。今天的操作台原型 `build_site.py:41` 就是这么坏的。
- **最小修法**：把 `operation` 的来源补成 `src/policy/models.py:226-233`，并写一句"该枚举必须由后端只读接口提供（G3/G5），不得在前端转抄"。

## C. 失败语义的缝：超时 / 空壳 / skipped / 未核对 / capability / evidence

### R3-C1【阻断】D4 的三态措辞自相矛盾，且**同一句错在三份文档里**

- **攻击步骤**：按字面实现漂移门禁。
- **证据**：R10——02:110"三态固定为 **未核对 / 已核对且一致 / 已核对且漂移**；**前两态**都**不构成"可以提交"的依据**，只有"已核对且一致"才能进入提交节点"；03:19（I6）同句；04:78（D4 裁决）同句。按列表顺序，"前两态" = 未核对 + **已核对且一致**；于是同一句话前半说"已核对且一致"不可提交，后半说"只有它才能提交"。
- **后果**：两个方向的坏结果都真实：① 实现者按前半实现 → **提交路径永久不可达**（P2 期废掉，而且是"看起来在保护"的废掉）；② 实现者按后半实现并自行"修正"措辞 → 漂移门禁被软化，未核对可以提交，D4 的整个裁决落空。
- **最小修法**：三处一律改成显式枚举——"**只有"已核对且一致"可提交；"未核对"与"已核对且漂移"均阻断**"。这是全文最便宜、收益最高的一处改写。

### R3-C2【应收敛】绿色门槛的措辞在 JS 语义下会**空集为真**

- **证据**：03 §7 写 `every(skipped_rules[].reasons)` 非空。JS 里 `[].every(p) === true`；若后端返回 `skipped_rules=[{rule_id, reasons: []}]`，门槛会**放行**到下一条件。今天我实测"空 reasons 的跳过 = 0 条"（R5），所以这是**未来的**缝，不是今天的洞——engine.py:105 用 `result.failures` 填 reasons，正常路径非空。
- **最小修法**：把条件写成"`skipped_rules` 非空当且仅当 `summary.skipped > 0`，且**每条** `reasons.length >= 1`"，并写进 V4/V5 的断言。

### R3-C3【可接受】其余六条失败档位都能被实现者正确落地

我逐条攻击过：超时（504 → 中性"没有结论"，03 §7）、503 依赖不可用（含 `audit_unavailable` 的 `retryable=false` 特例）、429、**空壳重放**（03 §7 单列一行"没有结论：这是幂等重放的空壳" + 换新键，02 §1-G G10 同步）、`skipped>0` 但响应无 `skipped_rules` 键（03 §7 单列"未请求证据明细"，U4 同规则）、**未核对**（03 §7 + I6 + V7 阻断提交）。
六条里没有一条能被渲染成绿。**唯一真正的缝是 R3-A1**——它不在表里，而在门槛的充要条件上。

## D. B1 / B2 / B3 是否被软化？

### R3-D1【阻断】03 把 `precheck` 写成"提交"的替代命令——这正是 B1 的软化形态

- **攻击步骤**：用户在 P3「受控执行」标签点灰掉的提交，读到替代命令 `python -m enforcement.cli precheck`（03:150）；在 P8 读到同样的替代（03:269），照着跑。

## E. 页面是否有越权或说假话的地方？

## 3. 如果只能改一处

**改 03 §7 的绿色门槛（R3-A1）。** 理由不是它最容易改，而是**只有它会让系统主动产出一个错的结论**：

- R3-C1 的字面实现会**挡住**一条合法路径（失败关闭方向，保守）；R3-D1 会让用户误解一次操作（可诊断、有审计）；两者都是"人还能发现"的问题。
- R3-A1 反过来：界面会打出**绿色**，而本批 6 个 checker 里有 5 个从未运行。这个绿点会被写进截图、周报、上线记录——它是这台「OS」唯一承诺过的东西（不撒谎、不把没跑的说成跑了）被自己破坏的形态。
- 而且它的触发条件不是边角：`/v1/policy/evaluate` 今天**恒不传 evidence**（runtime.py:540），所以只要上下文让 `forbidden_dependency` 命中一次，绿门槛就成立。**默认路径即漏洞。**

**修法（一行）**：绿 = `allow` 且 `matched>0` 且 `include_evidence=true` 且 `summary.skipped == 0` 或所有 skipped reasons 均**不含**证据缺失文案；并把这一条同时写进 03 §9 的 V4/V5。
