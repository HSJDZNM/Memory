### 3.4 最重要的结构性问题：P2 判定工作台的常态是"没有结论"

这是本轮最重要的一条设计发现，Lead 已逐行核实：

```python
# src/policy_api/runtime.py:539-540  —— evaluate 路由
def work() -> ValidationResult:
    return evaluate(rules, context)          # ← 没有 evidence

# src/policy_api/runtime.py:779  —— validate 路由
result = evaluate(rules, context, evidence=report.bundle) if request.include_decision else None
```

`src/policy_api/models.py:288`：`include_decision: bool = True`（默认就带判定）。

后果链条：

1. P2 走 `POST /v1/policy/evaluate` → 不传 evidence；
2. 6 类 checker 里 **5 类是证据类**（`src/policy/checkers.py:33-35`）→ 整批进 `extra_skipped`，原因写"需要验证器证据"；
3. 03:343 的第 ⑤ 条与 03:356 明确规定：**出现"需要验证器证据"类跳过 → 一律渲染中性灰「没有结论：N 条规则未评估」**；
4. 于是 **P2 的常态不是 allow、不是 block，而是"没有结论"**。

而**带证据的判定在 API 层今天已经可达**：`POST /v1/validation/evaluate` 先跑验证器流水线、再判定，`include_decision` 默认 true，两个租户的 `validation_root` 都已配置（`api/policy-api.yaml:56,77`）。

> **措辞更正（2026-09-25 外部独立评审提出，Lead 采纳）**：本节初稿写的是"带证据的判定今天已经可达"，容易被读成"控制台今天就能给出真结论"。**准确说法是：API 能力可达，控制台尚未接入**——`app.js` 里**没有任何** `/v1/policy/evaluate` 或 `/v1/validation/evaluate` 调用，唯一的网络请求是 `health/live`（`app.js:394-419`，Lead 已复核）。所以本节说的是**可实现性**（方案 A 的代价因此是"接线 + 表单"），不是"今天已经能用"。

**三个可选方案与代价**：

| 方案 | 改法 | 代价 / 风险 |
| --- | --- | --- |
| **A（建议）** | P2 默认走 `POST /v1/validation/evaluate`（带证据），并把"仅上下文判定"作为第二个显式选项 | 预算从 evaluate 级升到 validate 级（10s）；页面必须显示"跑了哪些验证器、哪些不可用"（C12 失败关闭） |
| B | P2 保留两条路，默认"两条并排" | 首屏认知负担增加；违反"一句话能懂" |
| C | 不改路由，页面照实显示"没有结论" | **合规但无用**：最高频页面永远给不出结论，新人第一次用就学到"这平台什么都不说" |

**这条同时解释了为什么"给新手一个结论"与"不给假绿灯"不矛盾**：不是把灰色涂绿，而是**换一条真能出结论的路**。这是本轴唯一一处"改一处、收益最大"的地方。
