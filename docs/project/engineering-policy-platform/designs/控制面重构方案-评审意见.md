# 《控制面重构方案》评审意见

评审对象：`docs/project/engineering-policy-platform/designs/控制面重构方案.md`（与上传件逐字节相同，当前为未跟踪文件）
评审方式：对照 2026-09-28 的工作树逐条核对方案中的「现在是这样」断言，再看设计本身的自洽性。未跑门禁，未改任何仓库文件。

## 总体结论

诊断部分质量很高：「平台没有把自己纳入它强加给别人的纪律」这个母体判断有说服力，34 条问题的分桶、红线可证伪化、认输与分歧留档都做得扎实。建议**有条件通过**：设计方向可以接受，但在台阶 0 之前有三件事必须先做（见 §1），另有几处设计缺陷需要在落地前修正（见 §2）。

## 1. 阻断级：落地前必须先处理

### 1.1 前提读数针对的是旧内核，需要在当前树上重采

方案的核心前提「判定内核 0 缺陷、30 臂 248 检查 0 偏差、11 fixture 逐字段全等」来自 round-09 / round-10 的树。但当前工作树里 `src/policy/` 有 7 个文件未提交修改（+608/−40 行），其中 `engine.py` 的 `evaluate` 已经新增了 `pending_for` 分支，`checkers.py` 新增了 `pending_implementation_violation`。也就是说，**§8「不动 `policy.engine.evaluate` 的判定路径」这条承诺在方案落盘前就已经被树外写者打破了**，而 §0 的「内核健康」读数不覆盖这次改动。

建议：把「在当前树上重跑 30 臂矩阵 + 11 fixture，钉 `pre_tree` 摘要」作为台阶 −1，结论不成立就先回到诊断。

### 1.2 基线不稳：大量已落地工作没有提交

`git status` 显示 92 个路径变更（65 个已跟踪文件 +6286/−249 行，另有 27 个未跟踪文件，包括 remediation 12–15 四份修复轮文档和本方案自身）。更关键的是：**AGENTS.md 在 HEAD 里只有第 1–40 条，第 41–54 条全部是未提交内容**。方案 §10 第 1 条、附录 B D12 把第 51 条当作「已成为编号契约」来处理，但这份契约目前只存在于工作区。

这直接影响 J2 与 R-d：「禁止同轮重记基线」「先出字段级差集」都需要一个可复现的 pre 基线，而现在的 pre 是一棵随时在变的未提交树。

建议：先把树外写者的修复轮按轮次拆成独立提交（每轮一个 commit 或一个分支），让 HEAD 成为台阶 0 的基线；`platform_revision` 在 git 仓库里直接取 `commit + 声明范围内的 dirty diff 摘要`，比自造摘要更便宜也更可信。

### 1.3 并发写的根因应当用隔离解决，而不是只做检测

附录 C 的三个现场事件（50 个文件被并发写、针脚 30 秒过期、round-15 命名空间被共用）都指向同一件事：多个会话共写一棵工作树。方案的回答是封条（检测）加写权租约（台阶 4 才出现）。封条只能事后宣布「本轮作废」，不能防止作废；而写权租约排在台阶 4，意味着台阶 0–3 全部在无排他的环境里验收，每一步都可能被 `external_write` 打回。

建议：把隔离提到台阶 0 之前，且优先用零源码成本的办法——每个会话一个 `git worktree`（或独立克隆），`.tmp/round-NN/` 目录名带会话 ID 并在创建时做独占检查。封条保留，但定位为「隔离失效时的兜底」，而不是主机制。

## 2. 设计缺陷：建议落地前修正

### 2.1 义务「按方向判一次性」与 J1 冲突

§3.3 规定 `missing_targets` 持平或扩大即 block（`pending_not_renewable`）。但正常的测试先行流程里这两种情况都很常见：实现未写之前再改一次测试文件（持平），或者给测试加一个引用新名字的用例（扩大）。按这条规则，这两步都会被拦，而 J1 的目标恰恰是「先写测试、再写实现不再被平台惩罚」。

另外键里带 `session_id`，新会话会把义务清零，「拼错的 import 永久待实现」的问题只是从会话内挪到了跨会话。

建议：会话内不以方向判罚，只记账（计数 + 年龄 + missing_targets 快照）；判罚集中在本机门禁（这与 §10 第 2 条「判罚在本机门禁」一致，避免会话内与门禁双重判罚）。「拼错的 import」由门禁上的 `obligations_open == 0` 兜住，并且义务账按 `(rule_id, target, missing_target)` 跨会话持久化。

### 2.2 状态代数缺少与现有状态的映射表，有成为「第五种表示」的风险

当前代码里已经有多套「没判/没查」的表示：`skipped_rules` + reason、`Blocker`（validator status）、`ValidatorStatus.PENDING_IMPLEMENTATION`、`language_coverage.status = not_covered_by_design`、`check_volume.skipped_by_reason`、`CheckerJudgement(JUDGEMENT_EMPTY)`。§3.3 的 `(verdict, reason)` 是一个更干净的模型，但方案没说它存在哪（决策协议保持 1.0，那就只能在审计里？），也没给出从上述六种表示到新代数的映射。

按方案自己的母体判断，「再加一种表示而不收编旧的」就是复发。建议补一张映射表：每种现有状态 → `(verdict, reason)`，并写明哪些旧字段在 1.1 里变成派生字段、由同一函数产出。

同一节的「未知 reason 一律 block」会改变 decision，应显式纳入 R-d 的差集要求。

### 2.3 R-e 的「读过的文件集合」在纯标准库约束下不可实现

`referenced_files_digest` 要求记录判据**实际读过**的文件。检查会调起 pytest、ruff、mypy 子进程，它们各自做 import 解析和配置发现，用纯标准库无法可靠观测这些读取；做到了也是另一套需要自证的仪器。

建议改为**声明输入**（构建系统的做法）：每条检查声明输入范围，封条覆盖声明范围；声明不足由沙箱暴露。仓库里已经有现成载体——`pre_evidence` 本来就在影子树副本上跑，影子树就是天然的「判据级输入集合」，它已有 `_tree_digest`。门禁侧可以用干净的 worktree 达到同样效果。

### 2.4 `worktree.py` 放在 `src/policy/` 与 J2 正面控制相互干扰

J2 的正面控制是「故意在 `src/policy/` 改一行必须变红」，而台阶 0 自己就要在 `src/policy/` 新增文件。如果 `platform_revision` 的声明范围包含 `src/policy/`，台阶 0 本身会触发内核漂移；如果排除 `worktree.py`，就出现了一个「在内核目录里但不算内核」的例外。

另外，现有唯一的树摘要实现 `src/adapters/dsh/pre_evidence.py:_tree_digest` 在 `OSError` 时**跳过该文件**，注释写明「指纹是标注，不是证据本身」。方案要把它升格为封条（证据），这个语义必须反过来：读不到 → `unprovable`，不能静默少算一个文件。「一份实现」需要显式区分标注模式与封条模式，或者只保留严格模式。

建议：把 `worktree.py` 放到内核目录之外（例如 `src/common/` 或 `src/provenance/`，同样纯标准库、不 import adapters），并在台阶 0 的测试里钉住「不可读文件 → unprovable」。

### 2.5 H4 是判定层的假绿，应当先于归因修

核对确认了 H4 的机制：`pytest_runner.py` 在退出码 5（没有收集到任何用例）时返回 `ValidatorStatus.OK`，`pipeline.py` 把 `OK` 视为成功状态并 `served.update(checkers)`，于是 `failing_tests` 被记为「服务过」，TESTING-002 在零个测试被执行的情况下判为通过。这会产出错误的 allow，性质比台阶 1 的「理由措辞错」更严重。

按方案自己的纪律（失败关闭先于理由正确），建议台阶 1 与台阶 2 对调，或者把 H4 作为不依赖任何新结构的独立小修先行（改动面预计很小，但会改变 decision，需要走 R-d 差集）。

### 2.6 退出码 2 语义过载

§5.3 用退出码 2 表示 `external_write`（本轮结论作废）。在本平台里退出码 2 已有明确含义：Hook 的 block（AGENTS 第 10 条）、`evidence_unavailable`、`startup_error`、`wiring_error`。门禁脚本不是 Hook，但读者和 `ci_local.py` 的调用方很容易混读。建议给「封条失效」一个独立退出码，或者在方案里显式列出门禁退出码表。

## 4. 可维护性与表达

证据不可持久：方案的全部证据指针指向 `.tmp/`，而 `.tmp/` 在 `.gitignore` 里，且 `tools/cleanup.py` 默认清理顶层 `.tmp/`。一次清理之后，这份放在 `docs/.../designs/` 下的长期文档就无法复核。建议把支撑结论的最小证据（矩阵摘要、PLAN-VERIFICATION 的偏差表、101 个文件的不一致清单）落进 `reviews/` 下已跟踪的目录，方案只引用已跟踪路径。

术语密度过高：一份 276 行的文档里同时使用 J1–J5、R-a–R-h、L1–L9、D1–D12、H1/H4/H5、W1–W3、A–E、N/M/P/Q 编号，其中 L1–L9 在文档内没有任何定义（要去 `.tmp` 里读裁决文件，而 L9 在那里也没有），H 系列只在台阶 2 里顺带说明。建议加一张术语与编号索引表，并把「针脚」「臂」「母体」这类研讨内部用语在首次出现时给出定义或换成仓库既有口径（`术语与口径.md`）。

成本与「不新增层」的张力：§8 说五件东西「没有新包、不新增层」，§7 估计新增 7,200–14,400 行源码加同量级测试，而最高频真样本是 27 行源码。两个数量级的差距说明估计还没有落到具体改动面上。建议按台阶给出估计，至少对台阶 0–2 给出基于文件清单的估计，这也能帮助判断最小可行子集是否真的「最小」。

## 5. 建议的落地顺序

1. 台阶 −2：会话隔离（git worktree + 轮次目录独占），零源码。
2. 台阶 −1：把树外修复轮拆分提交；在 HEAD 上重跑 30 臂矩阵与 11 fixture，钉摘要，确认「内核 0 缺陷」仍成立。
3. H4 独立小修（带 R-d 差集），先消除已知假绿。
4. 台阶 0（封条放在内核目录外，严格模式，声明输入）。
5. 台阶 2 其余部分（H1/H5）→ 台阶 1 → 台阶 3（义务按 §2.1 改为会话内记账、门禁判罚）→ 台阶 4 → 台阶 5。

每一步沿用方案已有的「红→绿 / 回退 / 分歧」格式，这部分设计本身不需要改。
