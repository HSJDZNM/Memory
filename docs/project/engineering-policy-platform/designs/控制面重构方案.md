## 0. 一句话

判定内核是健康的：34 条历史问题（N16–N28 / M1–M5 / P1–P8 / Q1–Q8）里 **0 条**的根因落在引擎上；
30 臂确定性矩阵 **248 条检查跨轮 0 偏差**，且被第二方用自己的运算符表逐条重算过。缺口的 **32/34** 长在**接缝**上，母体一句话：

> **平台把「它自己」——自己的配置、自己的失败、自己的状态、自己的覆盖——当成内部实现细节，
> 而它要求被治理者把这些东西当成一等数据。**

所以重构不是「再加一层」，而是**把平台自己纳入它已经强加给别人的三条纪律**：事实进数据、失败关闭、可证伪。
落地形态是**五件东西 + 八个台阶（−2 → 5）**；每步可独立验收、可回退，且不许踩 §5 的红线。

## 2. 母体：平台没有把自己当成治理对象

| 被治理者必须遵守 | 平台对自己 |
| --- | --- |
| 事实进数据（规则、注册表、语料都是 YAML） | 控制面的事实散在 YAML / hooks.json / profile patch / 环境变量 / 脚本常量 / 两门语言里，各有各的解析 |
| 失败关闭（未知一律拒绝） | 失败原因只有文本，且归因可以错；接线自检曾有「缺席即通过」的形态 |
| 可证伪（每条能力都要有会失败的检查） | 覆盖、接线、版本漂移、仪器自身，大量性质**没有任何检查承载** |
| 状态要显式（跳过 ≠ 通过） | 状态被折叠：同一名字两种意思、不同东西同一形态、缺键与 null 同形 |

## 3. 目标形态：五件东西（不是五个模块）

### 3.1 一套针脚（四个名字，一份实现）

| 名字 | 含义 |
| --- | --- |
| `evidence_tree_digest` | 取证时那棵影子树（AGENTS 第 48 条已有） |
| `referenced_inputs_digest` | 本次检查**声明的输入范围**（判据级封条） |
| `workspace_tree_digest` | 整个工作树（轮次级封条） |
| `platform_revision` | 产出这条判定的**平台代码**（范围由声明给出，不写死目录） |

- **一套函数实现**，落 **`src/provenance/worktree.py`**（纯标准库、不 import adapters）——
  **不落 `src/policy/`**：J2 的正面控制是「在内核目录改一行必须变红」，针脚实现自己坐在内核目录会造成自干扰（评审批次 1 §2.4）。
- **严格模式**：读不到的文件 → `unprovable`，**不许静默少算**。现有唯一实现 `pre_evidence.py:507` 是**标注模式**
  （原文注释：「读不到的文件不进指纹（权限 / 竞态）：指纹是标注，不是证据本身」）——升格为封条必须反过来。
- **两层封条都要**：判据级回答「结论有没有被我声明之外的东西污染」；轮次级回答「这一轮有没有未声明的写者」。不一致 → `invalidated`（不是 pass、不是 fail，门禁算红）。
- **判据级封条用「声明输入」而不是「实际读过」**：检查会拉起 pytest/ruff/mypy 子进程，纯标准库无法可靠观测它们读了什么；
  照「实际读过」写会造出第二件需要自证的仪器。声明不足由沙箱暴露，影子树与干净 worktree 是现成载体（评审批次 1 §2.3）。

### 3.2 一张检查登记表（facts + checks 合表）

落 `validation/control-plane.yaml`：
- **facts 段（9 字段）**：key / authority(canonical|observed) / canonical_ref / consumers / predicate / severity / remedy / on_unprovable / expires。**不放值**（限制只作用于本段）。
- **checks 段（8 字段）**：check_id / owner / command / covers / evidence_level / mutation_id / gap_note / severity。**只放指针**：出现 `last_run` / `status` / `passed` / `observed_*` 即加载期报错。
- **连接键** `facts.key ↔ checks.covers` **双向必查**；任一边悬空即红。给不出这条就拆回两张表。

### 3.3 一个状态代数（两维）+ 义务账

格 = `(rule_id@version, checker, target)`，在一次判定、一棵树、一个平台修订上取值：
`verdict ∈ {passed, violated, not_evaluated}`；`reason` 只对 `not_evaluated` 有值，且是受控集合：
`out_of_scope` / `missing_dimension` / `no_subject` / `no_provider` / `not_covered_by_design` / `blocked(kind)` / `pending_precondition`；**未知 reason 一律 block**。
**语义变化必须走 R-d**——「未知 reason 一律 block」本身就改变 decision。**台阶 3 的验收项**：补一张「每种现有状态 → `(verdict, reason)`」的映射表，旧字段降为派生、由同一函数产出。

**义务账（v2 修正）**：
- **会话内只记账，不判罚**：记 `(rule_id, target, missing_targets 快照, 计数, 年龄)`；正常测试先行流程里「再改一次测试」（持平）与「加一个引用新名字的用例」（扩大）都很常见，按方向判罚会直接拦掉正确写法（评审批次 1 §2.1）。
- **判罚集中在本机门禁**，且**跨会话持久化**（键 `(rule_id, target, missing_target)`，不含 `session_id`——否则新会话把义务清零）。
- 门禁声称 `obligations_open == 0` 时，必须同时给出「最近一次真实测试运行时间」；解除只由**一次真实 pytest 运行**判定，不许由账本推断。

### 3.4 一个归因闭集（+ 核验前置）

`origin` 是闭集（`platform.*` / `agent_runtime.*` / `host.*` / `project.*` / `unknown_origin`），每个 origin **必须**携带：
`owner` / `object{kind,value,source}` / `observation{method,result,verified,verified_at,run_scoped}` / `fix` / `causal_link(proven|unproven)`。**写不出 `fix` 的 origin 不许存在**。

**核验前置**：每条指控在写进理由之前先执行它的证伪判据（报「可执行文件不存在」先 `stat` 它；报「工作目录不存在」先判目录）。
核验允许证伪自己人——判据不成立时只能落到 `unknown_origin`，不许换一个对象继续指控。
三处伪造面同时处置：核验对象必须是模型**写不到**的东西；记 `verified_at` 与 `owner_note`；核验记录**无权威**，消费者不得据它 allow/block。

### 3.5 一份边界裁定 + 三数分离的报告

- **边界裁定**：把「平台治理受控会话、不治理使用者日常入口」这条**已经做出但只写在 CI 注释里**的决定（`.github/workflows/phase-8.yml:266-272`）提升为顶层契约。
- **载体** `adapters/wiring-scope.yaml`：`decision(in_scope|out_of_scope|expected_absent)` + `kind` + `owner` + `reason` + `consequence` + `expires_at` + `renewals`。
- **报告只报三数**（`discovered` / `declared` / `measured`）与**五个差集**：`discovered_not_declared`、`declared_not_discovered`、`in_scope_not_wired`、`out_of_scope_active`、`out_of_scope_expired`。
- **不许出现比例**：顶层只允许 `account` / `differences` / `channels` / `reading_context` / `headline`；计数一律整数、禁浮点、禁 `ratio`/`percent`/`coverage` 键名。

### 3.6 台阶 4–5 的前置评估：先问「能不能不建」（v2 新增）

台阶 4–5 是成本最高、最容易让「配置写错就起不来」的两步，也正是反方「收缩承诺面」最该用的地方。
**前置问题（用整数清单，不用比例——本方案禁止比例）**：这一步要建的东西，服务对象里 **已声明 `out_of_scope` 的有几个、在范围内的有几个**，两份清单都列出来。
**判据**：若某条检查的全部用途是「让一个已声明 `out_of_scope` 的对象不再红」，它属于收缩承诺面的工作，**不该建机制**（写一条声明即可）；只有当对象**在范围内**时，检查才有资格建。
**可证伪**：若评估结论是「全部该建」，必须交出「这些对象都在范围内」的清单；交不出，就必须有一部分降级为声明。
**边界**：收缩承诺面**修不了**「平台对自己的状态说假话」（H4 假绿、归因指错对象）——所以台阶 0–3 必修，4–5 先评估。

**冻结（D-2 裁定，2026-09-29，树 `6b3dd36`）**：台阶 4–5 **不排期**——先交本节要求的那**两份整数清单**（`out_of_scope`（已声明不治理）与**在范围内**，各列对象、取值与来源）。清单交出即**停**：评审通过之前不建任何机制（含「写一条声明」这类收缩动作）。
**为什么冻结而不是先收缩承诺面**：把「已声明 `out_of_scope`」的对象逐条写进声明表看似零成本，但那份声明的**真源**正是台阶 5 要合并的谓词；在合并规则未评估之前写它，等于把「配置写错就起不来」的风险提前引进门禁，而且清单本身还没有被评审过（本轮只交付清单，评估留到下一轮）。

**预算纪律（裁定日 2026-09-29）**：**每个台阶的上限 = 原估算 × 2.5**；**实测超过 1.5 倍就停下复核**——不继续往下做，先复核「为什么超、估的是什么口径」。
「原估算」以 §7 表内该台阶桶的**上限**为准，§7.1 的 ×2.5 表就是它的展开；**下限不动**（依据见 §7.1）。
**超过 1.5 倍时按什么读**：口径是「实测 / 原估上限」，**逐桶算、不取合计**（台阶 0 的 src 与台阶 2 的 tests 已经各自击穿过一次，见 §7.1）；**墙钟**（评审、复核、门禁重跑）不在 §7 的分桶里，因此「停下复核」不因墙钟触发，但墙钟仍要在归档里如实记。

### 台阶 −2 · 会话隔离（零源码，v2 新增）
**内容**：每个会话一个 `git worktree` 或独立克隆；`.tmp/round-NN/` 目录名带会话 ID 并在创建时做独占检查。

### 台阶 1 · H4/H5 独立小修（先消除判定层假绿，v2 前移）

**红→绿**：**R-f**——`served_checkers` 里的每个 checker 必须有**真实执行**的证据（`status ∈ {ok, findings}` 且**真实执行的用例数 ≥ 1**，或该次运行确实没有对象且由**验证器**给出对象判定）；**不允许检查自己用「显式 no_subject」改名修绿**。

### D-1b 的执行口径（台阶 3b，2026-09-29）

**为什么"升 `SCHEMA_VERSION`"就是裁定里那句"递增记录协议版本"**：三者被绑成一批（代码 / AGENTS
第 51 条 / 协议版本），而三件里唯一具备"协议"属性、且本次**字段真的变了**的落点就是决策载荷。
证据路径与四种 decision 逐条不变的证明见 13 号 §2.3；字段级差集与预注册形状见 13 号 §5.4。

**两个必须写进提交说明的后果**（13 号 §4.3 反驳 3 要求它们"说出来"，否则设计意图与意外副作用长得一样）：

1. **1.0 的决策载荷会被拒收**：`SUPPORTED_SCHEMA_VERSIONS` 只认 1.1，`parse_decision` 对 1.0

- **不新增 `not_evaluated` 状态值**：本裁定只把 pending 挪出 `violations`；状态代数（台阶 3 的另一半）
  不在本次授权内，义务账（3c）与 §3.6 评估留到下一轮。

  发生了什么"，本台阶改的是"判定载荷怎么表达它"。13 号 §1.2 已否决 T2（复用

- **不在 API 响应与请求级 JSONL 上加 pending 计数键**（13 号 B4 的"另加一个键"一半）：按第 55 条，

  `RequestLogEntry` 加键要递增 `REQUEST_LOG_SCHEMA_VERSION`；这两项破坏性后果**不在本次裁定的
  清单里**（裁定只列了决策载荷 1.0 与旧 checkpoint 两条），因此本批**停在门口并登记**，
  B4 的断言改为钉住现状（`summary.violations == len(decision["violations"]) == 0`
  且 `decision["pending_findings"]` 非空——pending 的可见性由**同一个响应体里的决策载荷**承接）。

  `tools/phase7_cells.py` 的两条生成期断言与手册重生成），要么把第 55 条的范围写成
  "只覆盖写侧载荷、读侧附加键不算"。

**这条事件的含义（口径写清，免得被读成两件事）**：**文件工具的拒绝不等于隔离**——同一个会话、同一个目标路径、同一个时刻，`write` 工具被拒而 `pwsh` 落盘成功（第 5 轮的原话是「通道之间也不一致」）。于是「文件工具被拒 → 换 pwsh」这条路径把改动写进了**会话工作区之外**的树，而**没有任何声明**记录过「本次写入的目标在工作区外」。这是**事实**；它算不算「绕过」，取决于把 DSH 的文件工具策略读成**约束**还是**单一通道的实现细节**——这里按前者记（W7），理由是同一次会话里找不到任何一条声明说「本次写入的树在工作区外」。它正是 §3.1 封条与台阶 −2 隔离要覆盖的那一类输入。
**处置（与 W6 同一口径）**：第 5、6 轮都没有改仓库的忽略规则、没有用 `git add -f`、也没有申请沙箱放宽；落树的改动全部是评审对象本身。**未核实**：只拦文件工具而不拦 `pwsh` 通道的强制点实现；以及第 6 轮是否重试过文件工具（没有读数）。

七件事是同一个机制：**没有声明、没有排他、没有显式拒绝**（W7 补上的那一半是「拒绝只在一条通道上生效」）。修法在同一份方案里：台阶 −2 隔离 + 台阶 0 封条 + `(claim, revision_pin, observed_at)` 三元组 + 针脚过期即失效。
