## 新问题（本轮最重要的读数）：**审批把 `exec.pwsh` 锁在一条命令模式上**

受治侧这次会话共发起 **3 次** `pwsh`：前两次 `approval_invalid`（`exit_code=2`），第三次放行并执行。

被拒的不是参数格（三次都是同样的 `command` + `description` 两格），而是**命令取值**。模型可见原文：

```text
check approval: approval_invalid 参数 'command' 的取值不匹配审批模式 '^python -m pytest( .*)?$'（整串匹配）：
参数一变旧授权自动失效；可用替代：注册表白名单允许的命令形态
```

被拒的两条命令是 `git diff -- tests/test_order_service.py` 与 `git diff`——**它们都在注册表白名单里**
（`^git (status|diff|log|show)( .*)?$`），但仍然过不去，因为 `exec.pwsh` 只有**一条**审批记录，而那条的模式是
`^python -m pytest( .*)?$`；同一个 `tool_id` 再签一条会**原地取代**（`--replace` 才是清空），所以「跑测试」与「查看」
**只能二选一**。

⇒ 对使用者的直接后果：**受治会话里命令类动作只跑得动一条命令模式**。
「跑测试」拿到了，「只读查看」（`git diff` / `Get-Content` / `Get-ChildItem` …）拿不到——
而使用者的原始约束恰恰是「**接受能自动跑测试 / 查看的命令**」。

（模型自己恢复了：它放弃 `git diff`、改用 `read` 工具看文件，最后跑 pytest 通过。所以这一条是**可用性缺口**，不是故障。）

### 三个处置选项（都要使用者点头，不在本计划内自动做）

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| ① 收窄期望 | 承认「GUI 里一个工具只能放行一条命令模式」，把只读查看交给 `read`/`glob`/`grep` 工具（它们本来就不需要审批） | 命令行的只读用法（`git diff`、`git log`）在受治侧不可用 |
| ② 放宽这一条模式 | 重签 `exec.pwsh`，把模式写成覆盖白名单里的只读族 + 测试族（例如 `^(python -m pytest|git (status|diff|log|show))( .*)?$`） | 一张条子覆盖多条命令；仍然是**人类签字**，外圈还有白名单兜底，但「一条命令一张条子」的姿态没了 |
| ③ 平台侧改协议 | 允许同一 `tool_id` 多条记录（按命令族各签一张） | 动审批协议，要走版本链（AGENTS 第 55 条） |

**登记**：这条补进 open-work 的 5.69（原来只写了「参数格」那一半，现在要加上「命令模式只有一条」这一半）。
