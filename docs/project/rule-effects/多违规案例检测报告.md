## 1. 被检案例全文

```python
import json
import logging

from shop.order_repository import OrderRepository
from shop.order_service import OrderService

LOGGER = logging.getLogger(__name__)

DEFAULT_PASSWORD = "shop-admin-2024"

STATUS_NEW = "new"
STATUS_PAID = "paid"
STATUS_MISSING = "missing"

MAX_PAGE_SIZE = 50
AUDIT_WINDOW = 200

__all__ = ["OrderControllerMulti", "build_default_controller", "describe_controller"]


class OrderControllerMulti:
    def __init__(self, repository=None, service=None):
        self._repository = repository or OrderRepository()
        self._service = service or OrderService()
        self._audit = []

    def create_order(self, payload):
        """创建订单，返回订单号与初始状态。"""
        order_id = self._service.create_order(payload)
        self._remember("create", order_id, payload.get("actor", "anonymous"))
        LOGGER.info("created order %s for customer %s with %s items and total %s through channel %s", order_id, payload.get("customer_id"), payload.get("items"), payload.get("total"), payload.get("channel"))
        return {"order_id": order_id, "status": STATUS_NEW}

    def get_order(self, order_id):
        """按订单号查询订单详情。"""
        record = self._repository.find_by_id(order_id)
        if record is None:
            return {"order_id": order_id, "status": STATUS_MISSING}
        return self._present(record)

    def list_orders(self, customer_id, page=1, page_size=20):
        """按客户分页列出订单。"""
        if page_size > MAX_PAGE_SIZE:
            page_size = MAX_PAGE_SIZE
        records = self._service.list_orders(customer_id, page, page_size)
        return [self._present(record) for record in records]

    def cancel_order(self, order_id, reason):
        """取消订单；已支付订单先走退款。"""
        record = self._service.load_order(order_id)
        if record is None:
            return False
        if record.get("status") == STATUS_PAID:
            self._service.refund_order(order_id, reason)
        self._service.mark_cancelled(order_id, reason)
        self._remember("cancel", order_id, reason)
        LOGGER.warning("cancelled order %s because %s", order_id, reason)
        return True

    def attach_note(self, order_id, note):
        """给订单追加一条内部备注。"""
        trimmed = self._trim(note)
        self._service.append_note(order_id, trimmed)
        return trimmed

    def handle_action(self, action, payload):
        """按动作名分派请求。"""
        if action == "create":
            return self.create_order(payload)
        if action == "cancel":
            return self.cancel_order(payload.get("order_id"), payload.get("reason", ""))
        return {"error": "unknown action", "action": action}

    def export_audit(self):
        """返回最近的审计记录，由调用方决定怎么序列化。"""
        return list(self._audit[:AUDIT_WINDOW])

    def service_name(self):
        return self._service.name

    def order_count(self):
        return len(self._repository.all())

    def _present(self, record):
        return {
            "order_id": record.get("order_id"),
            "status": record.get("status", STATUS_NEW),
            "total": record.get("total", 0),
            "customer": record.get("customer_id"),
        }

    def _remember(self, action, order_id, actor):
        self._audit.append({"action": action, "order_id": order_id, "actor": actor})
        if len(self._audit) > AUDIT_WINDOW:
            del self._audit[0]

    def _trim(self, note):
        try:
            return str(note).strip()
        except (TypeError, ValueError):
            return ""


def build_default_controller(repository=None, service=None):
    LOGGER.info("building default order controller")
    return OrderControllerMulti(repository, service)


def _parse_total(raw):
    try:
        return float(raw)
    except (TypeError, ValueError):
        return 0.0


def describe_controller(controller):
    """返回控制器的可读描述。"""
    return "OrderControllerMulti(service=%s, orders=%d)" % (
        controller.service_name(),
        controller.order_count(),
    )
```

## 2. 埋了哪 6 处违规

| # | 期望违规 | 规则 | 码 / checker | 行 | severity |
| --- | --- | --- | --- | --- | --- |

| 2 | 模块缺 docstring | DOC-001 | （无码）/ `missing_docstring` | 1 | warning |
| 3 | 类缺 docstring | DOC-001 | 同上 | 21 | warning |
| 4 | 顶层函数缺 docstring | DOC-001 | 同上 | 104 | warning |
| 5 | 未使用的导入 | STYLE-002 | F401 / `style_lint` | 1 | error |
| 6 | 单行超 100 列 | STYLE-001 | E501 / `style_lint` | 31（207 字符） | warning |
| 7 | 硬编码口令 | SEC-004 | S105 / `style_lint` | 9 | error |

按**规则**计 6 条，按**违规条目**计 8 条（DOC-001 一条规则对 module / class / function 各产出一条）。
覆盖 4 种 checker：`forbidden_dependency`、`missing_docstring`、`style_lint`、`missing_tests`。

案例里同时放了**反面锚点**（存在可疑写法但**不该**报，已逐条断言未命中）：私有顶层函数 `_parse_total`、
四个方法、允许方向的 `from shop.order_service import OrderService`，以及除第 31 行外全部 ≤95 字符的行。

## 3. "不指定规则"是怎么证明的

- CLI 命令里**没有** `--rules` / `--validators` / `--dependencies`；子会话的 `demo.py` 对**真实 argv** 逐项断言并写进 `evidence.json`。
- 每个场景都断言 `len(matched_rules) + len(skipped_rules) == 43`：场景 A 是 **41 + 2**，场景 B/C 是 **43 + 0**，没有静默丢弃。
- `RuleSet.identity` 在 7 次运行里恒为 `sha256:7a19264fd5790c71c8a10cee198fd23f876f4cdf04ec2307e6f93e8a72cb077d`，来源文件 43 个。

## 4. 检测结果

### 4.1 三个场景

| 场景 | 上下文 | 决策 | CLI 退出码 | 违规条目 | 命中规则 |
| --- | --- | --- | --- | --- | --- |
| A 纯静态 | `--layer controller`，不声明 `operation` | block | 1 | 7 | ARCH-001、DOC-001、STYLE-002、STYLE-001、SEC-004 |
| B 变更 | 再加 `--operation edit --changed …` | block | 1 | 8 | A 的 5 条 + **TESTING-001** |

`tool.pytest@1.0 / unavailable`，且 `missing_tests` / `failing_tests` 被移出 `served_checkers`。

**场景 A 里 TESTING-001/002 没命中，不是"判定合规"**——它的 scope 要求 `operation=[create,edit]`，

## 5. 必须一起读的 6 条边界

1. **SEC-004 只能当提醒，不是"没有硬编码凭据"的证明。** 规则文件自己写明了实测覆盖边界：
   S105/S106/S107 是**按变量名 / 参数名做的字符串启发式**，不是语义分析。漏判（`API_KEY`、`api_key`、
   字典值 `{"password": "hunter2"}`、`os.environ.get("PASSWORD", "hunter2")` 都不报）与
   误报（`TOKEN_EXPIRED = "token_expired"` 这类错误码常量被判成 hardcoded password）两头都不严，
   规则注释甚至点名了仓库里的真实误报现场 `src/policy_api/errors.py:43`。
   所以"本例命中"说明的是**名字像口令**，不是**值真的危险**。
2. **TESTING-001 的违规是文件级**（`line=null`）。它不是"某一行有问题"，而是"这次变更缺测试"；
   给它硬填行号就是编数据。
3. **证据强度不齐平。** 场景 B 的 `tool.pytest` 记录 `tool=null`（选择阶段就出了结论，
   pytest 进程没被执行，只跑了 `--version` 探针）；而 `tool.ruff` 的证据带
   `version=0.14.13` / `config_sha256` / `exit_code`。消费方不能假定 `tool` 一定存在。
4. **`matched` ≠ `hit`。** 场景 A 有 41 条规则"范围命中"，但只有 5 条产出违规。
   判断"规则集有没有在看这个文件"不能只看 `violations`；反过来，`matched` 多也不代表被判红。
5. **"修 TESTING-001"做不到纯净的单点修改。** 案例的桩在 `:22-:24`
   （`repository or OrderRepository()`）让 Controller 与 Service 各持一个仓储，
   `get_order` / `order_count` 读不到 `create_order` 写的行——任何**真能通过**的同名测试都会 3 红 1 绿
   并触发 TESTING-002。所以那一份副本是"加测试 + 生产文件一处最小修复"。
   为了把归因分离干净，另做了对照：`ws-fix-arch` 同样改了 `:22-:24` 但**不加测试**，
   TESTING-001 依旧在 ⇒ TESTING-001 的消失只能归因于"新增了测试"。
6. **行号会随修复位移**（删一行、加一段注释都会挪），所以归因判据用的是"规则 + 语义锚点"，
   不是抄死的行号。

## 6. 复核链：验证者也被验证

这一轮的价值不只在"6/6 命中"，还在于**复核本身出过错，而且被抓出来了**：

1. 子会话 1 写案例 + 检测，`demo.py` 98 条断言通过。
2. 子会话 2 做归因反证。**它第一版有 8 条断言失败。** Lead 逐条核查后确认：
   - **5 条**（`其余 5 条的每一处违规都原样保留`）的失败信息里给出的**计数已经是对的**
     （被修的那条 = 0，其余 5 条与基线一致）——说明失败发生在复核脚本的**锚点匹配层**，
     不是规则集出了问题；
   - **3 条**是真问题：为修 TESTING-001 写的测试跑不过，于是触发 TESTING-002（见第 5 节第 5 条）。
3. 子会话修正了测试与判据（改成"规则 + 语义锚点"）后收敛到 **132/132**。
4. **Lead 不依赖任何子会话脚本**，直接从 7 份原始 CLI JSON 复算归因矩阵，结论一致。

结论：**"子会话说通过了"不等于通过**——中间态确实红过，红的 5 条是复核脚本的锅、3 条是被测案例的锅。
