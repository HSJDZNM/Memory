# 规则效果演示报告：五种 checker 类型 × 正例 / 反例 × 全流程

> 每条规则给一条正例、一条反例，全部走**真实验证器流水线**（真的起 Ruff / pytest 子进程），
> 不 mock、不伪造证据。执行由 5 个子会话各自完成，本报告的最终数字由 Lead 用 CLI 复跑核对。

## 0. 一句话结论

43 条规则归 **5 种 checker**（也就是仓库全部 5 种判定机制）。每种抽一条、各给正反例：
**5 条反例全部命中并阻断（DOC-001 按声明的 warning 语义告警），5 条正例全部放行**，
且每次运行里**只有目标规则**产生违规。规则"管什么、不管什么"确实由 `policies/` 里的数据决定，
而不是由代码里的特判决定。

## 1. 演示范围：为什么是这 5 条

规则集构成（实测，`RuleSet.identity = sha256:7a19264fd5790c71c8a10cee198fd23f876f4cdf04ec2307e6f93e8a72cb077d`）：

| 维度 | 分布 |
| --- | --- |
| 总数 | 43 条 |
| 领域 | coding 21、security 19、testing 2、architecture 1 |
| checker | `style_lint` 39、`forbidden_dependency` 1、`missing_docstring` 1、`missing_tests` 1、`failing_tests` 1 |
| severity | error 24、warning 19 |
| source.kind | `standard`（镜像文档提炼）38、`project-policy`（项目自订）5 |
| enforcement.type | `deterministic` 43（无第二种） |
| scope 维度使用 | `language` 43、`layer` 1、`operation` 2 |
| 有 `tests/fixtures/rules/<ID>/` 语料夹具 | 40 / 43 |

抽中矩阵 —— 5 条同时覆盖**全部 checker 类型**与**全部领域**：

| # | checker 类型 | 抽中的规则 | 领域 | severity | source.kind | 语料夹具 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `forbidden_dependency` | ARCH-001 | architecture | error | project-policy | 无 |
| 2 | `missing_docstring` | DOC-001 | coding | warning | standard | 有 |
| 3 | `style_lint` | SEC-001 | security | error | standard | 有 |
| 4 | `missing_tests` | TESTING-001 | testing | error | project-policy | 无 |
| 5 | `failing_tests` | TESTING-002 | testing | error | project-policy | 无 |

**3 条没有语料夹具不是漏了。** 覆盖率门禁只强制 `source.kind=standard`；而这三条要么要求
`layer=controller`（ARCH-001），要么要求 `operation`（TESTING-001 / TESTING-002），
而夹具契约固定为 `layer="fixture"` 且**不声明 `operation`**——它们在那套契约里根本命中不了。
[tests/fixtures/rules/README.md](../../../tests/fixtures/rules/README.md) 把这件事写成了结论：
"那说明这条规则的正反例需要另一种调用方式，而不是测试该放宽断言"。
本报告用的就是"另一种调用方式"：受控工作区 + 显式上下文。

## 2. "全流程"指什么

| 段 | 做什么 | 本仓库的实现 | 演示里的落点 |
| --- | --- | --- | --- |
| ① 溯源 | 这条规则从哪来，来源文件真的存在吗 | `source.kind` / `source.path`；`standard` 规则另有 `knowledge/corpus.yaml` 的 `rule_sources` 登记 | 每条都验了 `Path.exists()`；DOC-001 / SEC-001 追到 chunk_id |
| ② 加载 | 规则 YAML → 规则集，原子、可复核 | `policy.loader.load_rule_set`，`RuleSet.identity` | 43 条，identity 见上 |
| ③ 作用域 | 这条规则管不管这个上下文 | `policy.scope` → `matched_rules` / `skipped_rules`（带原因） | 实测出三种跳过原因 |
| ④ 证据 | 谁去查、查出了什么 | `validators.pipeline.run_pipeline`：内置 `py.source`/`py.ast`/`py.depgraph`/`py.docstring` + 外部 `tool.ruff`/`tool.pytest` | 真的起子进程，带版本与配置哈希 |
| ⑤ 判定 | 证据 → 决策 | `policy.engine.evaluate`——**全仓库唯一判定入口** | `info`/`warning` → `allow_with_warnings`；`error`/`critical` → `block` |
| ⑥ 路由 | 决策怎么约束调用方 | CLI 退出码 0 / 1 / 2；dsh Hook `exit 2` 阻断；Policy API 结构化错误码；编排层按 Decision 分支 | 本报告用 CLI 退出码取证 |

②–⑤ 是同一条链路：`python -m policy.check`、dsh Hook、Policy API 与 Phase 5 闭环
最终都调用 `policy.engine.evaluate`，不存在第二条判定路径。

## 4. 逐条演示

### 4.1 ARCH-001 · `forbidden_dependency`（architecture）

规则：[policies/architecture/ARCH-001.yaml](../../../policies/architecture/ARCH-001.yaml) ｜ severity `error` ｜ scope `language=python` + `layer=controller`
语义：Controller 不得直接访问 Repository，必须经 Service；依赖由 AST / 依赖图证据判定，**不采信调用方声明**。

| | 文件 | 决策 | 关键证据 |
| --- | --- | --- | --- |
| 反例 | `tests/fixtures/validators/project/src/shop/order_controller_bad.py` | **block** | `order_controller_bad.py:3`，detail "layer=controller 直接依赖 repository · from_import · internal · shop.order_repository"，验证器 `py.depgraph@1.0` |
| 正例 | `tests/fixtures/validators/project/src/shop/order_controller.py` | **allow** | 依赖只有 `service`（`shop.order_service`），ARCH-001 零命中 |

本类型独有的约束能力 —— **范围本身就是约束**：

- 同一个反例文件、只把 `--layer` 从 `controller` 改成 `service`，决策从 **block 变 allow**，
  ARCH-001 进 `skipped_rules`，原因 `layer service != controller`。
  旁证：`served_checkers` 少了 `forbidden_dependency`——规则不参与时，`py.depgraph` **根本没被选中**。
- **失败关闭**：`tests/fixtures/validators/project/src/shop/dynamic_dependency.py`（`importlib.import_module(name)`）决策 **block**，
  ARCH-001 以 **critical** 阻断，blockers 为 `py.depgraph@1.0 / failed`。
  "解析不了"不等于"没有依赖"。

### 4.2 DOC-001 · `missing_docstring`（coding）

规则：[policies/coding/DOC-001.yaml](../../../policies/coding/DOC-001.yaml) ｜ severity **`warning`** ｜ scope `language=python`
规则体：`targets: [module, class, function]`、`include_private: false`

| | 文件 | 决策 | 关键证据 |
| --- | --- | --- | --- |
| 反例 | `tests/fixtures/rules/DOC-001/bad.py` | **allow_with_warnings** | 3 条 warning：`bad.py:1` 模块、`bad.py:4` 类 `OrderCalculator`、`bad.py:9` 函数 `describe`；验证器 `py.docstring@1.0`（标准库 ast） |
| 正例 | `tests/fixtures/rules/DOC-001/good.py` | **allow** | DOC-001 零命中 |

本类型独有的约束能力 —— **warning 不等于放行，判定范围由数据决定**：

- 决策是 `allow_with_warnings` 而不是 block，但 **CLI 退出码仍是 1**：
  "需要人看一眼"不能静默跳过。
- 子会话另建探针验证边界：`py.ast` 看见了 5 个定义，其中 4 个缺 docstring
  （method `OrderCalculator.total`、私有类 `_Internal`、method `_Internal.hidden`、私有函数 `_helper`），
  DOC-001 **零命中**——证明范围确实由 YAML 里 `targets`/`include_private` 两行数据决定，不是"没看见"。
- 被引原文（PEP 257）比规则体更宽（原文提到 public methods 也应有 docstring），
  规则刻意收窄并在 `source.note` 里写明"检查对象集合由本文件的 targets 决定"——
  **引用同一段原文的规则，判定范围可以比原文窄，且这件事必须写在数据里**。

### 4.3 SEC-001 · `style_lint`（security）

规则：[policies/security/SEC-001.yaml](../../../policies/security/SEC-001.yaml) ｜ severity `error` ｜ Ruff 码 `S102` / `S307`
溯源：OWASP Cheat Sheet "API8:2019 Injection → RCE"

| | 文件 | 决策 | 关键证据 |
| --- | --- | --- | --- |
| 反例 | `tests/fixtures/rules/SEC-001/bad.py` | **block** | `S307 @ bad.py:8`（"consider using ast.literal_eval"）、`S102 @ bad.py:9`（"Use of exec detected"） |
| 正例 | `tests/fixtures/rules/SEC-001/good.py` | **allow** | SEC-001 零命中 |

本类型独有的约束能力 —— **"码 → 规则"的归属双向一致，工具不决定策略**：

- 证据可追溯：`tool.ruff@1.0` ｜ ruff **0.14.13** ｜ 配置 `validation/ruff.toml` ｜
  `config_sha256 = sha256:7e22f1da332e56dfcbe16c849c6dd9414a82c56209a3a398153d1472b1e329a3` ｜ 退出码 1
- 规则声明的码必须被 `validation/ruff.toml` 的 `select` 选中，`select` 的码也必须有规则归属；
  单向不一致等于规则静默失效。本次 `unmapped_findings = 0`。
- 同一个诊断码归哪条规则由**规则 YAML** 决定，不由工具决定；没有归属的诊断只计数、不判定。

### 4.4 TESTING-001 · `missing_tests`（testing）

规则：[policies/testing/TESTING-001.yaml](../../../policies/testing/TESTING-001.yaml) ｜ severity `error` ｜ scope `language=python` + **`operation: [create, edit]`**
载体：受控工作区（从 `tests/fixtures/validators/project/` 只读复制），上下文 `layer=service`、`changed=src/shop/order_service.py`

| | 场景 | 决策 | 关键证据 |
| --- | --- | --- | --- |
| 反例 | 工作区删掉 `tests/` | **block** | `selection = {"level": "none", "missing": ["src/shop/order_service.py"], "nodeids": []}`；命中来自**选择阶段**，pytest 子进程根本没起（`tool.pytest` 记录 `tool=null`） |
| 正例 | 保留 `tests/test_order_service.py` | **allow** | `selection.level = related`、`nodeids = ["tests/test_order_service.py"]`；`tool.pytest@1.0` status=ok、pytest **9.1.1**、`config_sha256 = sha256:83d818b4…05c36`、退出码 0——**测试真的跑了** |

本类型独有的约束能力 —— **"证据不足"与"检查通过"是两件事**：

- 不声明 `operation` → TESTING-001 进 `skipped_rules`，原因 `operation <missing> != [create, edit]`。
- 声明了 `operation` 但**不给变更集** → 证据不足，`tool.pytest@1.0` 记 `unavailable`，
  TESTING-001 以 **critical** 阻断。**没有变更集不等于没有风险。**
- "跑什么测试"与"有没有对应测试"被刻意分成两条判断：只看 related / package 决定有没有，
  升级到 package / suite 只决定跑什么。否则"工作区里随便有个测试"就能让这条规则永远不触发。

### 4.5 TESTING-002 · `failing_tests`（testing）

规则：[policies/testing/TESTING-002.yaml](../../../policies/testing/TESTING-002.yaml) ｜ severity `error` ｜ scope `language=python` + `operation: [create, edit]` ｜ 工具 `pytest`

| | 场景 | 决策 | 关键证据 |
| --- | --- | --- | --- |
| 反例 | `tests/test_order_service.py` 换成 `def test_broken(): assert 1 == 2` | **block** | 违规仅 1 条且就是 TESTING-002：消息 `FAILED tests/test_order_service.py::test_broken：assert 1 == 2`，detail `tool.pytest@1.0 / pytest=9.1.1（退出码 1）` |
| 正例 | 恢复夹具原样 | **allow** | `tool.pytest` status=ok、exit_code=0、"选中的测试全部通过"；`selection` 与反例逐字节相同 |

本类型独有的约束能力 —— **阻断能指名道姓**：

- 证据给出**失败用例名 + 断言差异**，不是笼统的"测试没过"。
- 与 TESTING-001 分工：同一个 `tool.pytest` 子进程同时服务两条规则——
  `selection.missing` → TESTING-001，`-rf` 摘要里的失败用例 → TESTING-002。
  两条规则互不抵消，各自按 scope 参与。
- 确定性：两次运行 `cases` 子文档 sha256 完全相同（`e269a235…`），可重放。

## 5. 跨条结论：这套约束能做什么，边界在哪

### 5.1 跳过是显式的，不是默认放行

三条规则被跳过时都给出了机器可读的原因，且 `matched + skipped = 43`，没有静默丢弃：

| 跳过原因（实测原文） | 触发场景 |
| --- | --- |
| `layer service != controller` | ARCH-001 换 layer |
| `operation <missing> != [create, edit]` | TESTING-001 / 002 不声明 operation |

### 5.2 路由层看不出"跳过了"——这是要看细节的地方

不声明 `operation` 时：决策 `allow`、违规 0 条、**退出码 0**——与"真的检查过且没问题"完全相同，
"这条规则没参与判定"只写在 `result.skipped_rules[].reasons` 里。
**只看退出码的调用方会把 skipped 当成 pass。** 要区分，必须读 `skipped_rules`
（dsh Hook 侧同样：AGENTS.md 第 23 条要求把"需要验证器证据"的规则记进 `skipped_rules` 并写明原因）。

### 5.3 失败关闭有两条被实测出来的路径

| 路径 | 触发方式 | 实测结果 |
| --- | --- | --- |
| 验证器**失败** | `dynamic_dependency.py` 动态 import | ARCH-001 以 `critical` 阻断；blocker `py.depgraph@1.0 / failed` |
| 验证器**不可用** | 有 `operation` 但没有变更集 | TESTING-001 / 002 各 1 条 critical；`tool.pytest@1.0` 记 `unavailable` |

两条都是"证据链不成立"，而不是"没发现问题"；同一批里的其他 PASS 抵消不了它。

### 5.4 验证器记录有两种形状，消费方不能假定字段齐全

内置验证器（`py.source` / `py.ast` / `py.depgraph` / `py.docstring`）的 `tool` 字段是 `null`，
"跑过"只由 `status` / `reason` 表达；外部工具验证器（`tool.ruff` / `tool.pytest`）才有
`version` / `config` / `config_sha256` / `exit_code`。演示里两种都出现过。

### 5.5 复现这次演示时踩到的一个坑

用 `-p no:cacheprovider` 跑 pytest 在本仓库**会得到 0 条测试证据**：
[pytest.ini](../../../pytest.ini) 第 3 行的 `cache_dir` 由 cacheprovider 插件注册，
第 5 行的 `--strict-config` 把它升级成致命配置错误（退出码 4，`Unknown config option: cache_dir`）。
正确口径是**不要禁用该插件**：直接 `python -m pytest <nodeid>`（仓库 README 的写法），
需要隔离缓存时用 `--override-ini=cache_dir=<自己的目录>`。
仓库自己的 `tool.pytest` 调用模板就是 `-p no:cacheprovider` **加** `-o addopts=` 一起用的。
